# 套索工具实时平滑 — 可行性分析与实施计划

> 版本：v2（2026-10-12）｜状态：**方案 A 的 P0–P4 已实现，待真机验收**（P5 明确不做）
> 目标：在套索工具**实际绘制过程中**对笔迹轨迹做实时平滑（对齐 PS 原生 Smoothing / Lazy Nezumi Pro 的观感）。
> 明确排除：「选区已生成之后再平滑」——即现有「选区改造」路径（`src/utils/SelectionHandler.ts`），本次不动它。
> v1 只做分析与规划；v2 增补第 9 节「实现状态与待验收清单」，第 1–8 节保留原始分析（结论未变）。

---

## 1. 结论摘要

**一句话结论**：这个功能在当前架构下**必须把平滑做在「PS 收到鼠标输入之前」**，而 UXP 层完全没有画布指针输入能力，所以真正的实时平滑**只有一条路：扩展现有原生守护进程（`native/HotkeyDaemon`），挂 `WH_MOUSE_LL` 全局鼠标钩子做输入层滤波 + `SendInput` 回注**。UXP 侧只承担「布防/参数下发/UI」。

三个必须让决策者先知道的判断：

| 判断 | 依据 | 推论 |
| --- | --- | --- |
| UXP 观测不到画布上的鼠标轨迹 | 全仓无任何画布指针 API；`app.tsx:552` 的 `document.addEventListener('mousemove')` 监听的是**插件面板自身 DOM**，不是 PS 画布 | 绘制过程中 UXP 是**盲区**，任何"纯插件内实现实时平滑"的方案都不成立 |
| UXP 唯一能拿到套索结果的时刻是**提交后** | `app.tsx:534` 订阅 `set` 通知并筛 `channel + _selection`，`handleSelectionChange`（`app.tsx:1278`）在其后 | 在 UXP 侧做平滑 ⇒ 天然是"事后平滑"，正是本次要排除的形态 |
| 原生进程已经具备扩展的全部骨架 | 已有常驻 `WH_KEYBOARD_LL` 钩子线程（`Program.cs:859`）、`IsPhotoshopForeground()` 前台闸门（`Program.cs:765`）、`ws://127.0.0.1:18923` 协议（`HotkeyBridge.ts:24`） | 新增鼠标钩子与 `smoothArm` 消息属于**同构扩展**，不是新架构 |

**推荐路线**：P0 先做一个"只观测不干预"的探针阶段来验证钩子可行性（**这是去/留决策门**），通过后再投入滤波算法；算法分标准 / 拉绳 / 追笔三档；提交时的轮廓精修作为可选质量增强，而非主路径。

### 2.2 三个候选插入点

```
 [输入: 鼠标/数位板] → [PS 内部轨迹采样] → [生成选区·蚂蚁线] → [派发 set 通知] → [UXP 消费]
        ▲                      ▲                                                      ▲
     插入点 1               插入点 3                                              插入点 2
   (输入层/PS 之前)      (PS 轨迹后处理)                                    (选区已生成之后)
```

- **插入点 1 — 输入层（PS 收到输入之前）**：拦截原始鼠标事件、滤波、回注。**唯一能做到"绘制过程中实时"的位置**。需要原生钩子。目标特性（Lazy Nezumi 路线）就在这里实现。
- **插入点 2 — 选区生成之后（UXP 侧）**：即现有「选区改造」的形态（`smartBrushWorkspace` / 自写 `applyExpand`）。**本次明确排除**。补充记录：这条路的栅格域平滑有固有损失（抗锯齿软边掩码 → 需要阈值化才能取轮廓，亚像素信息丢失），这也是它不适合作为主路径的技术原因，而不只是"重复功能"。
- **插入点 3 — PS 内部轨迹后处理**：不可行。PS 不向插件暴露套索的中间轨迹，也没有"对正在绘制的轨迹施加平滑"的接口（`Select > Modify > Smooth` 是**提交后**对掩码的形态学处理，属于插入点 2 的变体）。

### 2.3 待 Phase 0 验证的观测性假设

以下三条目前**不宣称成立**，必须在 P0 用日志核实（它们是方案可行性的前置条件）：

1. PS 在套索拖拽**过程中**是否会派发 `channel+selection` 的 `set` 通知？——预期**不会**（提交才派发）。若实际会派发，插入点 2 的实时性讨论需要重开。
2. 左键按下后，`WH_MOUSE_LL` 在 PS 画布上是否收到**连续且未被合并**的 `WM_MOUSEMOVE`（≥60 条/秒）？
3. 数位板/触控笔输入是否走 `WH_MOUSE_LL`？（若 PS 走 Wintab/Windows Ink 直读，钩子可能看不到笔输入 ⇒ **平板用户平滑失效**，这是本方案最大的单点风险）

## 3. 目标特性拆解（对齐 PS / Lazy Nezumi Pro）

### 3.1 要还原的核心特性

| 特性 | 说明 | 验收口径（建议） |
| --- | --- | --- |
| **抖动抑制** | 衰减手抖引入的高频小幅噪声 | 静止/慢速下，输入 1px 幅度 ±2px 抖动，输出轨迹抖动幅度 ≤0.5px |
| **延迟（跟手感）** | 绘制点落后光标的时间/距离 | 参数量化：给定平滑强度下，稳态跟随距离 ≤ 预设值（如 ≤12px）；松手后 ≤80ms 收敛到终点 |
| **拐角保留** | 过度平滑会把直角磨圆 | 90° 直角处圆角半径 ≤ 预设值（如 ≤6px）；快速折返不出现"甩尾过冲" |
| **起笔锚定** | 起点必须精确落在按下位置 | 起点偏差 ≤1px（起笔不能有跟随滞后） |
| **收笔追齐** | 松手后曲线要收敛到真实终点 | 松手后 ≤80ms 内终点误差 ≤1px |
| **闭环处理** | 套索松手自动闭合 | 闭合处不出现自交/缺口；闭合段与起笔锚点严格同点 |
| **三档模式** | 对应 PS 的 Smoothing 三种行为 | 见 3.3 |

### 3.2 对照分析

- **PS 原生 Brush Smoothing**（笔刷设置 / 2021+ 工具选项栏的「平滑」）：提供 `Standard`（弹簧跟随）、`Smooth`（更强阻尼）、`Stroke Catch-up`（绘制端追赶光标）、`Pulled String`（拉绳，光标与笔尖之间用一根"绳子"牵引）+ 数值 0–100。**注意：这套平滑只存在于画笔类工具，套索/选框工具没有**——这正是本功能要补的缺口。
- **Lazy Nezumi Pro**：Windows 全局鼠标平滑工具，实现方式就是 **低层鼠标钩子 + 位置滤波 + 回注**，并支持按进程启用、按住某键临时启用（stabilizer hotkey）、Wintab/Windows Ink 兼容。它是本方案"插入点 1"的现成同类实现，也印证了架构方向。
- **结论**：要还原的对象是**行为观感**（延迟/阻尼/追笔/拉绳四要素 + 强度滑杆），而不是 PS 的某个具体参数字段。因此参数面应自主设计，不必强行对齐 PS 的字段名。

### 3.3 参数建议（供讨论）

| 参数 | 建议范围 | 建议默认 | 作用 | 对应概念 |
| --- | --- | --- | --- | --- |
| `enabled` | 开/关 | 关 | 总开关（与主开关/工具联动布防） | — |
| `mode` | 标准 / 拉绳 / 追笔 | 标准 | 滤波族 | PS 三档 |
| `smoothing` | 0–100（整数） | 40 | 平滑强度总轴，映射到各模式内部系数 | PS「平滑」滑杆 |
| `radius` | 1–40 px | 8 | 抖动抑制窗口（兼作采样抽稀半径） | Lazy Nezumi «Smoothing» |
| `tension` | 0–100 | 50 | 拉绳模式的绳长/松紧 | PS Pulled String |

## 4. 技术可行性评估

### 4.1 实时性

- 链路：`鼠标硬件 → Windows 输入栈 → WH_MOUSE_LL 回调 → 滤波 → SendInput(MOUSEEVENTF_MOVE|ABSOLUTE) → Windows 输入栈 → PS`。
- 纯计算开销在**微秒级**（滤波是 O(1) 或 O(缓冲长度) 的浮点运算），硬件回报率 ~125Hz（游戏鼠标可达 500–1000Hz）⇒ 单帧预算 8ms 绰绰有余。
- **唯一真实的实时性风险不是算力，是钩子回调的排队语义**：低层钩子回调由系统串行调用，而 `SendInput` 会再走一遍输入队列。若回注事件又被自己的钩子收到（回环），会瞬间打满 ⇒ **必须在钩子内识别并直接放行"自己注入的事件"**（`dwExtraInfo` 打签名 + `LLMHF_INJECTED` 标志双重判据）。这是 P0 必须验证的第一件事。
- 观感上还要接受一个事实：**平滑 = 延迟**。光标物理位置会被拖后（这正是 PS/Lazy Nezumi 的可见现象）。需要产品上确认是否接受"光标被拖住"的观感，或改用"光标先走、笔尖滞后"的表现（后者需要隐藏系统光标，风险更高）。

### 4.2 性能与稳定性开销

| 项 | 评估 |
| --- | --- |
| 钩子系统开销 | 低层鼠标钩子对**全系统**输入增加一次回调往返。仅布防期间（PS 前台 + 套索 + 左键）安装/启用，其余时刻必须卸载或直通 |
| 内存 | 轨迹缓冲建议环形数组，固定容量（如 1024 点 × 8B ≈ 8KB），**零运行时分配** |
| 钩子线程铁律 | 继承现有约定：**钩子线程严禁阻塞 I/O**（`Program.cs:5` 已写明）。滤波不得加锁、不得写文件、不得调 WS；参数从 `volatile`/不可变快照读取 |
| 钩子被系统摘除 | Windows 有 `LowLevelHooksTimeout`：回调超时会被**静默摘钩**且不通知。必须有心跳自检 + 自动重挂 |
| 回环放大 | 见 4.1，是首号风险 |
| 杀软/权限 | 全局鼠标钩子 + `SendInput` 比键盘钩子更敏感，可能被安全软件拦截或告警。需要卸载/回退路径与文档提示 |

### 4.3 与撤销/重做的兼容

- **方案 A（输入滤波）**：对 PS 而言仍是"用户的一次连续拖拽"，只产生**一条**历史记录，撤销行为与原生套索**完全一致**。✅ 无风险。
- **方案 B（提交后几何重建）**：会插入一次 `imaging.putSelection`。必须包在 `doc.suspendHistory` 里（现有 `app.tsx:1371` 的做法），否则会在历史面板里多出一条"无意义中间步"。⚠️ 需注意：`putSelection` 自身是否可被 `suspendHistory` 合并进"套索工具"那一步，取决于 PS 版本，需实测。
- **方案 C（覆盖层自绘 + 提交时路径化）**：PS 侧看不到"用户绘制"这个动作，选区是由我们写入的 ⇒ **历史记录里不会出现"套索工具"这一步**（或只出现我们命名的那一步）。对"撤回一次回到空白"的用户预期是破坏性的。⚠️ 中高风险。

### 4.4 与选区封闭的兼容

- 方案 A：闭合完全由 PS 负责，我们的滤波只需保证**松手时输出点收敛到真实终点附近**，闭合段自动由 PS 补。✅ 最安全。唯一注意：松手瞬间的最后一个输出点不能距离起点过远，否则闭合边会是一条长直线（观感差）——这正是「收笔追齐」参数的验收点。
- 方案 B/C：闭合必须我们自己保证（多点闭合 + 非自交检查）。若平滑后轨迹出现自交（打结），PS 的选区填充规则（奇偶/非零环绕）会导致**中间被挖空**。⚠️ 需加"自交检测 + 降级为较弱平滑"的保护。

### 4.5 与「锚点调整 / 已有选区再调整」的兼容

> ⚠️ 待你确认术语（见第 6 节 Q6）。本节按三种可能解读分别给结论：

1. **PS 侧对已有选区的再调整**（「选择 > 变换选区」/快速蒙版/再次套索加减选）：方案 A 不参与这些路径（只在"新拖拽"时生效），天然兼容；需确认的是**布防范围**是否要覆盖「加减选」拖拽（建议覆盖，否则手感不一致）。
2. **路径锚点**（自由钢笔/转换为路径后的锚点）：本功能不产生路径对象，与锚点无关。若未来改用"路径化提交"（方案 C），则会涉及锚点数量与曲率分配，届时单独评估。
3. **插件内的「选区改造」参数**（`selectionSmooth` / `selectionContrast` / `selectionExpand`）：与实时平滑是**串联**关系（实时平滑决定"输入轨迹"，选区改造决定"提交后的掩码形态"）。两者叠加会互相放大效果 ⇒ 建议：实时平滑开启时，UI 上对「选区改造」给出提示（不强制禁用），并在验收阶段专门测"双开"的表现。

## 5. 实现思路对比

### 方案 A：输入层滤波（原生钩子 + 回注）— **推荐主路径**

- 原理：`WH_MOUSE_LL` 拦截左键按下后的 `WM_MOUSEMOVE`，维护轨迹状态，滤波器输出"平滑后的位置"，用 `SendInput` 回注；原事件被吞掉。
- 子模式（同一套骨架，三种滤波族）：
  - **标准（EMA/弹簧跟随）**：`out = out + k·(in − out)`，k 由强度映射。实现最简、手感最接近 PS Standard。
  - **拉绳（Pulled String）**：缓冲最近 N 个输入点，输出端以张力牵引。观感最"顺"，但延迟最大。
  - **追笔（Stroke Catch-up）**：输出端以受限速度追赶光标，快慢可控。兼顾延迟与抑制。
- 优点：**唯一真正实时**；PS 侧完全不知情 ⇒ 历史/撤销/闭合/工具选项（羽化、抗锯齿、加减选）全部原生行为，零兼容成本；参数可实时下发。
- 缺点：需要原生代码与钩子权限；平板兼容性存疑；光标会被拖后（需产品确认）；杀软敏感性；调试链路长（跨进程）。
- 复杂度：**高**（原生 + IPC + 算法 + 安全边界）。
- 适用：追求"原生级手感"的主线需求。

### 方案 B：提交后几何重建（选区轮廓平滑）

- 原理：在 `handleSelectionChange` 的既有模态内，增加一步"把当前选区掩码取轮廓 → 抽稀 → 光顺（Chaikin/高斯/最小二乘）→ 回写 `putSelection`"，排在「选区改造」**之前**，与填充合并进同一次 `suspendHistory`。
- 优点：纯 UXP/JS，无原生依赖，无安全风险；复用现有 `psRead`/模态/历史基建；算法可离线对拍（符合本仓 `algo-param-bench` 习惯）；参数面与现有子面板同构。
- 缺点：**不是实时**（松手后才生效，有可感知的"跳一下"）；栅格域取轮廓有量化损失；需处理自交与写回自触发。
- 复杂度：**低–中**。可 1–2 天出原型。
- 适用：作为**兜底/降级路径**（平板用户不生效时），或未来做"精修"叠加层。**不是本次主路径。**

### 方案 C：原生覆盖层自绘 + 提交时路径化

- 原理：布防期间吞掉鼠标事件，由一个 Win32 透明置顶窗口在 PS 画布上**自绘平滑轨迹**（真·零 IPC 延迟的实时预览）；松手时把平滑后的点列交给 UXP，转换为选区（栅格化多边形 → `putSelection`，或写工作路径 → 转选区）。
- 优点：实时反馈质量最高（自己画，不受 PS 输入栈限制）；最终几何完全可控（可以做到亚像素光顺）；平板问题天然绕开（只要钩子能拿到笔的坐标）。
- 缺点：**与 PS 画布的坐标对齐**（缩放/平移/画布位置）要自己算，且 PS 缩放后需要跟随；覆盖层窗口会与 PS 的浮层/工具提示抢 Z 序；历史记录里没有"套索"这一步（4.3 的高风险项）；工具选项栏（羽化/抗锯齿/加减选）全部失效，需要自己实现；工作量最大。
- 复杂度：**最高**。
- 适用：若方案 A 的手感被判定不达标，作为"终极质量方案"，不建议首期投入。

### 混合建议（推荐落地形态）

```
主路径     = 方案 A（输入滤波：标准/拉绳/追笔）
降级/兜底  = 方案 B（提交时轮廓精修，平板用户或手感不满意时启用）
远期备选   = 方案 C（仅当 A 被否决）
```

方案 A 与 B **不冲突**：A 决定"输入轨迹"，B 决定"提交几何"，可独立开关、分阶段上线。这也让项目在 P0 决策门失败时**仍有可交付物**（B），降低整体风险。

### 9.4 实现中的两处设计决定（可推翻）

1. **总开关关闭时不禁用参数**。参数是预置值，用户可先调好再开总开关；这与「选区改造」滑块恒可编辑一致。只有「参数不适用于当前滤波族」才走整行禁用态（张力↔拉绳、追笔↔追笔、拐角/速度适应↔标准）——对应仓库既有的「行级 `.disabled` + 标签与控件双置灰」规范。
2. **修正了一处通用 CSS 的潜在缺陷**：`.row-between.disabled .range-slider` 对传入 `className="slider-track"` 的 `RangeSlider` **不生效**（组件根节点用 `className || 'range-slider'`，传了自定义类名就没有 `.range-slider`），只写 `.range-slider` 会让禁用态没有任何视觉反馈。已把 `.slider-track` 一并列入选择器。
3. **状态广播的时序修正（必须有）**：`SetSmoothArm` 返回时钩子尚未装上（`SetWindowsHookEx` 由钩子线程异步执行），若在那里广播，`hookInstalled` 必然为 false ⇒ 面板每次启用都会先闪一下红色的「启动失败（被安全软件拦截）」。同理，拖拽开始/结束发生在**钩子线程内**，而钩子线程严禁 I/O。因此改为：`SetSmoothArm` **不广播**，统一由 `SmoothWatchdog` 上报，上报条件是「连续两个采样周期读数一致（已稳定）且与上次上报不同」—— 单周期 120ms，健康检查仍保持 2s 一次；单帧中间态不会外泄，真故障约 240ms 内如实报出。这同时让「生效中」成为可用指标 —— 它是数位板场景（钩子装上了但收不到事件）唯一的 UI 判据。

## 10. 第二轮：双钩子解耦 + 两个真机缺陷（v3，2026-10-12）

### 10.1 需求

> 平滑钩子与热键钩子必须**完全独立运行**：禁用/卸载任意一侧不得影响另一侧。
> 并修复两个真机问题：① 套索工具下开启功能，状态行误显示「待命」；② 绘制选区后显示
> 「启动失败（被安全软件拦截）」，关掉电脑管家也无法启动。

### 10.2 架构：两侧各自一个闭环

本次把两个钩子改造成**结构对称、状态零共享**的两套子系统。每一侧都自带完整的
「布防 → 装卸 → 看护 → 熔断恢复 → 状态上报」通路，任何一侧的动作都不触碰另一侧的变量。

| 维度 | 热键侧（键盘钩子） | 平滑侧（鼠标钩子） |
| --- | --- | --- |
| 钩子类型 | `WH_KEYBOARD_LL`(13) | `WH_MOUSE_LL`(14) |
| 承载线程 | `RecordingThreadProc`（`_recThreadRef`） | `MouseHookThreadProc`（`_mouseThreadRef`） |
| 句柄 | `_hookId` | `_mouseHookId` |
| 布防标志 | `_hotkeyArmed` | `_smoothArm` |
| 装卸指令 | `WM_HOOK_INSTALL` / **`WM_HOOK_UNINSTALL`（新增 0x8008）** | `WM_MOUSE_HOOK_INSTALL` / `WM_MOUSE_HOOK_UNINSTALL` |
| WS 指令 | **`hotkeyArm`（新增）** / `hotkeyStatus`（新增） | `smoothArm` / `smoothParams` / `smoothStatus` |
| 熔断标志 | `_hookSafeMode`（预算 100ms） | `_mouseHookSafeMode`（预算 30ms） |
| 熔断自愈 | `_hookSafeModeSince` + `SafeModeCooldownMs` | `_mouseSafeModeSince` + 同前 |
| 看护线程 | **`HotkeyWatchdog`（新增）** | `SmoothWatchdog` |
| 状态消息 | **`hotkeyState`（新增）** | `smoothState` |

新增/强化的四件实事：

1. **热键钩子可在运行期独立装卸**。此前键盘钩子只在进程启动时装一次、只有「全局卸载」
   才卸，因此「禁用热键」只能靠清空热键表让钩子**空转**（钩子仍挂在系统输入链上）。
   现在 `hotkeyArm` 能真正装卸它，且装卸路径只碰 `_hookId`。
2. **两条独立看护线程**（原先只有平滑侧有）。职责：线程存活探针、熔断自愈、句柄重挂。
   刻意不合并成一条 —— 合并后任一侧循环卡住/抛异常都会连带拖住另一侧。
3. **钩子线程逐轮异常隔离**。两条消息循环里每轮都包 `try/catch`：这些循环里的指令直接调
   Win32，一次未捕获异常就会让**整条线程消失**，而低层钩子正挂在这条线程上 ——
   钩子被系统连带摘除、`_threadId` 变成死地址（`PostThreadMessage` 不报错但消息进死队列），
   该子系统从此永久失效。看护线程的 `Thread.IsAlive` 探针是唯一出路，前提是异常不能带走线程。
4. **熔断可自愈**。原先 `safeMode` 是单向闩锁：低层钩子一次卡顿（GC/换页/驱动抖动）
   就永久废掉该子系统，只能重启进程。现在冷却 30s 后由**本侧**看护线程复位并重挂。

另外两处隔离加固：`HandleClient` 断开时的三段清理（录制 / 退格删除 / 套索平滑）
改为**各自 try/catch**（原先任一段抛异常都会跳过后面的清理）；`WatchPhotoshop` 整轮包
try/catch —— 它产出的 `_psPids` 是两个钩子共用的前置条件，这条线程一死两侧会同时「莫名失效」。

### 10.3 修复 ①：套索下状态行误显示「待命」

**根因（确定性缺陷，非环境问题）**：布防意图的镜像原先只是实例字段 `lassoArmed`，
而状态行的文案与配色完全依赖它。布防是在 300ms 工具巡检里**异步**完成的 —— 那一刻
没有任何 `state` 变化 ⇒ **不重渲染** ⇒ 状态行停留在布防前算出的
「待命（当前不是套索工具）」。只有等到别的原因触发重渲染（daemon 回报下一帧、绘制选区…）
才会跳到真实文案 —— 与用户观察到的「开启时显示待命，绘制后才变成别的话」完全吻合。

**改法**：镜像进 `state.smoothArmed`（仅在跃变时 `setState`，300ms 巡检不会造成渲染抖动），
状态行一律按 state 派生。同时新增 `smoothToolId` / `smoothToolErr` 两个 state 字段，
把「工具读不到」与「读到了但不是套索」在界面上分开：
`待命（无法读取当前工具）` / `待命（当前工具：多边形套索）`（未知 ID 原样显示枚举名）。
这样「工具读取链路故障」与「用户工具选错」一次就能分辨，不必再来回猜。

### 10.4 修复 ②：「启动失败（被安全软件拦截）」

**先证伪了「安全软件」这条假设**（三组证据）：

1. 写了一个独立探针程序，用**与守护进程完全相同的 P/Invoke 写法**尝试安装
   `WH_MOUSE_LL`/`WH_KEYBOARD_LL`：16 种组合（有无显式 `EntryPoint`、`A`/`W` 后缀、
   `hMod = GetModuleHandle(null)` 或 `NULL`）**全部 OK**。⇒ 系统策略与写法都没问题。
2. 查询**正在运行的**守护进程 `getState`：`"version": "2026-09-06.1"`，且响应里
   **完全没有** `smoothArmed` / `smoothHookInstalled` 等字段。
3. 安装目录 `%LOCALAPPDATA%\JWautofill\daemon\` 里的 exe 是 **9 月 7 日**的产物，
   `daemon.log` 首行版本同样是 `2026-09-06.1`。

**根因**：面板侧 `launchDaemon` 从未被调用；守护进程由**开机自启**从安装目录拉起，
而安装目录的副本**不会自己更新**（只有在「从插件目录启动 → 比对新旧 → 拷贝到安装目录」
这条自安装路径上才会更新）。于是跑的一直是 9 月的旧进程 —— 它根本不认识
`smoothArm`（未知 type 静默丢弃），面板因此永远收不到 `smoothState`，
`hookInstalled` 恒为 `false` ⇒ 被文案判成「启动失败（被安全软件拦截）」。

**改法（两层）**：
- **能力协商**：守护进程上报 `protocol: "2.0"` 与 `features: [hotkey, hotkeyArm, hotkeyState,
  smooth, smoothState, watchdogs]`；`smoothState` 每帧带 `protocol`。
- **能力探测**：UXP 侧建连后主动发一次 `smoothStatus` 询问，`PROBE_TIMEOUT_MS = 2500ms`
  内收不到任何 `smoothState` ⇒ 标记 `unsupported`，状态行如实显示
  **「守护进程版本过旧，请重启守护进程」**（红色）。收到任意一帧即清除该标记，
  每次重连重新计时 —— 把「版本过旧」与「钩子被拦截」彻底分开，
  不再让一个版本问题伪装成安全问题。

**现场处置**：更新并重启本机安装的守护进程（见 10.6）。

### 10.5 边界说明：进程级开关天然是全局的

必须区分两个层级，二者不可混为一谈：

| 层级 | 控制点 | 影响范围 |
| --- | --- | --- |
| **子系统级**（本次解耦的目标） | `smoothArm` / `hotkeyArm`、各自熔断、各自看护、各自状态 | 只影响自己那一侧 |
| **进程级** | 面板「守护进程」开关（`shutdown`）、「卸载」（`uninstall`）、开机自启 | 两者同时停（进程没了，两个钩子都不存在） |

「功能快捷键」子面板右上角那个开关的语义是**服务连接状态**（文案「服务已就绪 / 服务未启动」），
即进程级。若要求「关掉它但平滑继续工作」，唯一办法是把两个钩子拆到**两个独立进程**
（各自的 exe / 自启动项 / 安装目录），成本与维护面显著上升。本次不做，按需再议。

### 10.6.1 顺手修掉的第三个缺陷：更新时可能留下「无守护进程」空窗

现场更新守护进程时真机复现了一次：从插件目录启动新版后，**机器上变成零个守护进程**
（面板显示「服务未启动」、热键全失效），必须再启动一次才恢复。

根因在 `EnsureSelfInstalled()` 的两步之间：它先 `p.Kill()` 停旧副本、`File.Copy` 覆盖，
再枚举进程判断「安装副本是否已在跑」，据此决定要不要拉起。而
**`Process.Kill()` 只是「请求终止」，进程要过几毫秒才真正退出** ⇒ 那次枚举仍会把
刚被杀的进程算作在跑 ⇒ `otherRunning = true` ⇒ 跳过拉起并 `Environment.Exit(0)` ⇒ 空窗。
同一个异步性还会导致 `File.Copy` 撞上未释放的文件锁（被外层 `catch` 吞掉，日志只说
「拷贝到安装目录失败」，安装目录里仍是旧 exe）。

**改法**：Kill 之后 `p.WaitForExit(3000)` 等它真退出，再拷贝、再做在跑判断。
真机验证：安装副本在跑时再次启动插件目录副本 ⇒ 结果恰好是一个存活的新版守护进程（此前会变成零个）。

### 10.6.2 顺手补上「静默死亡」的可诊断性

排查过程中发现：`daemon.log` 是 `FileMode.Create`，**每次重启都抹掉上一轮日志** ——
所以「守护进程忽然没了」这类问题事后永远查不到原因（新进程一启动，旧证据就没了，
只剩一段干净的启动序列）。已改为：

- **追加模式 + 每次启动写分隔行**（含时间/版本/进程号），单文件超 1MB 自动截断；
- 注册 `AppDomain.UnhandledException` / `ProcessExit` / `TaskScheduler.UnobservedTaskException`，
  在**崩溃路径上绕过日志队列同步落盘**（队列此刻不可靠），把「静默死亡」变成可查。

（本次取证时 Application 事件日志里查不到任何 .NET Runtime 条目，说明那次消失是
**正常退出**而非崩溃 —— 与「使用者点了启动服务、撞上 10.6.1 的空窗缺陷」这一推断一致。）

### 10.6.3 真机实战暴露的第四个问题：长拖拽后熔断

更新到 `2026-10-12.3` 之后，真机日志（`%LOCALAPPDATA%\JWautofill\daemon\daemon.log`，
进程 1564）出现了这一段：

```
[HotkeyDaemon] 套索平滑：本次拖拽原始 1215 点 / 注入 1110 点
[HotkeyDaemon] ⚠️ 鼠标钩子回调耗时 308ms（预算 30ms），已熔断：此后只放行鼠标事件，
                套索平滑失效（键盘热键不受影响）……（30s 后自动复位并重挂）
```

先说好消息：**平滑本体是真的在跑** —— 一次拖拽吞掉 1215 个原始点、回注 1110 个滤波点，
说明四道闸门、回注、防回环全都通了。这条日志证明的不是「没实现」，而是「跑到一半被自己掐断」。

**读法（关键在行的先后顺序）**：「本次拖拽……」这行是在 `SmoothMouseDispatch` 的
`WM_LBUTTONUP` 分支里打的，而「⚠️」是在 `LowLevelMouseProc` **计时结束之后**才打的
⇒ 那条 308ms 的回调**就是抬起那一下**，不是拖拽途中的某一帧（若发生在拖拽中，两行顺序会反过来）。

那一下回调里只有三个动作：`Marshal.PtrToStructure`（廉价）、`InjectMouseMoveTo`（**一次 `SendInput`**）、
一行汇总日志。而拖拽途中 1110 次回注都远快于 30ms —— 唯一能解释 300ms 量级的是
**`SendInput` 被目标进程 / 输入栈 / 安全软件偶发阻塞**，不是算法变慢
（`LassoMouseSmoother.Step` 是纯算术、零分配，单次耗时与已处理点数无关，见类头注释）。
日志通路也已排除：钩子里的 `Console.WriteLine` 走的是 `QueueTextWriter` → **无界队列**，
不碰文件句柄（`AutoFlush` 的 `_logWriter` 只被日志线程写）。

**真正的问题是熔断策略被放大成了功能级故障**：熔断是「**一次即断**、冷却 30s」，
于是一次转瞬即逝的输入抖动就让接下来半分钟完全没有平滑 —— 用户体验即「时灵时不灵」。

**当时提出的收口方向**（已确认并实施，落地情况见 10.6.4）：

1. 鼠标侧自设预算 `MouseHookBudgetMs` 由 `30ms` 放宽到 `100~120ms`
   （Windows `LowLevelHooksTimeout` 默认 300ms，放宽后仍有 2.5× 以上余量，
   远不到被系统摘钩的程度；30ms 对含一次 `SendInput` 的回调本就过紧）；
2. 熔断改为**连续 N 次（N = 2）超预算**才触发：单次抖动只记一条日志、不熔断，
   真正持续卡顿才降级 —— 与「看护线程自愈」配合，抖动不再毁掉整个会话；
3. 抬起那一下的「回注 + 汇总日志」是**收尾动作**（不参与后续帧的实时性），
   可考虑不计入预算窗口，避免用收尾成本误判整条回路的健康度。

### 10.6.4 收口实施与实测（v2026-10-12.5）

**已实施的四项**（对应上面 1–3 的落地版）：

1. `MouseHookBudgetMs`：`30ms` → **`120ms`**；
2. 熔断判定改为**连续 `SafeModeStrikes = 2` 次**超预算才触发，任一帧回到预算内即清零计数；
3. **钩子回调内不再有任何日志**：拖拽汇总与熔断告警改由 `SmoothWatchdog` / `HotkeyWatchdog`
   在下一轮（≤120ms）代打（`_smoothPendingDragLog` / `_smoothPendingBreakLog` /
   `_hotkeyPendingBreakLog`）；`LogFromHook` 的使用范围收紧为「录制 / 解绑」这类低频路径；
4. **零 I/O 耗时拆解埋点**：回调内只写内存字段，经 `smoothState` 上报
   `budgetMs / strikes / overBudget / lastCbMs / lastCbInjectMs / maxCbMs / maxCbInjectMs /
   worstOverCbMs / worstOverInjectMs`。其中 `worstOver*` **永不重置**，
   专为事后回答「那 306ms 里到底有多少是 `SendInput`」而设（`maxCb*` 会随每一笔清零，
   等你去看时往往已被下一次拖拽覆盖）。

**运行期实测（v2026-10-12.4，`smoothState` 读数）**：

```
budgetMs=120 strikes=0 overBudget=4 maxCbMs=2 maxCbInjectMs=2 callbacks=8190 injected=1531
```

- `budgetMs=120` 生效；
- `overBudget=4` ⇒ 确实存在超 120ms 的帧，但**从未连续两次** ⇒ `strikes` 恒为 0 ——
  这正是「单次抖动不再毁掉整个会话」的预期表现；
- **`maxCbInjectMs == maxCbMs`（2ms / 2ms）** ⇒ 慢帧的耗时**全部来自 `SendInput` 回注**，
  与滤波算法无关，直接验证了本节开头的判断。

**同批查清的环境因素（很可能是根因）**：本机 `tasklist` 可见
**腾讯电脑管家实时防护正在运行** —— `QQPCRTP.exe`（Session 0 服务态）、`QQPCTray.exe`、
4 个 `QQPCExternal.exe`，另有 Windows Defender `MsMpEng.exe`。
即「关掉电脑管家」只关了托盘界面，**实时防护服务并没退出**。这同时解释了
观察到的两件怪事：

- 注入的鼠标事件会被安全软件的输入过滤 / 节流检查 ⇒ 与 306~316ms 的偶发阻塞吻合
  （这也是同类「按键精灵 / 轨迹平滑」工具最常见的性能干扰源）；
- 守护进程以 Administrator 权限 `taskkill /F` 报「成功」但进程仍在、`Stop-Process` 静默失败
  —— 典型的安全软件自保护行为。

⇒ **B7 的前置条件**：分别在有 / 无实时防护下各画三笔长套索，比较 `worstOverCbMs` 的量级，
即可判定 300ms 是安全软件所致，还是系统输入栈固有。

// HotkeyBridge.ts —— 连接状态与平滑连接状态被绑成同一件事

  UXP 侧开两条 WS，平滑状态只由平滑那条连接决定。代码已经是双子系统对称结构，改动可控。
- **路 B**：保持单进程，但把「停止服务」重新定义为「卸键盘钩子、保留进程」，
  「卸载」也只在移除热键自启/配置后保留平滑宿主。改动最小，但「卸载」不再等于「程序消失」，
  语义上与用户预期有落差。

### 11.4 ② 数位板：为什么鼠标钩子对它无效

低层鼠标钩子（`WH_MOUSE_LL`）能看到的只有 **Windows 鼠标消息**。
数位板驱动有两种工作模式：

- **鼠标模式 / Windows Ink**：笔输入经 Windows 合成鼠标消息 ⇒ 钩子能看到 ⇒ 现在的方案有效；
- **Wintab 模式**：驱动直接把报文交给客户端，**Photoshop 走的是 Wintab 报文而不是
  `WM_MOUSEMOVE`**。我们的钩子吞掉并回注鼠标消息，光标是动了，但 PS 根本不吃这条数据流
  ⇒ 画出来的线仍是笔的原始轨迹 ⇒ 表现为「完全没效果」。

**这不是 bug，是拦截层选错了。** 而 Wintab 没有系统级钩子 API，要拦它只有三个方向：
注入 Photoshop 钩 `Wintab32`（高侵入、易被杀软针对、PS 升级即可能失效）、
写虚拟 HID/驱动（内核态、需签名）、或**让数位板走鼠标模式**（零代码，但失去压感——套索不需要压感）。

**判定方法（30 秒，零代码）**：`node analysis/ws-tablet-probe.cjs`，按提示先用鼠标划、
再用笔划，看 `callbacks` 增量。笔段增量为 0 ⇒ 通路确认绕过鼠标。

### 11.5 ②b 算法层：为什么「有延迟却不平滑」

`LassoMouseSmoother.Step()`（标准模式）当前是三件事叠加，其中两件在削弱抖动抑制效果：

```csharp
double k = Math.Pow(0.18, Clamp01(s.Strength / 100.0));   // 强度 40 ⇒ k ≈ 0.50
if (s.SpeedAdaptive) { double boost = Math.Min(1.0, _speed / 1.2) * 0.5; k += (1.0 - k) * boost; }
if (corner) k = Math.Max(k, 0.75);                        // ← 拐角守卫
_ox += distX * k;
```

- **拐角守卫是主要嫌疑**：`cornerAngle` 默认 45°，而慢速手抖时相邻两帧的方向夹角
  经常超过 45° ⇒ `k` 被抬到 0.75 ⇒ **平滑几乎被关掉**，只剩下一阶低通带来的滞后。
  这正是「有延迟、却没变平滑」的观感来源。
- **速度适应方向相反**：它为了减少甩笔滞后而**在快速移动时减弱平滑**，而那恰恰是抖动最明显的时候。
- **停笔不收敛**：`Step()` 只在有鼠标事件时被调用，手一停就再没有事件 ⇒ 残余滞后要等到
  `WM_LBUTTONUP` 那一次回注才被抹平（表现为末段被「拽直」）。

收口方向（待确认后与 ① 一起进同一批构建）：给拐角守卫加**位移门限**（抖动的段长通常 <3px，
不参与判定）、加**噪声死区**（位移低于阈值不推进输出）、把速度适应的增强门槛提高到真正的快速段、
并在暂停后由看护线程补一次收敛回注。`SendInput` 是否被指针加速影响「拖很长画一小段」，
也在同一批里用「注入位移累计 vs 原始位移累计」对拍坐实。

### 12.2 ② 数位板通路：定案 = PS 走 Wintab，注入是唯一可行路径

不再依赖推测，直接枚举 Photoshop 进程已加载模块并扫描其字符串表：

```
Photoshop.exe            WinTab32.dll ×1, WTPacket, WTPacketsGet, WTOpen, WTInfo
MouseHookPro64.8li       WTPacket, WTPacketsGet, WTDataGet, WTOpen, WTInfo
Wacom_Tablet.dll         （真正的实现体：WTPacket ×17、WTDataGet ×9、WTInfo ×122）
WinTab32.dll             （转发壳，含 "Wacom_Tablet.dll" 字符串）
```

- `C:\WINDOWS\SYSTEM32\WinTab32.dll` 与 `Wacom_Tablet.dll` 都在 PS 地址空间里 ⇒ **PS 用 Wintab**。
- `Photoshop.exe` 自身含 `WinTab32.dll` 导入名 ⇒ **静态导入（IAT）**，而非 `GetProcAddress`。
- 另加载 `MouseHookPro64.8li`（Adobe 自带的笔/鼠标输入插件），它也引用同一批 Wintab API
  ⇒ **光钩某一处 IAT 不够**：实现上应当钩 `WinTab32.dll` / `Wacom_Tablet.dll` 的**函数本体**
  （inline hook），这样无论调用方是 IAT 还是 `GetProcAddress` 都会经过我们。
- 本机 `HKLM\SOFTWARE\Wintab` 与 `WOW6432Node\Wintab` 均不存在；`WinTab32.dll` 也不在
  KnownDLLs 里 ⇒ 理论上「把代理 DLL 放进 PS 安装目录」也能生效，但那属于 DLL 种植，
  且会被 PS 升级覆盖，**不作为主方案**。

**待办**：`analysis/ws-tablet-probe.cjs` 的笔段结果需真机跑一次（需用手握笔），
用于把「callbacks 增量为 0」这一条从推断升级为实测。

### 12.3 ②b 真凶：`SendInput` 被放在低层钩子回调里（实测 300ms 级停顿）

真机日志的每一笔拖拽都是同一个形状：

```
本次拖拽原始 191 点 / 注入 165 点（最差一帧 304ms，其中回注占 304ms）
本次拖拽原始 519 点 / 注入 306 点（最差一帧 305ms，其中回注占 305ms）
本次拖拽原始 244 点 / 注入 215 点（最差一帧 312ms，其中回注占 312ms）
...  304 / 305 / 309 / 310 / 312 / 314 / 315 —— 全部落在 300ms 附近
```

- 这个 300ms 不是巧合，正是 Windows 的 `LowLevelHooksTimeout` **默认值**。
  在 `WH_MOUSE_LL` 回调里**同步**调用 `SendInput`，注入事件要等本回调返回才能入队，
  而系统又在等回调返回 ⇒ 卡到超时才解开。**每笔拖拽都可能冻结整个输入队列数百毫秒。**
- 这也解释了「熔断形同虚设」：预算 120ms × 连续 2 次，而每笔通常只出现**一帧**超预算，
  连续计数总被清零 ⇒ 熔断**从未触发**（`strikes` 回零）。
- 观感即用户报的：「鼠标拖了很长、画布上只画了一小段，而且抖」。

**同类隐患（真机复现）**：这种阻塞**不可中断**。一次卡住之后，进程即便收到退出指令也
永远停不下来 —— 实测两个守护进程都停在了「`HasExited=True` 但对象不回收、端口一直被占、
`TerminateProcess` 返回 ACCESS_DENIED(5)」的状态。第一个由真实拖拽造成，第二个由自检造成。

**收口（已实施）**：把回注整体搬出钩子回调。

| 位置 | 旧 | 新 |
| --- | --- | --- |
| 钩子回调 | 同步 `SendInput`（可卡 300ms） | 只写 `volatile` 目标 + 置事件，微秒级返回 |
| 回注 | 回调内 | 独立线程 `InjectThreadProc`（AboveNormal） |
| 注入方式 | `MOUSEEVENTF_MOVE`（相对） | `MOUSEEVENTF_ABSOLUTE \| VIRTUALDESK`（绝对） |
| 抽稀 | 逐帧注入 | 天然合并：连续多帧只补最新位置 |
| 熔断预算 | 120ms / 连续 2 次 | **50ms / 连续 3 次**（回调已无重活，重新具备早发现能力） |

**绝对坐标为什么也一起换**：本机 `SPI_GETMOUSE = [6,10,1]` ⇒「提高指针精确度」**开启**。
相对注入同样会被加速曲线整形，而平滑后的位移更小、更均匀，落在曲线另一段 ⇒ 位移不守恒；
又因为注入是闭环的（每帧先 `GetCursorPos` 再取差值），一次过冲会在下一帧变成反向修正
⇒ 光标在目标附近来回抖。绝对坐标不经加速，位移严格等于请求值，两个问题一起消失。

**新增安全网**：`_injectBusySince`。钩子每帧检查回注线程是否已超过 400ms 未从 `SendInput`
返回；一旦超时立刻**熔断 + 放行原始事件**，把光标交还系统 —— 宁可平滑失效，也绝不让光标
被我们冻住。这类熔断**不自动复位**（`SendInput` 卡住不会自己回来，自动复位只会再冻一次）。

**新增自检命令**：`{"type":"pointerTest"}` —— 在同一台机器上对拍
`相对 / 绝对 / SetCursorPos(上界对照)` 的位移守恒率，并回报 `SPI_GETMOUSE`。
⚠️ 该命令本身会调用 `SendInput`；若系统输入队列已被别的进程占住，它会让**本进程也卡住**，
所以只在确认输入通路健康时使用。

### 12.4 工具链定案：便携 zig（阻塞项已解除）

### 12.5 面板整理：「启用平滑」与「平滑服务」二合一

原先平滑分区是**三行**：`启用平滑 [开关]` / `状态 [文字]` / `平滑服务 [开关]`。
问题在于服务本是平滑的**前提**，用户却要先开服务再开平滑；服务没开时点平滑开关毫无反应，
两行谁是谁的前提并不直观。现合并为**一条状态条**，形态与「笔刷热键」分区的服务条同款
（指示点 + 状态文案 + 右侧开关）：

| 档 | 指示点 / 外框 | 触发条件 |
| --- | --- | --- |
| 灰 | `indicator-disabled` / `notify-bar-disabled` | 总开关关闭 |
| 橙 | `indicator-warn` / `notify-bar-warn` | 服务没起来 / 协议过旧（**需要用户处置**） |
| 红 | `indicator-fail` / `notify-bar-fail` | 钩子被拦截 / 熔断 |
| 绿 | `indicator-ok` / `notify-bar-ok` | 已就绪 / 绘制中 |
| 中性 | `indicator-disabled` / 无修饰 | 待命（当前不是套索工具）—— **不是故障，不染警告色** |

### 14.3 ⛔ P1 踩到的三个坑（均已固化进工具）

1. **`GetExitCodeThread` 取远程 `LoadLibraryW` 的返回值会截断**。

   ⇒ 判定「注入成功」改用**证据文件**（更硬的判据）；卸载改用 `EnumProcessModulesEx`
   按名字查真实基址（`inject.py --eject <pid> <dll_name>`）。
2. **十六进制地址不要手算**。第一次把十进制的模块基址换算成 hex 时算错了，
   白白多花一轮排查。（与「Unix 时间戳必须用命令取」同一条戒律。）
3. **`kernel32.dll` 是共享映像** ⇒ 本进程 `GetProcAddress("LoadLibraryW")` 得到的地址
   在目标进程里同样有效，**不需要**远程解析。这是该技术的标准前提，记下来免得后人怀疑。

## 15. 第七轮：P2 落地 —— Wintab 内联钩子实测（v7，2026-10-12）

### 15.1 先侦察，再动手：把「要改的那几个字节」钉死

改代码段一旦写错就是 PS 当场崩，所以不盲写。先用**零风险**手段把事实拿全
（`analysis/_tools/spike/recon_wintab.py` + `recon_thunk.py`）：

| 要回答的问题 | 手段 | 结果 |
| --- | --- | --- |
| `WinTab32` 的导出是转发壳还是实现体？ | 比对 `WinTab32!WTPacket` 与 `Wacom_Tablet!WTPacket` 的地址 | **不同地址**，两份各自有实现体（各 ~3MB `.text`） |
| 要改的那几个字节长什么样？ | 本进程 `LoadLibrary` 后按导出名取址读 32 字节 | **每个导出入口本体就是一条 5 字节 `E9 rel32`** `WTPacket: E9 D8 39 0E 00` |
| 是出厂代码还是已被别人 hook？ | 与**磁盘文件同 RVA** 逐字节对照 | 磁盘 == 内存 ⇒ **出厂代码**，无人 hook（Wacom 自带 `MouseHookPro64.8li` 也没动它） |
| `E9` 跳到哪？目标是什么形态？ | 沿链读一层 | `impl` 是标准 MSVC 序言 `40 53 55 56 57 48 83 EC 28` ⇒ **真实现体** |

### 15.2 ★ 手法定案：入口那 5 字节既是「唯一入口」又是「完整指令」

这两条合在一起，把 inline hook 的复杂度与风险同时降到接近零：

| 事实 | 推论 |
| --- | --- |
| 入口 = **一条独立完整的 5 字节 `jmp`** | 原位覆盖**天然指令对齐** ⇒ ①**不需要长度解码器**；②**不需要搬迁任何指令** |
| `E9` 的目标就是真实现体 | 直接 `call impl` 与原语义**逐位等价** ⇒ **不需要跳板**（省掉最容易出错的一步） |
| 入口是**所有调用方**的必经之路 | 静态 IAT（`Photoshop.exe`）、插件（`MouseHookPro64.8li`）、`GetProcAddress` 全都经过它 ⇒ 只钩这一处就够 |

剩下的唯一约束是「`E9 rel32` 射程 ±2GB」，而注入的模块离目标可能很远
（实测 PS 内 `WinTab32` @`0x7FFF767C0000` 与 `Wacom_Tablet` @`0x7FF8065F0000` 相距 ~29GB）
⇒ 在目标**附近**分配一页放转发桩：

```
entry:  E9 rel32 ──► relay: 48 B8 <&detour> FF E0   (mov rax,imm64; jmp rax)
                            │
                 detour: 计数 → call impl → 透传返回值
```

### 15.3 实现（`analysis/_tools/spike/wtprobe.c`）

- **两条安全闸门**（不满足就跳过并记录原因，绝不盲改）：
  ① `entry[0] == 0xE9`；② `impl` 必须落在同一映像内。
- **改写期间冻结其它线程**：写 5 字节不是原子操作，若有线程正好取指到这条 `jmp`，
  可能读到「新 `E9` + 旧 rel32」的撕裂组合 ⇒ 跳野地址。PS 有 **151** 个线程、Wintab 轮询 50+Hz，
  窗口虽小但非零 ⇒ 按最保守做法挂起 → 改 → 恢复（与 MS Detours 同思路）。
  ⛔ 冻结窗口内**只放不需要 loader lock 的调用**（`VirtualProtect`/`memcpy`/`FlushInstructionCache`）；
  `LoadLibrary`/`GetProcAddress` 留在窗口外 ⇒ 安装拆成 prepare / commit 两趟。
- **自检导出** `wtprobe_selftest()`：**从入口地址**调用被钩函数（必然穿过完整链路），
  用最保守参数（句柄 0 / 出参 NULL）—— 把「钩子装上了」与「调用能正确穿过链路」**分开证明**。
- **卸载** `wtprobe_unhook()`：先停线程、再还原字节。⛔ 直接 `FreeLibrary` 必崩
  （入口里留着指向本模块的 `jmp`）。`inject.py --eject` 自动按这个顺序做。
- 只计数，**不解引用任何出参**（原型记错就是野指针崩溃，P2 不需要它）。
  强证据 = `WTPacketsGet` 的**返回值就是「取到几包」**，`WTPacket` 的 `wSerial` 是包序号。

## 16. 第八轮：P3 最小可用版 —— 笔输入层平滑落地（v8，2026-10-12）

目标：把 P2 的「计数探针」换成**真正改写坐标**，并在面板上给出一个开关。
判定标准（最小可用）：**开关打开时笔迹变平滑、关闭即恢复**，且标定失败时**只读不写**。

### 16.1 架构：为什么平滑不在守护进程里，而在一段注入 DLL 里

P2 已钉死一件事：笔的坐标**只在 PS 进程内**、且只经过 `Wintab32!WTPacketsGet` 一个咽喉。
守护进程在进程外，无论怎么做都拿不到那个缓冲区 ⇒ 唯一的着力点是**注入 PS 并就地改写**。

```
   [面板] --WS(18924)--> [SmoothDaemon] --命名共享内存--> [JWautofillWintabHook.dll @ PS 进程内]
                                                            └─ inline hook Wintab32!WTPacketsGet
```

- **配置下发走共享内存**（`Local\JWautofillWintabSmooth`，32 个 32 位槽）：detour 里读配置
  只是**普通内存读**，零系统调用。用它而不是管道/WS，是为了守住「detour 内零 I/O」。
- **强度 / 开关**由守护进程写槽位；**状态 / 标定结论 / 计数**由 DLL 回写，守护进程只读。
- **心跳防呆**：守护进程每秒把 `GetTickCount()` 写进槽位；DLL 侧发现 **3 秒**没更新就自动停手
  （否则守护进程被强杀后，共享内存不消失、`enabled` 永远停在 1，PS 会被一段「没人管」的平滑一直改着）。

### 16.2 安全设计：三道闸门

| 闸门 | 作用 | 失败时的行为 |
| --- | --- | --- |
| **标定**（改动前必须知道 X/Y 偏移） | `WTGetA` 读 `lcPktData` 掩码推算布局，再用「序号逐包 +1」验真实数据；另一条**盲扫**独立找同一对 (stride, offSerial)，两者必须一致 | 不一致 ⇒ `state=2`，**只 dump 原始字节、绝不改写**（写错偏移会污染 buttons，可能造出幽灵按键） |
| **线程冻结** | 5 字节 `E9` 不是原子写，撕裂会跳野地址；PS 有上百线程 ⇒ 挂起→改→恢复 | 线程数超过冻结表容量 ⇒ **放弃改写**（只冻一部分等于没冻） |
| **卸载** | 入口里留着指向本模块的 `E9` ⇒ **先还原字节再 `FreeLibrary`**，否则必崩 | 两条路径：共享内存 `CMD=2`（正常）或导出 `jwwh_unhook()`（排障） |

⛔ 本轮自查修掉的两处：

1. `try_calibrate()` 是**从 detour 里**调的，初稿直接走 `logf()` ⇒ `WriteFile + FlushFileBuffers`
   （全盘刷）跑在 **PS 取包线程**上，且 `log_write` 还会自旋抢日志锁。已改为**只往内存缓冲拼字符串**，
   由 worker 线程补写（`calib_logf` / `calib_publish`）。
2. 冻结表溢出标志 `g_overTent` 原来**只置位、无人消费** ⇒ 溢出后仍继续改写。已在 `do_install()` 里拦下。

### 16.3 算法：C 版单包低通（与守护进程 Mode 0 同源，但有两处刻意差异）

- `k = 1.0 - 0.85·(t/100)`（**线性**）——守护进程用 `0.18^(t/100)` 指数映射；此处为 MVP 阶段
  不引入 libm 的 `pow`。
- **不做 `MinSampleDist` 抽稀**——Wintab 的包必须**原样写回**，抽掉会打乱 PS 的时间轴。
- 保留了：速度低通、拐角守卫（夹角 ≥45° 时 `kk = max(kk, 0.75)`）、速度自适应、全局滞后上限、
  起笔锚定（复位帧输出点严格落回输入点）。
- 输出恒为「上一输出」与「本包输入」的凸组合，加上滞后上限只会朝输入移动 ⇒ **数学上有界，不会产生越界坐标**。

## 17. 第九轮：参数链路修复 + 拉绳 HUD（v9，2026-10-12）

> 触发：用户真机反馈「已平滑 47417 包（链路是通的），但测试各种参数组合**感知不明显**，
> 且不太理解半径 / 间距的含义；并要求像 PS 原生那样给拉绳模式加上具体的 HUD 拉绳表现。」

### 17.1 根因：不是算法不够强，是参数根本没接上

把 `面板 → WS(18924) → SmoothDaemon → 共享内存 → DLL` 逐字段核对，结论是**只有一个参数
真正接到了笔通路，而那个也接不通**：

| 面板参数 | 鼠标/套索通路 | 笔通路（P3 时） |
| --- | --- | --- |
| 平滑强度 | 实时下发 | 面板 `togglePenSmooth()` 只发 `{on}` ⇒ 恒为守护进程默认 **40**，用户改不到 |
| 半径（最大滞后） | 实时下发 | `_radiusPct` **全代码零写入点**，恒为 25（= 轴上界 0.25%） |
| 张力 / 追笔速度 | 实时下发 | DLL 里**没有模式分发**，选什么模式都走标准一阶低通 |
| 拐角保留 | 实时下发 | C 侧硬编码 45°（`CORNER_COS`） |
| 速度自适应 | 可开关 | `_flags` 零写入点，恒为 1 ⇒ 常开关不掉 |
| 采样间距 | 实时下发 | 刻意不做（Wintab 包必须原样写回，抽掉会打乱 PS 时间轴） |

**第二层根因（即使强度接通也不够看）**：笔实测 205Hz（3158 包 / 15.4s）。旧 C 版
`k = 1 − 0.85·t/100`，强度 40 ⇒ k=0.66；再叠加常开的速度自适应（`boost=0.208`）
⇒ k≈0.73。稳态滞后 `L = v·dt·(1−k)/k = 500px/s × 4.88ms × 0.37 ≈ 0.9 px`。
**亚像素 ⇒ 客观上不可能被感知**。同一数字在鼠标通路（125Hz、`k=0.18^t`）上是 2.4px。

⇒ 两条独立缺陷：① 链路断（除强度外全无效）；② 强度映射在 205Hz 下太弱。

### 17.2 修法一：整包参数下发

- WS 指令 `penSmooth` 从 `{on, strength?}` 扩为整包：`mode / strength / radius /
  tension / catchUp / cornerAngle / speedAdaptive / hud`，字段**全部可空**（缺 = 保持原值，
  不会被默认值冲掉 —— 面板的开关与调参走同一条指令）。
- 共享内存槽位表扩到 28 项（`I_MODE / I_TENSION / I_CATCHUP / I_CORNER / I_RADIUSPX /
  I_HUD / I_HUDCOLOR / I_PXPERAXIS`），并**删掉了已死的 `I_RADIUSPCT`**。
- ⛔ 这张表是 C 与 C# **两处手写**，错位不报错、只静默失效。两侧各加一道保险：
  C 侧编译期断言 `CFG_NLONGS >= CFG_I_PXPERAXIS+1`；C# 侧 `EnsureInit` 运行时越界抛错。
- 面板侧新增 `setPenSmooth(on, params)`（参数面属主，记住 `penOn`）；
  `sendParams` 里**笔平滑开着就同步推一份** —— 否则用户调参只影响套索，笔平滑永远停在旧值。
- DLL 侧 `smooth_packets` 实现**三种模式分发**，参数全部现读共享内存。

### 17.3 修法二：强度改按「时间常数」定义（跨采样率一致）

旧映射是「每帧跟随系数」，与采样率强耦合 —— 同一个数字在不同设备上含义不同，
这也是「参数难以理解」的根源。改为：

```
τ(强度) = 8ms · (0.18^(−t/100) − 1)      # 与鼠标通路 k=0.18^(t/100)@125Hz 的滞后严格等价
k = dt / (dt + τ)                        # 稳态滞后 = v·τ，与采样率解耦
```

同样强度 40：笔通路滞后从 **0.9px → 3.65px**（≈4 倍），且两条通路手感一致。
`0.18^` 的指数用 Maclaurin 12 项自己算（`exp_series`），`cos(拐角)` 同样自己算
（`cos_deg_series`，45° 误差 5e-6）—— **不引 libm**，避免多拉一个 crt-math 依赖。

半径单位从「轴上界万分之一」改为**屏幕像素**（与面板 1–40px 同单位），经 `pxPerAxis`
换算；拐角守卫**只对标准模式生效**（拉绳/追笔的跟随机制本身不磨圆，加削弱反而破坏手感）。

### 17.4 轴→像素比：不猜 Wintab 语义，用真实光标标定

Wintab 的 PACKET 到底在输入空间还是输出空间，文档语焉不详。本实现不赌：
屏幕上看到的光标**就是**平滑后的输出点，于是

```
pxPerAxis = |Δ光标| / |Δ输出轴|
```

一次除法 + 0.85/0.15 低通即可，天然跟随缩放 / 多屏 / 映射变化。标定值经
`CFG_I_PXPERAXIS`（×1000）上报，真机一眼可验：
`1.0` ⇒ 包坐标本身就是屏幕像素；`0.0586` ⇒ 数位板逻辑单位（1920/32767）。

### 17.5 拉绳 HUD：形态、边界与风险最小化

**为什么必须 overlay**：UXP 没有在 PS 画布上绘制的 API（这正是当初必须注入的原因 ——
连指针都拿不到）；PS 原生的「画笔绳线」由**它自己**的画笔平滑绘制，而我们在 Wintab 层
改写坐标、PS 的平滑状态是关的 ⇒ 它不会替我们画。

**⛔ 但 detour 铁律没有被违背**，这是本实现的关键约束：

- detour 只多写 5 个普通内存字段（`g_snRawX/g_snRawY/g_snOutX/g_snOutY/g_snMs`），
  **零系统调用**，205Hz 取包路径不变；
- 建窗 / 标定 / 绘制 / 消息循环全在**独立渲染线程**，与取包线程无交集。

真正被放松的只有「DLL 不碰 UI」这一条。

**风险最小化**（overlay 是安全软件的典型启发式特征，能收的都收）：

| 措施 | 理由 |
| --- | --- |
| 窗口仅 192×192 且**跟随光标** | 大面积全屏顶层透明窗才是 overlay 软件的典型特征 |
| 空闲 250ms（抬笔）即隐藏 | 不长期驻留屏幕 |
| `WS_EX_NOACTIVATE` + `WS_EX_TRANSPARENT` + `WM_NCHITTEST→HTTRANSPARENT` | 不抢焦点、不吃鼠标事件 |
| `WS_EX_TOOLWINDOW` | 不进任务栏、不进 Alt-Tab |
| `CFG_I_HUD = 0` 时窗口根本不出现 | 面板提供「拉绳提示」开关 |

**卸载顺序**：窗口过程在本模块内 ⇒ 必须先 join 渲染线程再 `FreeLibrary`，
否则下一条消息就会跳进已卸载的代码。`hud_stop()` 由 worker 退出路径与 `jwwh_unhook`
双重保障（幂等），等待上限 3s。

**画什么**：品红线（光标 ↔ 原始笔尖，PS 画笔绳线同色）+ 半径圈（直观显示「最大滞后」）
+ 原始笔尖点。位域 `CFG_I_HUD`：bit0=绳 bit1=半径圆 bit2=原始点。

### 17.6 本轮新增依赖与真机观察点

- DLL 依赖从 `KERNEL32 + UCRT` 增至 **`+ GDI32 + USER32`**（HUD 建窗自绘必需）。
  这是本轮的**主要杀软风险增量**：注入进程 + 建顶层窗 + 读光标，三者叠加正是
  overlay 类软件的画像。真机需重点观察。
- 若 leash 长度或位置不对 ⇒ 看 `smoothState.pen` 里新增的 `pxPerAxis` 上报值，
  以及日志里 `# [status]` 是否出现（渲染线程本身不写日志，标定结果只进共享内存）。
- 若窗口完全不出来：① 确认 `showLeash` 开着；② 确认正在**用笔画**（鼠标不走 Wintab，
  没有包 ⇒ `g_snMs` 不更新 ⇒ 250ms 后自动隐藏）；③ 确认标定已通过
  （`state === 1`；标定失败时平滑本身也没生效）。
