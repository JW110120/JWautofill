# 混合器 + 通道混合器：逐笔尖浮雕（设计稿）

> 2026-10-22 · 目标 PS 27.11，向下兼容 2022
> 前置结论：**你的路线是对的**，但颜色那一步要改算法 —— 常量是加法，浮雕要的是乘法。

---

## 0. 先用一句话说清

Krita 的印章笔是「**一张灰度图 × 一支颜色**」：灰度图决定"哪里亮哪里暗、哪里透哪里实"，
颜色只决定"这支笔是什么色"。两者相乘，所以改颜色不会破坏明暗。

PS 的混合器笔刷能做到同样的事 —— 它把**一整块画布区域**吸进储层，一笔下去能带出多种亮度。
我们只要在"吸"之前，把那张灰度图**乘成目标颜色**，剩下的就交给混合器。
而"乘"这个动作，唯一能在 PS 里精确做到的入口就是 **通道混合器**。

| 明暗不改形状 | 通道混合器只动 RGB，不动 alpha | ✅ 数学上成立 |

## 2. 资产：一张 400×400 的"图案母版"

`dist/brushes/impasto-detail/MIX-impasto-detail.png`（本次已生成）

```
400 × 400 RGBA
  ├─ 笔尖 178×400 居中，左右各留 111px
  ├─ A（透明度）= 覆盖度 —— 白底已转透明，四角 alpha 全 0
  └─ R=G=B     = 立体亮度 —— 之后由通道混合器上色
```

生成方式：`python scripts/build_mixer_pattern.py --id impasto-detail`

三条硬要求（都来自你的实测，别改）：

1. **图案必须是 RGB 模式** —— 灰度文档根本没有「通道混合器」这个菜单项。
2. **白底必须转透明** —— 混合器把整块 400×400 都当真，白底会在画布上拖出一个白方块。
3. **采样点必须是画布正中** —— 笔刷是 400×400 方形，吸在 (200,200) 才能让图案与笔刷严丝合缝。

### 2.1 ⛔ alpha 必须是"覆盖度"，不能是"亮度"

第一次生成时我直接把笔尖亮度当透明度，结果上色后叠在深底上是一坨**暗红泥**：

> 原因：沟槽处亮度本来就低 → alpha 只有 0.4 → 颜色又被乘了一次暗 →
> 半透明 + 暗色 = 糊掉了。**颜料是不透明的**，有料的地方 alpha 就该是 1。

所以脚本里分了两条曲线：

| 通道 | 来源 | 曲线 | 作用 |
|---|---|---|---|
| A | 同一个亮度 | `cover_mask(floor=0.04, ceil=0.30)` 再 `gamma 0.85` | 0.30 以上一律全实 → 只有笔丝外缘是半透明 |
| RGB | 同一个亮度 | `gamma 0.6` | 中位亮度从 85 抬到 ~135，配上高光 255，才有"厚度" |

可调参数：`--cover-floor / --cover-ceil / --rgb-gamma / --alpha-gamma / --side`。

**判据**（生成后自检）：全覆盖像素（alpha=255）应占整块方形的 **25%~40%**，
全覆盖区亮度中位应在 **110~160**。低于这个区间画出来就发黑。

预览（左：深底 / 右：浅底）：

- 未上色：`docs/assets/mix-pattern-raw-preview-2026-10-22.png`
- 模拟乘以 RGB(197,42,42)：`docs/assets/mix-pattern-tinted-preview-2026-10-22.png`
  ← 这张就是"§4 系数法"在像素层面的效果：沟槽暗红、棱线亮红，层次完整。

> ⚠️ 缩放提醒：笔刷调小，整块图案跟着缩，笔丝会被重采样糊掉。
> 建议把可用尺寸下限定在 **≥ 200px**；再小就换一套低分辨率图案（同一脚本 `--side 200`）。

## 3. 命令链

### 3.1 首次安装（一支笔一辈子一次）

```
1. 新建文档 400×400，RGB/8
2. 置入 MIX-<id>.png          （保持透明）
3. 锁定透明像素
4. emboss(135°, 3, 100)       ← 把浮雕烘焙进图案
5. fade(60%, overlay)         ← 压回原图，只加光影
6. 定义图案 / 保持图层常驻（见 §7）
7. 切混合器笔刷 → 400px 方形 → 潮湿0/混合0/载入100/流量100
8. 在画布正中吸一下
```

### 3.2 每次前景色变更（要"实时"的就是这一步）

```
1. 复制母版图层 → 临时层
2. channelMixer(系数 = 前景色)      ← 只有这一条命令
3. 在最上层重采样一次（§7 的未知项）
4. 删掉临时层
```

**为什么只重发一条命令**：浮雕已经烘焙在母版里，换色只改 RGB。
反复 emboss 会把笔丝越磨越平（每次叠加 60% 都会糊一层）。

## 4. 颜色算法（核心）

### 4.1 通道混合器的数学

每个输出通道是一条线性式：

```
out_ch = ( r% · src_R + g% · src_G + b% · src_B ) / 100 + constant / 100
```

我们的图案层是**灰度**（R=G=B=v），所以：

```
out_ch = v · (r% + g% + b%) / 100 + constant / 100
         └────── 乘法部分 ──────┘   └─ 加法部分 ─┘
```

要让 `out_ch = v · F_ch`（F = 前景色，0..1）：

| 想要 | 就设 |
|---|---|
| 乘法（跟亮度成正比） | **系数** = `F_ch × 100`，常量 = 0 |
| 加法（整体平移） | 常量 = `(F_ch − 0.5) × 100` |

### 4.2 为什么"只调常量"会毁掉浮雕

以 RGB(197, 42, 42) 为例，常量取 `+54 / −64 / −67`（你给的样本档位），
在 6 个亮度上分别算出来：

| 笔尖亮度 v | 系数法（out = v·F） | 常量法（out = v + c） |
|---|---|---|
| 0.0（最暗的沟） | 0, 0, 0 | **138, 0, 0** ← 纯黑被染红了 |
| 0.2 | 39, 8, 8 | 189, 0, 0 |
| 0.375（实测沟槽值） | 74, 16, 16 | 233, 0, 0 |
| 0.5 | 99, 21, 21 | **255, 0, 0** ← 开始削顶 |
| 0.75 | 148, 32, 32 | **255, 28, 20** ← 削顶 |
| 1.0（最亮的高光） | 197, 42, 42 | **255, 92, 84** ← 削顶 |

看最后一列的 **255**：从 v=0.5 开始红通道就顶死了。
意思是 **画面上一半的明暗层次被压成同一个红** —— 笔丝、沟槽、高光全糊成一片，
浮雕感正是从这些层次里来的。所以肉眼会看到"一笔死红"。

用生活化的话：系数是**音量推子**（按比例放大），常量是**垫底噪声**（整体抬高）。
用垫底把声音抬到爆音，听着就只剩一片糊响 —— 层次没了。

### 4.3 落地实现

`src/brushstudio/mixerColor.ts`

```ts
channelMixerFor({ r: 197, g: 42, b: 42 })
// → { _obj:'channelMixer', red:{ red:77.3, constant:0 },
//                          grain:{ grain:16.5, constant:0 },
//                          blue:{ blue:16.5, constant:0 } }
```

三个坑（都写进注释了）：

1. **绿通道输出在 AM 里叫 `grain`**（charID `Grn`），不是 `green`。写错就静默不生效。
2. **三个源系数必须显式写 0**，不能省。默认值是"同通道 100%"，省略会变成
   `v × (1 + 我们的系数)`，越调越亮。
3. 常量默认 **0**。只有在"沟槽死黑、看着太干"时才给 **3~12** 抬一点黑位。

`assertTintMath()` 会拿 6 个采样点断言"系数法 = Krita 乘法"，容差 1/255 —— 算法被改坏会立刻报出来。

## 5. 浮雕：emboss + 渐隐

```
{ _obj:'emboss', angle:135, height:3, amount:100 }
{ _obj:'fade', opacity:{percentUnit:60}, mode:{blendMode:'overlay'} }
```

| 项 | 取值 | 说明 |
|---|---|---|
| angle | 135° | 光从左上来（与 PS 图层样式的默认一致，看着自然）。用户换光向就改这个 |
| height | 1–5 | 笔丝粗细的视觉宽度。400px 笔尖上 3 比较像刻痕，>5 会变成"塑料浮雕" |
| amount | 100 | 浮雕强度 |
| fade 不透明度 | 40–70% | **这是"像不像"的旋钮**。太高会像贴纸，太低看不见 |
| fade 模式 | overlay | 只加光影、不改底色；换 `softLight` 更柔 |

⛔ 两个必须：**先锁透明像素再 emboss**（否则方角被填灰，画出白框）；
**fade 必须紧跟 emboss**（它只作用于上一条滤镜，中间插任何命令都会失效）。

## 6. 性能预算

| 步骤 | 频率 | 估计 |
|---|---|---|
| 生成图案（python/UXP 内绘制） | 装笔一次 | 一次性 |
| emboss + fade | 装笔一次 | ~30ms |
| 通道混合器 | **每次换前景色** | ~10ms |
| 重采样 | 每次换前景色 | 待测（§7） |
| 落笔绘制 | 每一笔 | **PS 原生，零插件开销** |

关键点：**这笔刷的性能瓶颈不在插件**。混合器是 PS 内置引擎，
我们只在"用户换颜色"时做一次矩阵运算。这一条比"回放第二遍"（每笔要重跑一遍绘制）好一个量级。

## 7. 未知项（E2 已定案，E1 结论：结局②）

### E2. ✅ 已定案（2026-10-22 用户实测）

**吸一次会同时吸进多个颜色** ⇒ 储层是**一张彩色位图**，不是"一个颜色"。
H1 成立，H2 排除。所以"一笔多亮度、多颜色"这条根是稳的，**不用重估方案**。

附带确认的机制（Adobe 官方文档 + 用户实测一致）：

| 混合器的两个色管 | 内容 | 谁填的 |
|---|---|---|
| **reservoir（储槽）** | 笔上储备的颜料 | 「载入画笔」= **前景色**；Alt+点画布 = **从画布采样像素** |
| **pickup（挑色管）** | 从画布刮到的颜料 | 落笔时自动 |

⇒ 这解释了你观察到的现象：**改前景色，储层就被"载入画笔"重置成纯前景色**，
图案因此被抹掉。要"实时跟随前景色"，就必须每次换色后**重新把储层装一遍**。

### E1. 储层能不能脚本化？★唯一剩下的阻塞

**做法 = 插件内探针**（不需要装 ScriptingListener）：

`src/brushstudio/psMixer.ts` 里的 `probeMixer()`，面板底部署名行的「混合器探针」入口触发。
它只发 `get`，把混合器工具的完整 `currentToolOptions` 落盘到 `brushstate/_mixer.json`。
配合「监听采样」（`listenSampling()`）抓 PS 在 Alt+点画布时派发的 AM 通知。

**判读前先看指纹字段**：混合器的 cto 一定有 `wetness` / `dryness` / `reservoirState` / `autoFill`；
普通画笔没有。⛔ 别用 `get currentTool` 判工具身份 —— PS 27 上它必报 **-25920**，
`toolName` 恒 null，会把"读到了完整状态"误报成"未知"（14:40 就踩了这个）。

---

### E1 结论（2026-10-22 14:53 第二次真机，250×250 方形混合器）

| 读到了 | 读不到 |
|---|---|
| `reservoirState=2`、`reservoirImageMode=3`、`reservoirCols=361`、`reservoirRows=362`、`reservoirChannelNumber=4` | `reservoirChannels` = `{}`、`reservoirSampleData` = `{}`；单独 `get` 这两条都报 **-25920** |

⇒ **结局② 定案：元数据可读、像素取不到。** 我们**写不进储层**，也不能把像素存盘回灌。

> 尺寸 `361×362`（笔刷 250）说明 PS 内部按画布/笔刷关系降采样，不是笔刷边长 ——
> 这也顺带证明了这一族字段描述的是**储层位图本身**，不是画笔。

### ⛔⛔ 撤回一个错误结论：`autoFill` 不是真凶（用户实测推翻）

14:40 我据 `autoFill=true` 推断"每笔都用前景色重灌储槽"。**这个推断是错的**：

> 用户原话：「真机实测下这个开关状态不会影响我之前的结论：
> 用户修改前景色 ➡ 储槽的内容变成该前景色。」

即 **`autoFill=false` 时，改前景色照样把储槽顶成纯色**。这是 PS 的**必然行为**
（内部就是 `FillReservoirWithForegroundColorAndInitializeWells`，二进制里能查到这个名字），
不是某个开关的副作用 ⇒ 不要再往开关方向找。

### ⇒ 因果链定稿

```
用户改前景色
   └─ PS 自动把储槽灌成该前景色（无视 autoFill）
        └─ 我们吸好的图案被顶掉
             └─ 必须把"新颜色 × 亮度"的图案重新注入储槽
                  └─ 注入 = 在画布上 Alt+点一下（采样）
                       └─ 这一步能不能脚本触发 = 唯一的阻塞 ★
```

**换色后必须重注入**，这是绕不过去的。要讨论的只剩"注入的代价是多少"。

### E1 第二问：采样能不能脚本触发（三条候选路）

| 路 | 做法 | 代价 | 状态 |
|---|---|---|---|
| **A 派发 AM 事件** | 拿到"采样储槽"那条 AM 命令名，直接 `batchPlay` | 零感知、真·实时 | **待验**：面板新增「监听采样」入口，用户手动 Alt+点一次，看 PS 派发什么通知 |
| **B 模拟输入** | native 宿主（`JWautofillHost`）发 `SendInput` Alt+左键 | 要处理坐标/前台/时序，且要开承载图案的临时文档 | 技术可行，工程量大 |
| **C 半自动** | 插件自动把"已上色图案"准备好并对齐，提示用户点一下 | 用户手上多一个动作（约 2 秒） | 保底可用 |

> 若 A 成功 ⇒ 换色 ≈ 一次 batchPlay，落笔期间零开销，体验接近 Krita。
> 若 A 失败 ⇒ 走 C（先可用），B 作为后续优化。

### 顺带：图案着色必须在 PS 里完成

注入储层的图案**必须是彩色**（储层是彩色位图）。而"亮度 × 前景色"这两个因子
一个是灰度图、一个是前景色 —— 合成只能在像素层做。两条路：

1. **PS 内合成**：临时文档 → 置入灰度图案 → 加「通道混合器」调整图层（系数=前景色，§4 的算法）
   → 拼合 → 得到彩色图案 → 采样。全程 `batchPlay` 可控。
2. **UXP 内合成**：读图案像素 → 逐像素乘 → 写回/落盘。省掉 PS 文档，但要走 `imaging` 的像素 API。

两条都可行，选 1（复用用户已给的通道混合器 API，且不依赖 UXP canvas 支持的完整性）。

## 8. 红线

1. ⛔ **不要用"只有几何/只有常量"的描述符去改画笔或颜色** —— 参考 0x0128 起那一串返工。
2. ⛔ **图案层永远保留一份未上色的母版**。通道混合器是"乘"不是"设"，反复施加会累积失真。
3. ⛔ **不动 alpha**。换色只走 RGB，形状靠 alpha —— 这是"改色不改形"的唯一保证。
4. ⛔ **不要为了"实时"去 hook 绘制**。这条路（回放第二遍）已被否，性能也不在一个量级。
5. ⛔ 所有新增的 batchPlay 命令，失败条数必须 = 0（见铁律 51：每条失败命令都会刷一条黄条）。
   探针阶段若必须试错，**必须放进一次性探测入口**，不许混进日常点击路径。

## 9. 与现有「特制笔刷」的关系

现在跑通的是 **普通画笔 + 缓存笔尖** 那条链（`psBrush.ts` / `psState.ts`），
它解决"笔尖怎么装上去、怎么不弹框"。

本条线是**并列的第二套笔**：混合器浮雕笔。两者共用：
- 同一份笔尖素材（`BRS-*` / `PAT-*` / `SHD-*`）
- 同一套"零失败命令"纪律
- 同一个诊断落盘（`brushstate/_last-run.json`）

互不覆盖：普通笔走 `defineBrush + cto 缓存`，浮雕笔走 `图案 + 混合器储层`。
⛔ **普通画笔那条链保留不动**（2026-10-22 用户明确：以后可能还有别的笔刷路线，
已跑通的不要为了新线让路而删改）。

  读不出来时退回程序化浮雕兜底，并在日志里写明（不静默降级）。
- 验货改成真的：Alt+点之后**先清空临时文档**，再补一枪普通点击 ——
  这样读到的像素只可能是"笔尖从储层吃到的颜色"。不清空的话读到的是我们自己铺的图案，永远"验上"。

## 12. 直径改不动的真实原因 + 降级策略（2026-10-22 16:10 真机）

### 现象

点「堆叠细描」直接红：

```
「堆叠细描」未完全生效：笔刷直径没改成 400（现在是 407）—— 吸进去的图案会错位。
两种写法都没把直径改成目标值
```

`_mixer-reload.json` 同时记到另一次运行「现在是 84」，两次 `set` 都写
`命令"设置"当前不可用`。

### 根因：`set` 的目标写法错了（不是权限问题）

| 写法 | 结果 |
|---|---|
| `{_ref:'property',_property:'currentToolOptions'}` + `application` | ❌ 命令"设置"当前不可用 |
| `{_ref:'wetBrushTool',_enum:'ordinal',_value:'targetEnum'}` | ❌ 同上 |
| `{_ref:'brush',_enum:'ordinal',_value:'targetEnum'}`（`to` = 整份 brush） | ✅ 工具无关 |
| `{_ref:'wetBrushTool'}`（**裸引用**） | 待验证 |
| `{_ref:'paintbrushTool'}`（**裸引用**，`psBrush` 已验证） | 兜底 |

⛔ 与铁律 51 是同一个坑：**PS 27 上 `_target` 用小写类名裸引用，带
`{_ref:'tool',_enum:'ordinal'}` 一律失败**。切工具如此，`set` 工具选项也如此。

### 407 是什么

PS 接受写入后可能按笔尖/文档**换算**直径（400 → 407，+1.75%）。
所以判据只能是**回读值**：

- `|回读 − 目标| ≤ 1` ⇒ 正常完成；
- 回读值**变了但不等于目标** ⇒ 也算完成（记 `PS 把 400 换算成 407`），
  并且**后续所有尺寸都用回读值**（铺 407×407 的方块去配 407 的笔刷，才叫严丝合缝）；
- 回读值完全没变 ⇒ 这条写法无效，换下一条。

### 降级（宁可先跑通，也不红）

严丝合缝的本质是「**采样的方块边长 == 笔刷直径**」，谁迁就谁不影响结果：

| 情况 | 做法 |
|---|---|
| 直径改成功 | 笔刷 = 图案长边（400），图案 1:1（细节最全，用户要的形态） |
| 直径改不动 | 笔刷保持现值，**图案等比缩到该尺寸**（`scalePat` 双线性） |
| 现值 < 64px | 直接报错并提示手动调大（缩过去会糊成一片，没有意义） |

⛔ 降级**不许静默**：`_mixer-reload.json` 的 `degraded` / `diaTried`、
步骤名「装储层（降级）」、状态条都会写明，否则下一轮又会把"糊了"当成 bug 查。

### 其它

- `setForm` 会话记忆：**只要 PS 接受过某条写法就记住**（哪怕数值没到位），
  避免每次点击都从第一条开始试、失败的那几条一遍遍刷黄条。
- `_mixer-reload.json` 新增 `diaTried[]`（每条写法 + 回读直径 + 笔尖名），
  `ok:false` 的条数 = PS 会画出来的黄条数。

## 13. 「储层还是纯色」的真根因：Alt 根本没按下去（2026-10-22 16:35）

### 证据链

面板报 `储层装上了但没验上（dab 32239px，亮度±0，色相 cos=1）` —— 三条一起指向"纯色"：
亮度标准差 0（整片同色）、色相 cosine 1（和前景色完全同向）、均色 `rgb(228,164,164)` 就是当前前景色。

`pi8li.log`：

```
16:16:46 [alt] 合成点击 alt=0 ... pt=(1920,1038)
16:16:47 [alt] 合成点击 alt=0 ... pt=(1920,1038)
```

**两枪都没有 Alt**。根因在原生 JSON 助手：

```c
json_bool(js, "alt", &alt);   /* 只认 true/false 两个字面量 */
```

面板发的是数字 `"alt":1` ⇒ 解析失败、`alt` 保持 0 ⇒ 第一枪变成普通落笔。
储层 `reservoirState` 1→1 不动、dab 就是纯前景色 —— 用户看到的"纯色"完全正确。

### 顺带修掉的第二处：`set` 直径会抹掉采样笔尖

`diaTried[0].tip` 回读是「（无采样笔尖）」：`set brush` 被接受、直径真变成 400，
但 `sampledData` 被抹掉 ⇒ 方形笔尖退化成计算圆笔。

⇒ 删掉整套 `setMixerDiameter`，改 `ensureSquareTip()`：
**`defineBrush` 一张 `side×side` 白方块**，笔尖直径天生等于边长、形状也是方的，全程不发 `set`。
笔尖留在画笔面板里（`悦绘·方400`），下次读到直径已经是 400 ⇒ 零命令复用。

### 判据升级：不画一笔也能知道装没装上

PS 只在储层**真有位图**时才序列化 `reservoirCols/Rows/ChannelNumber`：

| 储层状态 | 字段 |
|---|---|
| 纯色 / 空 | 只有 `reservoirState=1` |
| 装了图案 | `state=2` + `cols/rows/channelNumber` 齐（用户手动吸那次 361×362×4） |

所以「字段在不在」就是最准最快的判据。dab 退居第二层，只回答"画出来是不是多亮度"。

### 面板与原生之间加回执

`canvasClick` 原本是单向的（发出去就忘），所以"点了没效果"只能事后翻日志。
现在原生每枪回 `canvasClickResult{ok,why,alt,x,y}`，面板 `synthClick()` 等它并当场核对：
`alt!==1` 直接判 `click-noalt` 失败，不再有任何"发了就当成了"的空间。
