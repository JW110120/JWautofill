## lineSmoothProcessor 杂点修复（SDF 平滑第三轮）
- 用户反馈：平滑效果 OK，但线外出现游离像素杂点。
- 根因：Phase C 输出 `strokeAlpha = cov * bodyBlur * bodyScale`，其中 `bodyBlur` 是原始 alpha 的**无掩码高斯光晕**，而 SDF smoothstep `cov` 在边界外会泄漏一点正值 → 光晕 × 小 cov 在线外生成游离 alpha 杂点。

- 验证：
  - 合成杂点压力测试 test_specks_v18.mjs：撒 120 个线外杂点 → 残留 0；线保留 97.2%，线宽 20.58→20.06，AA 81.8%→85.7%。

## lineSmoothProcessor 游离杂点第三轮根因（本次，用户给出新线索）
- 现象（用户实测对比）：点击平滑后线条**整体轻微变细**，而**个别原线像素不受 SDF 影响仍停留在原位置**，看上去像变细线条的近外部有游离杂点。
- 根因（与上一轮「原杂点存活」不同）：SDF 由 `binaryOpen(lineMask,2)` 的 `lineMaskClean` 构建，原线被开运算削掉的边缘皮/小凸起/分支尖已**不在 SDF 内** → smoothstep cov≈0 → 输出 na==0；旧写回规则「na==0 且非 isSpeck → 保留原值」把这些原线像素**原样写回**，于是线条变细后它们在近外部残留。
  - 上一轮 `isSpeck` 只覆盖面积 < SPECK_MAX 的孤立小域，但本例残留像素属于**被 SDF 覆盖的大连通域**中「被推到线外」的部分，isSpeck 永远为 0 → 漏网。
- 修复（Phase A.5 + E.5 + 写回 na==0 分支重做）：
  1. Phase A.5 在 8 连通分量标注基础上记录每个分量的面积（lineCompSize），isSpeck 仍保留。
  2. 新增 **Phase E.5 分量级覆盖判定**：对每个原线连通域算覆盖率 cov=hit/cnt（hit=输出 na>0 的像素数）；cov ≥ COVER_MIN(0.25) → compCovered=1（该分量确实被 SDF 平滑，变细是正常结果）。
  3. 写回 na==0 分支重做：`na==0 && (isSpeck || compCovered[cid])` 才清除；并加守卫——仅当 8 邻域存在「输出空位(na<=0)」才视为外观残留清除，**被输出完全包围的（线条内部 1px 孔洞）保留**防误开洞；cov<COVER_MIN 的大分量（极细线 SDF 失效）保留原值防误删真实细线。
- 验证：analysis/test_writeback_logic.mjs 6 条分支用例全 PASS（近外部残留清除 / 内部孔洞保留 / 小杂点清除 / 极细线保留 / 正常像素保留）。`tsc --skipLibCheck` 仅余与本次改动无关的预存错误（line156 Float32→Float64 参数，原文件即存在）。

## 扣白/扣黑 alpha 分层修正（用户提供理想/实际日志对比）
- 现象：用户测试后反馈「不同区域应有不同不透明度」。理想结果 alpha 分三档：主体 128(3549px)/内部 192(675px)/核心 224(6px)；实际结果全部 128(4230px)——固定 KNOCK_RATIO=0.5 把分层信息压平。
- 算法 v2：**统一源色 + 逐像素亮度反推 alpha**。Pass1 找离背景最远（最饱和）非背景像素作源色 S；Pass2 用 Rec.709 亮度 Y=0.299R+0.587G+0.114B：扣白 `ratio=(255−Y)/(255−Y(S))`、扣黑 `ratio=Y/Y(S)`，alpha=ratio·KNOCK_MAX_ALPHA，颜色统一还原为 S。亮度度量比逐通道平均稳（避免某通道分母≈0 时噪声放大）。

## 扣黑「黑底偏亮」修复（反色往返解除预乘）
- 现象：用户反馈扣黑结果 Z 放在黑底上比原图层 X 在黑底上偏亮（此前曾反馈"白底偏暗"，是同一反色逻辑的两面）。
- **根因**：扣黑走 `Invert → 载入亮度选区 → Clear → 复制N份合并 → Invert`。反色往返把 straight 图层「解除预乘」：输入若是带透明内容图层 X=(x,a)（getPixels 返回 straight rgb=x、alpha=a），往返后变成 (x,1)；放黑底观感 = x·1 = x，而原 X 在黑底 = x·a，因 x>x·a 故偏亮。平铺合成图输入（rgb 已是 x·a、alpha=1）则不受影响（误差0）。
- **修复（src/adjustments/knockoutBatchProcessor.ts）**：黑分支处理前先 `capturePremultiplied(layer)` 抓 `premult = rgb·(alpha/255)`（黑底观感目标值），保留原图 bounds；流程结束后用 `applyPremultiplied(mergedLayer, cap)` 把最终图层遮罩内像素 RGB 覆盖为 premult、alpha 置 255，遮罩外透明。这样 Z 在黑底观感 = premult·1 = X 在黑底观感（严格相等）。复用原流程的合并仅用于得到可靠内容遮罩，不影响黑底观感。扣白路径不动。
- 像素 API：`imaging.getPixels` / `createImageDataFromBuffer` / `putPixels`（与 pixelDataProcessor 一致）；getPixels 返回 straight（未预乘）。
- 数值验证：analysis/knockout/sim_black_fix.py（红/绿/交叉，内容图层输入：当前黑底误差 120/66/28，修复后 0/255）；可视化 analysis/knockout/knockout_black_fix.html。
- 构建通过（仅 asset 体积告警）。

## 扣黑写回把图层撑成文档宽高的 bug 修复
- **现象**：扣黑结果 Z 的宽高被撑成整个文档，而原图层只是文档中一小块；扣白正常。
- **根因（两层）**：
  1. 初版用**局部 `targetBounds`** 写回，UXP 处理不稳定会撑大（已弃用）。
  2. 改全文档后又发现：`applyPremultiplied` 读内容遮罩时用的是**stale 的 `cap.left/top`**（处理前抓取的原始图层 bounds），而非 `mergedLayer` 的**实时 `bounds`**；一旦合并后图层几何有偏差，遮罩读区错位 → 写入异常。参照 `pixelDataProcessor.ts` 的「普通像素逻辑分支」（它固定用 `sourceBounds: layer.bounds` 实时取值）。
- **最终修复**：`applyPremultiplied` 以 `mergedLayer.bounds`（实时）读取内容遮罩，premult 用文档坐标反查 `cap` 偏移（轻微错位按偏移安全跳过，不越界）；仍用「全文档 imageData + `targetBounds:{0,0,docW,docH}`」写回，透明区不计入 bounds，尺寸不会撑大。扣白不动。
- **关键惯例**：本项目所有像素写回一律用「全文档 imageData + targetBounds(0,0,docW,docH)」；读取遮罩/像素必须用图层的**实时 bounds**（`layer.bounds`），绝不能用缓存坐标。

## 扣白/扣黑历史记录合并为单条
- **诉求**：扣白/扣黑在操作面板历史记录里生成一长串条目，用户希望合并成一条。
- **根因**：`runKnockoutBatch` 内有多个 batchPlay(DOM) 与 imaging 调用，每次都写一条历史态。
- **修复**（`src/adjustments/knockoutBatchProcessor.ts`）：把 `runKnockoutBatch` 函数体整体包进 `doc.suspendHistory(async () => {...}, mode==='white'?'扣白':'扣黑')`。`suspendHistory` 本身就是 `executeAsModal` 的封装，可在调用方已有的 executeAsModal 作用域内嵌套；校验（doc/layer 不存在）放在 suspendHistory 之前，避免报错路径生成空历史态。
- **验证**：`npm run build` 通过（仅 asset 体积告警）。重新加载插件到 PS 后，单次扣白/扣黑只产生一条名为「扣白」/「扣黑」的历史记录。
