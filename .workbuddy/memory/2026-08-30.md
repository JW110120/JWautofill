## 下拉遮挡「number-input 仍浮在弹层上」真凶 = author !important 压掉普通内联样式 + 统一 de61f56 选中样式
- **①遮挡失效的根本原因（重要，通用坑）**：`src/styles/input-fix.css` 里有
  `.pattern-picker/.color-settings-panel/.gradient-picker/.stroke-setting input[type="number"] { visibility: visible !important; opacity: 1 !important; pointer-events: auto !important; }`
  次级面板内的 number input 被强制可见。**普通内联样式属于 author 普通声明，层叠顺序低于 author `!important`**，所以之前 `el.style.visibility='hidden'` 完全无效——代码跑了、判定也命中了，但被 CSS `!important` 直接压掉。
  → 必须用 `el.style.setProperty('visibility','hidden','important')`：important 内联声明与 author important 处在同一 origin 层，再靠内联样式的最高特异性取胜。（同时写 `opacity:0` 与 `pointer-events:none` 的 important，Drover 下部分原生控件只吃 opacity。）

  - 调用侧（`Select.tsx` 与 `AdjustmentPanel.tsx` 的 `MaskSyncSelect`）统一：`useLayoutEffect([open,pos])` 里跑一次，再 `requestAnimationFrame` 补一次（UXP 偶发插入 DOM 当帧 `getBoundingClientRect()` 返回 0 尺寸），cleanup 里 `cancelAnimationFrame` + `session.restore()`。

## 选中行 `.sel` 背景蓝「消失」根因 = Spectrum `<Provider>` 覆盖了 `--primary-color`
- **现象**：CSS（`.mask-sync-select-opt.sel{background:var(--primary-color,...)}`）、JS（`o.value===value?'sel':''`）、构建产物均正确，但 portal 到 `#app` 后选中行背景不再变蓝。`dist` 中 `primary-color: rgb(38,128,235)` 仅 5 处（全为 theme.ts 的 `:root`/media 静态定义），无 JS 运行时覆盖。
- **根因**：`@adobe/react-spectrum` 的 `<Provider>`（`#app`/`#pixeladjustment` 根容器）会在其作用域根元素上注入/覆盖一批 CSS 变量，含 `--primary-color`（被设成 Spectrum 语义值）。弹层 `createPortal` 到 `#app` 后落在其作用域内，`var(--primary-color)` 解析到 Spectrum 值；变量「已定义但为空」时**不触发 fallback** → `.sel` 背景透明。这正是「CSS/JS 都对、逻辑上该蓝、实测不蓝」的唯一合理解释。`de61f56` 时弹层在面板内 DOM、不在 Provider 直接作用域根链上故正常。
- **修复**：在 `.mask-sync-select-pop` 与 `.mask-sync-select-wrap` 上**局部重声明** `--primary-color: rgb(38, 128, 235);`，让 `.sel` 与 `.head.open` 取到我们自己的主色蓝，覆盖 Spectrum 作用域。`.sel` 的 fallback 也收紧为 `rgb(38, 128, 235)`（与 `:root` 精确一致）。
- `webpack --mode=production` 通过（3 warnings）。已同步 MEMORY.md 避坑指南。改动未提交。

## 渐变「样式」下拉漏检（上一节"已修"是假象，本轮真正根治）
- **上一节（抬兜底高度到 90px）没生效的根因**：`update()` 之前的逻辑是「`measured.height>=24` 就判定矩形可信、直接采用它的 top/left」。而 UXP 下刚 portal 出来的 `position:fixed` 弹层，`getBoundingClientRect()` 的 **top/left 经常错乱（0 或远超真实值）**，只有 height/width 偶尔可信。于是短菜单（渐变「样式」仅 2 选项）的矩形被定位到错误位置，正下方「角度」数字永远判不到相交 → 一直浮在菜单上。把兜底高度抬到 90px 的修复因为 measured 矩形被优先采用而**从未被用到**。
- **本轮真正修复（src/utils/popOverlay.ts `update()`）**：弹层的 `left/top/width` 是我们亲手写成 `pos`（下拉头部 measured rect，含 `head.bottom+2`）的，所以 `pos` 才是可靠原点。`estimatePopRect(pos,…)` 的 `fallbackRect` 其 X/Y/width 全部来自 `pos`，`update()` 现在**用 `fallbackRect` 锚定矩形（绝不用 measured.top/left）**，高度取 `max(measuredH, fallbackH)`（兜底 = `min(200, max(90, n*24+12))`，2 选项即 90px，足以盖住头部正下方那一列文本控件）。这样无论 UXP 把 measured 坐标返回成什么样，遮挡带都稳定罩住「角度」数字。
- 几何依据：`.gradient-settings-area` 固定高度小区域，`样式`下拉在顶部、`角度` number 紧随（约在其头部下方 60px），菜单约 50px 高，二者屏幕重叠；旧逻辑因坐标错乱漏判，新逻辑锚定 pos 后稳命中。
- `tsc --noEmit` 仅 node_modules/@types/node/ffi.d.ts 的预存类型错误（与改动无关），`webpack --mode=production` 通过（3 warnings，均体积提示）。改动未提交。若重载后无变化，多半是 UXP 缓存了旧 bundle，需重载插件/清 UXP 缓存。

## ⚠️ 渐变下拉漏检（前两节"已修"均为误判，本轮才是真正根因）
- **前两次误判（撤销）**：① 抬兜底高度 90px → 无效；② 改用 `pos` 锚定弹层矩形（弃用 measured top/left）→ 仍无效。两次都假设"弹层矩形算偏所以漏判"，但 popup 矩形已锚定到可靠的 `pos`（head.bottom+2），几何本就罩得住角度输入。
- **真凶（输入框自身矩形退化）**：遮挡在 `update()` 里对每个候选控件用 `el.getBoundingClientRect()`，一旦 **width/height<=0 就 `continue` 跳过**。UXP 下**原生 number/text 输入控件（尤其次级面板 `.gradient-picker` 这种 `z-index:9999` 作用域内）常返回 0 尺寸退化矩形**——控件画得出来、用户看得到，但 JS 量到 0 宽高。于是「角度」数字明明压在弹层上，却因矩形退化被 `continue` 跳过、永远不隐藏 → 一直浮在菜单上。主面板输入框能正常量到尺寸，故只有渐变这种次级面板会触发，表现为"这个下拉有点特殊"。
- **修复（src/utils/popOverlay.ts）**：新增 `robustRect(el)`，逐级向上（自身→父包裹 div→更上层容器，最多 4 级）取第一个**有效尺寸**的矩形用于相交判定；普通 DOM 容器在 UXP 下通常能返回有效矩形，从而稳定命中。删掉原来 `if (r.width<=0||r.height<=0) continue` 的硬跳过。popup 矩形仍锚定 `pos`（上一轮的改进保留，无害）。
- **布局 3px 位移（顺带修）**：`gradient.css` 里 `.gradient-angle-setting{transform:translateY(-3px)}` 是把角度行整体视觉上移 3px 的 hack，径向模式移除角度行后这 3px 参考消失，造成"下拉相对容器上移/间距变化"的观感；且径向 `compact` 把 checkbox 间距 10→8、面板高度 18%/80px→12%/60px，移除中间行即重排。→ 删除该 transform hack，并把「样式下拉 / 角度 / checkbox」三组 `margin` 统一为 `10px 0`（配合 `.gradient-settings-area` 的 10px padding，使"下拉顶到容器上边距 == checkbox 底到容器下边距"在两种模式下恒定；移除角度行不再引发重排位移）。

## ⚠️ 渐变（及全部次级面板）下拉漏检的【真正】根因（前四节全是误判，本轮命中）
- **前三/四节误判全部撤销**：「抬兜底高度 90px」「改用 pos 锚定弹层矩形」「robustRect 向上取有效矩形」都假设"弹层几何算偏 / 输入框矩形退化 → 漏判"。但用户反馈"其它下拉没问题、只有渐变特殊"才是决定性线索：其它下拉（主面板 #app 下）能正常遮挡，说明 `popOverlay` 的几何 / robustRect / pos 锚定其实都工作正常；真正不同点只在渐变（及 pattern/color/stroke 等次级面板）被一条专门的 CSS 规则死死压住。
- **真凶 = `src/styles/input-fix.css` 第 38–45 行的次级面板强制可见规则**：
  `.pattern-picker/.color-settings-panel/.gradient-picker/.stroke-setting input[type="number"] { visibility: visible !important; opacity: 1 !important; pointer-events: auto !important; }`
  它带 `!important`，本意"确保次级面板输入可见"。**UXP 的 CSS 引擎在 important 级会把「样式表 !important」判在「内联 !important」之上（与标准 CSS 层叠相反）**——于是遮挡逻辑写的内联 `visibility:hidden !important` 永远赢不了它，表现就是"次级面板的下拉菜单下方数字始终浮在菜单上、而主面板下拉正常"。主面板 `#app` 下没有这条规则，故遮挡对主面板生效，造成"只有渐变特殊"的错觉。
- **修复（仅改 `input-fix.css`，一处）**：把这三个属性**去掉 `!important`**（降级为普通声明，保留 `visibility:visible;opacity:1;pointer-events:auto` 的"常态可见"语义）。去掉后，遮挡的内联 `visibility:hidden !important`（important 级）正常胜过普通声明 → 渐变 number 输入被隐藏；且用 `visibility` 而非 `display`，**不引发布局位移**（占位保留）。
- **附带收益**：pattern/color/stroke 等所有次级面板下拉的同类漏检一并根治（它们共用同一条规则）。
- **同步更正**：`popOverlay.ts` 两处过时注释（原先声称该规则"带 !important 且必须靠内联 important 取胜"）改为说明"此规则绝不可带 !important，否则 UXP 引擎让样式表 !important 盖过内联 !important"。
- `webpack --mode=production` 通过（3 warnings，均体积提示）。改动未提交。若重载后仍无变化，多半是 UXP 缓存旧 bundle，需重载插件 / 清 UXP 缓存。
