## 0x0226：裸数字键笔刷热键穿透到 PS，顺带改画笔不透明度

**用户报**：笔刷热键绑 `Num1–Num9`，按 Num5 调笔刷时画笔不透明度被改成 50%，要求避免。

**根因**：`kh_combo_to_hotkey()` 主动 `if(!m) return 0` 排除全部裸键注册 ⇒ 9 条裸键
（Num1–7 / H / L）只能由「不吞键」的键态轮询兜底触发；而 `pi8li.log` 实证 PS 前台时
`按键通路：钩子 +0 / 轮询 +1`（LL 钩子收不到键，反复强制重装）⇒ 唯一能吞键的通路
没干活，数字键原样落进 PS，被当成不透明度 1–9 快捷键。旧注释「RegisterHotKey
不接受裸键」经本机实测为误（`mods=0` / `MOD_NOREPEAT` 对 Num5、主键盘 5 均 TRUE）。

**修法**：`kh_hk_sync` 改用 `kh_combo_to_key` + 新 `kh_is_digit_vk`（0x30–39 /
0x60–69），只把表内实际绑定的**数字类裸键**纳入 RegisterHotKey 系统级独占；
字母符号裸键维持旧语义，录制/失焦/不在位/让位撤注册门逐字不动。

**文件级 change manifest**

| 文件 | 改动 |
|---|---|
| `native/JWautofillHost/keyhook.c` | ① 顶部补 0x0226 摘要；② 前置声明注释更新；③ 0x013D 段修正「裸键注册不了」的事实错误并写明取舍；④ 删 `kh_combo_to_hotkey()`、新增 `kh_is_digit_vk()`；⑤ `kh_hk_sync()` 循环放行裸数字键注册 + `digits` 计数；⑥ 注册日志增加「其中裸数字键 N 条」 |
| `native/JWautofillHost/plugin_main.c` | 补 0x0226 版本史，`jw8li_version` 0x0225 → **0x0226** |
| `native/JWautofillHost/build/JWautofillHost.8li` / `.dll` | 重新构建产物 |
| `.workbuddy/memory/MEMORY.md` | 现役版本改 0x0226、铁律标题范围 0x0211–0x0226、新增铁律 113 |
| `.workbuddy/memory/refs/keyhook-8li.md` | 追加 N11（根因三事实 / 修法 / 边界 / 验收） |
| `.workbuddy/memory/2026-11-11.md` | 本文件 |

**验证**：`bash build.sh`（沙箱外）零告警零错误；PiPL 162 字节往返一致；导出表
5 项齐全（AutoPluginMain / jw8li_version / jwwh_set_engine_off / jwwh_unhook /
jwwh_version）。独立 C 探测器实测 `RegisterHotKey` 对 `VK_NUMPAD5`、主键盘 `5`
在 `mods=0` 与 `MOD_NOREPEAT` 下均返回 TRUE。

**部署状态**：构建完成，但 PS 正在运行（pid 11808），安装目录
`C:\Program Files\Adobe\Adobe Photoshop 2026\Plug-ins\JWautofillHost.8li` 被独占

## 0x0227（面板侧）：纯色填充 + 清除模式按纯白输入，还原「套索 Delete」

> ⚠️ 0x0227 是**面板侧变更代号**，本轮没改 C，`.8li` 版本仍为 **0x0226**。

**用户报**：`Shift+E` 呼出清除模式套索后，若前景色是红色，删除只降低不透明度，
与「套索圈选 → Delete」体验不同、反直觉。要求：纯色填充 + 清除时不改用户前景色，
公式输入一律按纯白处理；想要半透明由用户自己调面板不透明度；图案/渐变清除维持原样。

**根因**：清除算法内核（`ClearAlgorithms.ts`）的统一不变量是
「输入越白，删除越多」，F=255 才等于 100% 删除。而纯色清除的 F 来自
`ClearHandler.getSolidFillGrayData()`：`app.foregroundColor` → `calculateRandomColor`
抖动 → `hsbToRgb` → `rgbToGray`。红色灰度约 76 ⇒ `A' = 255 − 76 = 179`
（不透明度还剩 70%），正好是「只是降低不透明度」。
另一条 `SingleChannelHandler.clearSingleChannel` 的纯色分支同样吃前景色。

**数值对照**（面板不透明度 100%，A=255）：

| 输入 | subtract A' | multiply A' | 背景 whiten C' |
|---|---|---|---|
| 旧：红色前景 F≈76 | 179 | 179 | 76 |
| 新：纯白 F=255 | **0** | **0** | **255** |

**修法（只动两个 TS 文件）**

| 文件 | 改动 |
|---|---|
| `src/utils/ClearHandler.ts` | ① 删 `ColorUtils` import 与 `getSolidFillGrayData()`；② `buildClearFillData` 去掉 `foregroundColor`/`quickMask` 两个参数，纯色分支改为 `buildSolidClearWhite(bounds)` 直接给 `F≡255`；③ 新增 `buildSolidClearWhite`（长度口径 = 选区内像素数）；④ `clearInQuickMask` 删「抓前景色算灰度」，改为纯色模式下「进入保存前景色 → finally 还原」（`getQuickMaskPixels` 为转蒙版会临时 set 前景色、退出快速蒙版也会扰动），图案/渐变不加这层包装 |
| `src/utils/SingleChannelHandler.ts` | `clearSingleChannel` 删掉预先保存前景色；`case 'foreground'` 不再调 `generateSolidColorData`，直接给全 255 的 `clearData` + 全 255 的 `alphaData` |

**⛔ 逐字未动**：`buildClearFillData` 的 pattern / gradient 两条分支、所有写回公式
（`clearScalarValue` / `clearBackgroundColor` / `clearStrength`）、面板不透明度参数、
非清除模式的纯色填充（`app.tsx` 的 `calculateRandomColor` 与颜色/抖动设置）、
`SingleChannelHandler.fillSingleChannel`（仍读前景色）、`StrokeSelection` 清除描边
（输入是描边色而非前景色）、`PatternFill` / `GradientFill` 的快速蒙版实现、原生 .8li。

**验证**：`npx tsc -p tsconfig.check.json` 全仓 143 条历史错误（调整面板/组件族），
落在 `ClearHandler.ts` 的 8 条全是 `selectionIndices[i]` / `selectionValues[...]` 的
`unknown` 索引老问题，行号 1723/2265/2581/2691/2805/2866/2887/3007 与本轮改动行段
完全不重合；`yarn build` 成功（仅 3 条 bundle 体积警告，历史常态），
`dist/bundle.js` 更新为 1,468,505 字节。

**生效方式**：面板 JS 需重载；若用 UXP Developer Tool 加载 `dist/` 直接重载面板即可，
正式安装版需把 `dist/` 同步到安装目录后重启 PS。本轮不需要重编/重拷 `.8li`。

## 0x0228 · H/L 在另存为对话框里被摘键（`.8li`，已部署）

**用户报**：「修改图层名称时 H、L 还能打出来，但另存为图片弹出的窗口里输入 H、L
被系统摘键，无法输入。」

**根因澄清（重要，别再归错）**：H/L **没有**注册 RegisterHotKey。日志
`RegisterHotKey 接管 9 条（其中裸数字键 7 条；其它裸键交钩子/轮询 2 条，被占用 0 条）`
里的「其它裸键 2 条」正是 `H`(`0x48`) 与 `L`(`0x4C`)（`hotkeys.json` 里另有一条
`altTool`=`/` 与空 combo 的 `blendHotkey` 不进热键表）。真正吞键的是 **LL 钩子**：
PS 主窗口的按键进不了钩子链（历史日志 `按键通路：钩子 +0 / 轮询 +1`），所以图层名
内联编辑时 H/L 原样输入；但**原生对话框**的按键能进钩子，且
`kh_ps_foreground()` 成立 ⇒ `kh_dispatch` 命中 H/L 即 `return 1` ⇒ 字符被吞。
同一键在两处结果相反，差别只在「钩子收不收得到这一击」。
今日日志 `12:54:41 ★诊断：前台判定失败 ⇒ 放行 vk=0x4C（fgPid=24584 本pid=24948）`
也印证：钩子确实能收到键，只是那次前台不是 PS 才放行。

**修法（`native/JWautofillHost/keyhook.c`，四条键路一起熄火）**

| 通路 | 改动 |
|---|---|
| 探测 | 新增 `g_khTextGuard` + `kh_text_input_probe()`：每 10ms 在 `kh_poll_step` 里只读判定 `#32770` / `WS_EX_DLGMODALFRAME` / 宿主被 `IsWindowEnabled` 禁用 / 焦点控件类（Edit、RichEdit、ComboBox、TextBox、AtlEdit…）/ 可见插入光标；**LL 回调只读一个 volatile LONG**，维持回调 O(1) 零 Win32 查询纪律。插入光标闪烁用 400ms 黏滞压翻面 |
| ① LL 钩子 | `kh_dispatch` 前台判定之后、退格删绑之前整击 `CallNextHookEx` 放行（不吞键、不广播、不记 `kh_dual_mark`）；新增 `★诊断：文本输入闸门生效` 边沿日志 |
| ② 轮询 | `kh_poll_edge` 在 `kh_ps_foreground()` 之后加 `if (g_khTextGuard) return;`（否则打字时 H 会翻主开关、L 抢工具焦点） |
| ③ RegisterHotKey | `kh_hk_sync` 的 `want` 加 `!text`，新增 `g_khHkText` 状态位；同步节奏 **100ms → 10ms 一拍**。`kh_hk_fire` 压住迟到的 WM_HOTKEY。⇒ 文件名框里 Num1–7 / Shift+E 也不再被全局独占摘走 |
| ④ 按住键电平 | 临时吸管 `/` 的 `altHold` 块加 `holdVk && g_khTextGuard` 分支，作废起按准入（`s_altArm=0`），防止打字时的 `/` 切吸管 |

**逐字未动**：录制分支（仍在闸门之前）、`kh_combo_to_key` / `kh_is_digit_vk` 数字键
注册规则、0x0224 混合模式让位、在位/布防/失焦/熔断门、`kh_dual_mark` 去重、
0x0211 物理 Alt 否决位。

**踩坑**：一开始为 `GUITHREADINFO` 显式写 `#define WINVER 0x0600`，反而把工具链
默认档调低 ⇒ `MOD_NOREPEAT`（0x4000，需 ≥0x0601）未声明、编译失败。
⛔ **不要手写 WINVER**，默认档两者都有。

**验证**：`build.sh` 零告警零错误、PiPL 162 字节往返一致、导出表 5 项齐全；
PS 当时已完全退出，已把 `JWautofillHost.8li` 覆盖到
`C:\Program Files\Adobe\Adobe Photoshop 2026\Plug-ins\`，`cmp` 字节一致。

**验收**：重启 PS 后日志应有 `文本输入闸门 0⇒1（fgCls=#32770 ... why=1）` 与
`★诊断：文本输入闸门生效 ⇒ 整击放行 vk=0x48/0x4C`；另存为文件名框能敲 H、L、
数字、退格且不触发任何热键；关掉对话框回到画布，H/L、Num1–7 仍照常生效
（离开输入框后有 ≤400ms 黏滞，属预期）。若 `why=0` 说明该对话框没被识别，
