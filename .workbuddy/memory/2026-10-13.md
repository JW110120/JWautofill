## 蒙版同步「无任务仍刷 modal scope」修复 + 全量高频 modal scope 清点

### 报障
用户截图：`[蒙版同步] 收到事件: set` 后紧跟红色 `821 Too many modal scope commands`，
且**当前一个蒙版同步任务都没有**。诉求：① 无同步任务时监听应停摆；
② 线稿参考下拉是否也产生高频 modal scope、能否改成展开时才取文件树；
③ 列出还有哪些监听会导致高频 modal scope。

### 根因（MaskSyncEngine）
「没任务」的短路点位置错了 —— 它排在**四个受保护读取之后**：
`refreshActiveDoc`(1) + `psRead(app.activeDocument)`(1) + `refreshActiveDoc` 又一次(1)
+ `checkUndoGate→readActiveHistoryId`(1)，之后才 `if (list.length===0) return`。
`set` 是最高频事件（画一笔/改滑块/拖选区各一条）⇒ 无任务时反而模态命令最密。
2s 兜底轮询再重复一遍这 4 个。

### 改动

### 线稿参考的根因（比预想更深）
两缺陷叠加：① 回调对**每条**通知（含纯选区 set）无条件 `invalidateLayerSnapshot()`；

⇒ 每条 set = 1 模态作用域 + ≈5N 次 get。

### 关键教训
⛔ **短路必须排在所有受保护读取之前**。「没任务/没数据就返回」写在链路末尾，
等于每个高频事件仍付全额模态作用域成本 —— 这是「无任务反而最拥堵」的通用模式。
⛔ 事件驱动的缓存打脏必须**按语义分类**（结构 vs 选区），不能「来什么事件都打脏」；
否则下游的 `isDirty()` 守卫与 `maxAgeMs` 复用全部失效。
⚠️ UXP 各面板是**独立 JS 上下文**：`app.tsx`（选区填充）与 `AdjustmentPanel`（绘画工具箱）
是两个 entrypoint，`MaskSyncEngine` 单例只存在于后者。

## 第二轮（12:30 用户回测反馈）：三个问题的**根因级**修复

用户回测否定了上一轮的 ③④⑤，并新增一条。逐条定性如下。

### 问题二（拉绳，最严重）根因：**把「绳」实现成了指数跟随**
现象「套索光标与洋红点（绘制点）始终重合」，截图可读出的信息是**洋红点偏移 ≈ 0**
⇒ 输出点与原始点几乎相等 ⇒ 不是 HUD 画错了，是**算法根本没产生滞后**。
定位：`wintab_hook.c` 的 `mode==1` 分支
```c
} else { g_ox += dx*0.25; g_oy += dy*0.25; }   /* 绳未绷紧时的“轻微跟随” */
```
205Hz 下包间隔 ~5ms ⇒ 一阶系统 τ = dt·(1−α)/α ≈ 15ms ⇒ 稳态滞后只有 v·τ
（500px/s 时 ≈7px），再被半径上限一夹就归零。**与用户描述「洋红点钉在圆心、光标圈内自由」
完全相反**。改法：删掉该分支，做成**真·定长绳**——`dist ≤ rope` 时输出点一字节不动，
`dist > rope` 时拖到恰好绳长处。这才同时满足用户描述的「绳没绷紧输出点不动 / 绷紧了圈被拖着走 /
光标永远出不了圈」。

### 问题一 根因：张力与半径**改的是同一件事**
`leash_px()` 里张力只在 `15%~100%` 之间**缩放半径** ⇒ 半径 100 + 张力 50 时圈只有 58px。
两个滑杆互相打架 ⇒ **删除张力**（用户要求）。
⚠️ 槽位 21 刻意**保留空洞不重编号**：它必须与 C# 的 `I_*` 常量逐项对应，少一项则后面 11 个槽整体错位。

### 问题三 根因：工具闸门**读失败即放行**
两处叠加：
1. `getSelectedBrushToolEnum()` 只认 `{_enum}`/`{_value}`。`application.tool` 在不同版本
   可能回**裸串** ⇒ 恒为 null ⇒ 上层判成「未知(2)」⇒ 原生侧对 2 是**放行** ⇒ 闸门形同虚设。
   ⇒ 新增 `normalizeToolId()`（吃 string/_enum/_value/_obj/tool/id/name 七种形态）并导出复用。
2. 面板读失败时直接 `setSmoothToolGate(2)`。偶发失败（宿主忙、世代号刚变）就把闸门整个打开。
   ⇒ 新增 `applyToolGate()`：**读失败沿用上次判定**（心跳仍会续期时间戳，让「不是套索」的 0 保持新鲜）；
   只有「从未读到过」才维持初值 2。
3. 诊断：状态条常驻显示**读到的工具 ID 原文**（`lastToolRead`）。闸门失效时
   「读错了」与「没读到」处置完全不同，而这两态原本在界面上不可分辨。

### 问题三的另一半：平滑感知被两个量程杀死
- `SPEED_FULL = 1.2px/ms` 落在**人的常规运笔区间 0.05~1.5px/ms 内部** ⇒ 500px/s 就被当「甩笔」，
  k 被抬到 τ_eff≈15ms，滞后只剩 ~8px。⇒ 抬到 **3.0**（3000px/s）并把混合系数 0.5→0.4。
- `tau_from_strength` 上限 36ms ⇒ 抬到 **100ms**（`TAU_LN = ln(13.5)`）。
- 顺带修一个真 bug：`DragHandler` 的 `'smooth:radius'` 上限还是 **40**（漏改，拖标签只能到 40）。

## 第三轮（13:26 用户回测）：HUD 角色倒置实锤 + 标定分母 10 倍失真

用户报（附三截图）：①光标钉在圆心不动，洋红点从圆心朝不可预测方向延伸到圆周又**弹回圆心**循环；
②某次开关「拉绳提示」后套索只能画折线（选区边缘与轨迹点有间距，拉远才补一段）；③能画曲线时毫无平滑感。

### 根因（真机截图 + jwwh 日志 + Wintab 语义推理，非猜测）
1. **旧前提「系统光标 = 平滑后的输出点」是错的**。系统光标由 Wintab 系统上下文
   （CXO_SYSTEM）在**驱动侧**移动，跟随**原始笔**；detour 改写的只是交给 PS 的那份副本，
   管不到系统光标。⇒ HUD 窗口钉在 GetCursorPos() = 钉在**笔尖**上；洋红偏移 (raw−out)
   从笔尖出发画出的是它的**镜像点**——用户看到的"诡异洋红点"由此而来（§F 预言的

## 第六轮（16:06 用户回测）：拉绳瞬移根因 / 绳样式 / modal 暴涨

用户报 3 条（**圆心位置与移动方向已对了**，但）：① 光标到圆周时圆心**立刻跃迁到光标**、选区画成一段段直线（要 PS/LN 那种平滑拉绳，圆周与光标保持相对静止）；② 绳子一头粗一头细、始终直线，没有绳感（PS 参照：光标在圆心内时绳呈**曲线**，到圆周才**拉直**）；③ **性能**：没操作也每隔一段时间 `Too many modal scope commands` 狂涨（截图：编号 2064→2486→2787，`pending promises: 20/40`），生成选区后 PS 频繁读条等「获取当前工具」，填充很不顺。

### ① 圆心瞬移 —— 根因是**公式写反**（明确 bug）
拉绳分支原为 `f = radiusPxF / distPx` ⇒ 每包沿 dx 走 `distPx·f = radiusPxF` ⇒
新距离 = `distPx − radiusPxF`。光标刚越过圆周时 `distPx ≈ radiusPxF` ⇒ 新距离 ≈ 0
⇒ **输出点被直接搬到光标上**（这就是「跃迁」），于是每个越圈点都成为一个新锚点
⇒ 选区是一段段直线。
✅ 修复：`f = 1.0 − radiusPxF / distPx` ⇒ 移动量 = `distPx − radiusPxF`
⇒ **新距离恒等于 radiusPxF** ⇒ 光标始终停在圆周上、与圆周相对静止，圆心沿光标方向连续前进。
两侧都连续：`distPx→radiusPxF⁺` 时移动量→0（不跳变）；此后 distPx 每增加 Δ，输出点同步走 Δ。

### ② 绳样式 —— 锥形直线 → 悬链曲线
旧：`NSEG=12` 折线 + `wdt = 4→1px` 锥形（用户明确否掉）。
新：统一 **2px** 细线 + **二次贝塞尔**；垂度取**小垂度悬链线**
`sag = sqrt(3·(L−d)·d / 8)`（L = 绳长 = 圆周半径，d = 两端距离）
⇒ `d → L` 时 sag → 0 **自然拉直**，不需要特判分支。
控制点 = 中点 + `2·sag·n`（贝塞尔 t=0.5 处偏移是控制点偏移的一半）；
`n` 取「垂直方向中 y≥0」那一侧（一律朝屏幕下方弓，像自重），
绳恰好水平时取右侧 —— ⛔ 不按运动方向定弯曲侧（停笔时方向未定义会导致绳突然翻面）。

### ③ modal 暴涨 —— 根因是**请求率超过节流吞吐**
`psAccess` 的 `MIN_MODAL_GAP_MS = 300` 是**全局**模态节流 ⇒ 模态命令
**吞吐上限 = 3.3 次/秒**。而空闲态常驻巡检合计：
工具 300ms(3.3/s) + 快速蒙版 300ms(3.3/s) + 文档身份 500ms(2/s) ≈ **8.7 次/秒**
⇒ **每秒净积压约 5 个请求** ⇒ 约 7 秒就堆到 40（正是截图里的 `pending promises: 40`，
编号递增则是同一个计数器累积）。用户看到的「读条等获取当前工具」= 本巡检的
`readCurrentToolId()`（label「读取当前工具」）排在模态队列里发不出去。
✅ 修复：把总请求率压到节流吞吐之下 —— 工具 300→**1000**、快速蒙版 300→**1000**、
文档身份 500→**2000**（合计 2.5 次/秒 < 3.3）。代价：切工具后闸门最坏 1s 更新。

直读与 skip 不算），降序 + 次/秒；`__jwPs.trace(true)` 后每 5s 自动打印一次。
⛔ 若下一轮仍超标，拿到这份输出就能一次定位（别再靠猜）。
