### ⛔ 真 bug：`drawOk` 把 HUD **永久挡死**（用户报的「切换工具后 HUD 失效」）

- 原实现 `drawOk = 极性已证 ? (最后一次值==1) : 放行`（smooth_engine.c:4722）。
- **`toolModalStateChanged` 的键是 `0x4C766C20` = `'Lvl '`**，与 `modalStateChanged`
  **同一个键**。它 64 次投递**全部是 1ms 内 `1→0` 成对翻转**
  （06:32:00.072 变 1、.073 变 0）⇒ **最后一次值恒为 0**，而极性一经那两次翻转就被判
  「已证明」⇒ `drawOk` 从 06:32:02 起恒 0，`[hud] 未显示` 行 `draw=0(tm=0,k=1)` 到日志末尾。
- **后果 = 即使切回套索，HUD 也再不会显示。** 它不是「工具是否在绘制态」，而是 PS
  每次工具操作的**模态瞬时起落**。
- **修复（0x0114）**：`drawOk` 恒放行，`tmv/tmK` 只留在诊断行继续取证。
  ①诉求由 `gateOk`（工具闸门）∧ `strokeOk`（一笔之中，含 penDown）完全覆盖。
- 📌 **教训**：`pstool_tool_modal_known()` 的「极性已证明」只要求见过 0 与 1 各一次 ——
  对一个 1ms 翻转的抖动信号，这个门槛**形同虚设**。凡是拿「见过两种值」当可信度门槛的
  判据，都必须再加「值保持时长」这一维，否则就是自欺。

### ⑤ 的偏移已由真机定案 —— 昨天标的两套**都错**

- 用户问：热键（WH_KEYBOARD_LL）能否从 HotkeyDaemon(65M)+FixKeyboard(76.5M) 迁进 PiSmooth8li，省 dist ~141.5M。
- 结论：**可行、同构迁移**。依据：① WH_KEYBOARD_LL 是全局钩子且不要求钩子过程在 DLL（daemon 自己 hMod=GetModuleHandle(null)，Program.cs:1890）；② .8li 已是「PS 进程内 WS 服务(18924)+钩子+看护」形态；③ 唯一结构缺口 = 专用消息循环线程（daemon「录制线程」Program.cs:2018 同款），.8li 现有线程均无消息循环。
- 需移植清单：钩子线程(逐轮 try/catch)、回调零 I/O + 50ms 预算 + 3 连击熔断 fail-open、IsPhotoshopForeground()（Program.cs:1773）、吞键 return 1、hotkeys.json/两段式录制、WS 18923 协议（建议 .8li 开第二监听，HotkeyBridge.ts 零改动）、HotkeyWatchdog、LowLevelHooksTimeout 启动检查（Program.cs:1333）。

- FixKeyboard 取舍：exe(76.5M) 可删；fix-keyboard.ps1(17KB)/bat 建议留（第 3 步重置 LowLevelHooksTimeout 仍是系统级威胁；第 6/7 步 HID/USB 冻结与钩子无因果）。dist/native 现 138M，迁移后 ~10M 内。
