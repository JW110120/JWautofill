## 第六轮：绘画工具箱按钮改 div + alpha对齐算法重写

1. **按钮样式统一**：AdjustmentPanel.tsx 全部 12 个 `.adjustment-button` `<button>`（含注释掉的"分块补色"）及 1 个 `.adjustment-modal-close` `<button>` 改为 `<div role="button" tabIndex={0}>`（PS 27.9 新后端给 `<button>` 绘制原生灰面、appearance:none 无效，只能换 div）；`.adjustment-button` CSS 对齐 `.main-button`：border-radius 4px、box-sizing:border-box、user-select:none，hover 增加 `border-color: var(--primary-color)`（原来缺）、active 用 `var(--button-down)`。做法：`replace_all` 三个字符串（开标签两处 + `</button>`→`</div>`），先把 modal-close 开标签也换成 div 以免 `</button>` 全局替换后标签不配对。

2. **alpha对齐重写（修复"没有效果"）**：原算法用单一环形邻域 Chebyshev[2,4] 迭代拉低，但交叉点（凸包）只要比环宽，环就"困"在凸包内（ring max 仍是高 alpha）→ peak≈0 → 完全不生效。改为**多尺度环形邻域 max 取 min**：对每个候选像素，在 scales=[4,8,14,22,32]（环宽 3）上分别求环形邻域最大 alpha，再取各尺度最小值作为"线条应有水平"（必有一个尺度能跳出凸包落到单线），单次拉低（rate 0.9）。合成测试验证：线宽 9/21/33/41px 的交叉点都从 192→约134，单线 128 不被误伤，细线 2px 也不误伤。

**经验**：单一固定半径的环形邻域无法覆盖不同粗细的交叉点——凸包比环宽时失效。取「多个尺度环形邻域 max 的最小值」能自适应：小尺度困在凸包内（高值）、大尺度跳出到单线（低值），min 自然落到单线水平；且线条中心各尺度 ring max 都≈自身，min 后 peak≈0 不会误判。用 Node 写合成场景（source-over 叠加两条半透明线）跑纯 JS 算法，比在 PS 里反复调试快得多。

## 第七轮：alpha对齐"无选区/全文档"修复 + 分块算法 + batchPlay 全选

**根因**：alpha对齐仍"置入像素但无效果"。排查确认纯算法本身是对的（Node 合成交叉点验证 190→109，会改动像素），问题出在**无选区场景的数据链路**：`getSelectionData` 里 `hasSelection = selectionResult[0].selection !== undefined` 判断不可靠——无选区时 PS 可能返回空对象/零面积 `selection`，导致走进"有选区"分支却得到空选区（0 像素），算法 validCount=0 直接原样返回，`applyProcessedPixels` 把未修改的像素写回 → 有"置入像素"历史但画面无变化。且全文档回退路径会构造 `Set` 存全部索引 + 全文档 RGBA/掩码数组，内存/性能差。

**改动**：
1. `alphaAlignProcessor.ts`：把 `RING_WIDTH/SCALES/MIN_ALPHA/PEAK_THRESH` 提升到模块级，导出 `ALPHA_ALIGN_HALO = maxScale + ringWidth + 2 = 37`（分块 halo 半径）。
2. 新增 `chunkedAlphaAlign.ts`：`processAlphaAlignChunked()`。tile=512 + halo=37 分块处理——每块 getPixels 读"块+halo"区域、有选区时 getSelection 读该块掩码（全文档则 mask 填 255）、跑 `processAlphaAlign` 后只把**内部区域**写回（halo 只作上下文，避免接缝），内存控制在单块尺度。
3. `AdjustmentPanel.tsx`：
   - `toPixels` 提升到模块级；新增 `selectAllDocument()`（batchPlay `set` selection→`allEnum`）与轻量 `getSelectionBounds()`（面积>0 稳健判选区，无选区时自动 batchPlay 全选并标 `isFullDocument`）。
   - `getSelectionData` 改为基于 `getSelectionBounds`（修复脆弱判空 + 统一全选逻辑），返回值新增 `isFullDocument`。
   - `handleAlphaAlign` 重写为 `getSelectionBounds` + `processAlphaAlignChunked`，不再走 `processPixelData/applyProcessedPixels` 的全文档大数组路径。

**验证**：`npm run build` 通过；Node 离线对比"分块+halo"与"整图直接处理"结果 alpha 通道 0 差异（125 个交叉像素全部正确，无接缝）。

**经验**：
- `imaging.getData()` 8bit 返回 `Uint8Array`（非 ArrayBuffer），可直接下标访问；`getSelection()` 返回单通道灰度（等价快速蒙版）；`getPixels()` 普通图层返回 4 通道 RGBA、背景层 3 通道。
- 需要邻域上下文的像素算法做分块时，块边缘要外扩 halo（≥ 算法最大邻域半径），只写回内部区域即可保证结果与整图一致且无接缝。
- `set selection` 全选的 batchPlay：`{_obj:'set', _target:[{_ref:'channel',_property:'selection'}], to:{_enum:'ordinal',_value:'allEnum'}}`。

## 第八轮：alpha对齐 I/O 改用整文档读写 + 算法环形邻域解耦选区 + rate=1.0

**用户反馈的问题**（对照原图/结果图）：
1. 分块 per-tile `putPixels` 在普通图层上导致选区外像素被擦掉——证明这套 UXP 的正确读写范式是**整文档 `getPixels` → 处理 → 整文档 `putPixels`**（与 `handleGradientModify` / `applyProcessedPixels` 一致）。
2. 小选区时只产生轻微位移，没真正统一不透明度——因为环形邻域的有效像素被选区掩码限制，环里看不到选区外的单线，找不到"单线水平"。
3. 即使全文档选区，交叉点的不透明度"依然很高"——rate=0.9 留下 10% 残余。
4. 大选区多次 `putPixels`（每块一次）导致多个"置入像素"历史步骤。

**改动**：
1. `alphaAlignProcessor.ts`：环形邻域参考像素从 `vR[ni]===0`（依赖选区掩码）改为 `aR[ni] < MIN_ALPHA`（只看 alpha）。这样**选区只决定"哪些像素会被修改"，环形邻域永远参考所有画过的线条像素**，小选区也能引用选区外的线条找到"单线水平"真正统一交叉点。同时 `rate = 0.9 * strength` → `rate = strength`（默认 1.0，完全统一，无残余）。
2. 删除 `chunkedAlphaAlign.ts`（per-tile I/O 在这套 UXP 上行为不对）。
3. `AdjustmentPanel.tsx` 的 `handleAlphaAlign` 改为**整文档读写**模式（参考 `handleGradientModify`）：`getSelectionBounds()` 取边界+自动全选 → `imaging.getPixels` 读完整图层像素并映射到文档坐标系 → 构建整文档掩码（全选填 255 / 有选区读 `imaging.getSelection` 并映射）→ `processAlphaAlign` 处理 → 按掩码系数 `out = orig*(1-coeff) + processed*coeff` 混合（选区外像素不变）→ `imaging.putPixels` 整文档写回。一次 `putPixels`，一次历史步骤。

**验证**：构建通过（webpack production）；算法离线对比全文档/小选区两种场景，全文档交叉点正确拉回，小选区也能引用选区外线条完成统一（之前小选区会因为环里没参考而失效）。

**经验**：
- 这套 UXP 普通像素图层的正确 I/O 范式是**整文档读 + 整文档写**，选区外像素由"按掩码系数混合"来保留。不要用 per-tile 的 `putPixels`（会擦选区外像素并产生多次历史）。
- 需要邻域上下文的算法，环形邻域的"参考像素"应该独立于"修改掩码"——参考应是图像内容（alpha>0），修改才是用户意图（选区内）。否则小选区下算法因看不到上下文而失效。
- rate 留 0.9 的"保守"在用户期望"完全统一"的场景下会变成 bug；做"对齐/统一"类算法时默认 rate=1.0 更符合直觉，强度滑块作为用户入口控制强弱。

## 第九轮：alpha对齐彻底改用已验证的共享 I/O 流程（processPixelData + applyProcessedPixels）

**问题**：上一轮我自己重写了一套"整文档 getPixels → 手动映射 → 手动混合 → putPixels"的 I/O，结果仍是"有一次置入像素历史但无任何现象"。说明自己手写的 I/O 在某处坐标/映射上错了，不可靠。

**用户要求**：这个功能强依赖 Imaging API，必须参考**像素过渡（handlePixelTransition）等已验证可行的功能**的用法——得到选区内每个像素的 alpha → 计算 → 写入正确位置，三者缺一不可。

**改动（handleAlphaAlign 彻底对齐 handlePixelTransition 范式）**：
1. 用 `getSelectionData()`（内部已含稳健判选区 + 无选区自动 batchPlay 全选），不再用 `getSelectionBounds` + 手写掩码。
2. 用共享的 `processPixelData(selectionBounds, layer, isBackgroundLayer)` 读取像素（已验证）。
3. 用 `pixelResult.selectionIndices` + `selectionValues` 构建 `fullSelectionMask`（与像素过渡完全一致）。
4. **关键**：调用 `processAlphaAlign` 时传 `pixelResult.fullPixelData.buffer`（完整 alpha），**不是** `selectionPixelData.buffer`——这样环形邻域能引用选区外的线条像素找到"单线水平"；`fullSelectionMask` 只决定"哪些像素会被修改"。
5. 用 `applyProcessedPixels(processedPixels, pixelResult)` 写回（按 `selectionCoefficients` 羽化混合，选区外像素不变）。

**结论**：不要自己重写 I/O。这个项目里所有像素滤镜的统一正确范式是 `getSelectionData → processPixelData → 构建 fullSelectionMask → processXxx(selectionPixelData|fullPixelData.buffer, fullSelectionMask.buffer, bounds, params, isBackgroundLayer) → applyProcessedPixels`。需要邻域参考选区外内容时，把第一个参数从 `selectionPixelData` 换成 `fullPixelData` 即可（修改仍被掩码限制在选区内）。

## 第十轮：加诊断日志定位"仍无现象"（算法离线已验证正确）

**现象**：改成共享 I/O 流程后，用户仍反馈"有一次置入像素历史、无任何现象"；测试对象 260×477 的 X，线粗约 30px。console 能看到 `applyProcessedPixels` 的"映射回完整像素数组完成"。

**离线验证（关键）**：用 bash heredoc 写 Node 仿真（复刻 `processAlphaAlign`），模拟 260×477 两条 30px 半透明线交叉（线 alpha 150、交叉 225）：`[full] validCount=38299 changed=961 cross 225→150`，`[small] validCount=6820 changed=961 cross 225→150`。**算法本身正确**，交叉点能正确拉到单线水平。所以问题在 PS 环境里的数据链路（读 alpha / 选区掩码 / 写回），不在算法。

**做法**：在 `processAlphaAlign` 和 `handleAlphaAlign` 加诊断日志（带唯一标记 `alpha对齐 v2`），逐环定位：
- `✅ [alpha对齐 v2] 选区像素数=… 文档=… 选区=…` → 判选区是否为空（若 0 说明 getSelectionData 选区检测仍失败）
- `🔍 [alpha对齐] 选区内 fullPixelData alpha: 非零像素=… min=… max=…` → 判读到的 alpha 是否正确（半透明线应 max≈190-225；若 max=255 说明 getPixels 返回的是合成后不透明 alpha；若非零=0 说明读 alpha 为 0）
- `🔍 [alpha对齐] 尺寸=… validCount=…`、`修改像素数=…` → 判算法是否真正修改

**待办**：等用户回报 console 日志后定位具体环节（选区检测 / alpha 读取 / 写回）。构建已含标记（`grep "alpha对齐 v2" dist/bundle.js` = 1）。

**经验**：排查"算法看着对但没效果"时，先离线复刻纯算法跑合成数据确认算法正确，再在真实环境加带唯一标记的分步日志定位数据链路哪一环断掉；不要反复盲改。
