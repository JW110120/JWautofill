- ⚠️ 教训沉淀：**UXP 纵向 flex 里让子元素收缩出滚动条（min-height:0 路线）不可依赖**；需要「滚动区 + 固定区」时优先用 position: fixed 钉固定区、滚动区用整层 overflow。

## 第六轮：双滚动条根因定位（fixed 方案回退）

第五轮的 notify `position: fixed` 钉底**实测 notify 彻底不显示**（UXP 渲染不可靠）→ 用户明确反馈第四轮的 flex 三段结构 notify 位置是对的，只要去掉多余滚动条。

**双滚动条真正根因**（重新分析，非 flex 收缩问题）：
- 浮窗用 `max-height: 100%` 约束高度——浮窗是 `.float-overlay`（position:fixed + height:100%）的 **flex 子项**，UXP 对 flex 子项的百分比 max-height 解析不可靠 ⇒ 约束失效、浮窗按内容高度撑开 ⇒ **浮窗自身溢出滚动**（外侧那根）。
- 列表区被 flex 压到剩余空间 ⇒ 也滚动（内侧那根）。两根并存。
- ⚠️ 与第五轮判断相反：问题在 **max-height 百分比**，不在 flex 收缩能力。

修复（回到第四轮 flex 三段，仅换约束方式）：
- `.func-hotkey-window { height: 100%; overflow-y: hidden; }`——用 **height 而非 max-height**（overlay 有确定高度，height 百分比路径 UXP 支持），并禁止浮窗自身滚动 ⇒ 滚动只在 `.func-hotkey-body` 一层。
- `.func-hotkey-body { flex: 1 1 0%; min-height: 0; }` 双保险。
- notify 回到普通流（flex 子项，自然钉底），删除 `.func-hotkey-notify` 与 `.has-notify`。
- ⚠️ UXP 教训：**浮窗高度约束别用 max-height 百分比，用 height 百分比 + overflow 分配滚动层**；**position: fixed 钉底不可靠**（第五轮 notify 直接消失）。

## 第七轮：守护进程发布成功（长期停滞的发布问题定位）

用户确认全部功能达标后执行发布，**连续两次 publish 停滞 13 / 20 分钟无产物**。逐层定位：

## 第八轮：功能快捷键浮窗升级为「占满整个面板的子面板」+ 滚动条移到最外层

2. **铺满面板**：`.float-overlay.func-hotkey-overlay { padding: 0 }` + `.float-window.func-hotkey-window { padding: 10px 0; border: none; border-radius: 0; box-shadow: none; height: 100%; overflow-y: hidden; flex column }`。标题段/通知段各自 `padding: 0 26px 0 10px`（26 = 10 + 16px 滚动槽）⇒ 两者右缘与列表卡片右缘严格对齐。
3. **notify 恒可见**：`.func-hotkey-foot` 常驻（`flex: none`，不再随 `message` 条件渲染），只在内部切换 banner ⇒ 消息出现/消失时列表区高度不跳动。

- ⛔ `.float-overlay` / `.float-window` 的覆盖规则**必须写两级类**（`.float-overlay.func-hotkey-overlay`）：底色来自 `theme.ts` **运行时**注入的 `.float-overlay{background}`，而 `adjustment.css` 走 style-loader **也是**运行时注入 ⇒ 同为 (0,1,0) 时注入先后不确定，靠源码顺序决胜不可靠。（与既有「common.css 静态 link vs app.css style-loader」那条同源。）

## 第十一轮：修复「激活与试用」面板首次加载时 number 输入穿透（双根因）

**现象**：初次加载时授权面板出现，但其下方的 number 输入（不透明度 / 羽化）错误叠加显示在面板之上；
自动加载本地 license、面板消失后，再次点击入口唤出同一面板则正常。

**根因一（时序/状态层）**：`license-dialog-open` body 类由 `componentDidUpdate` 的
`if (state.isLicenseDialogOpen !== prevState.isLicenseDialogOpen)` 判断添加，而
`types/state.ts` 里 **`isLicenseDialogOpen` 初始值就是 `true`** ⇒ 首次加载时 prevState === state
⇒ `!==` **恒假** ⇒ 类永远加不上。再次点击入口时 state 由 false→true，`!==` 成立 ⇒ 类正常加上。
**这就是「首次有 bug、再次正常」的全部原因**（不是布局/图层顺序/测量缓存问题 —— 用户猜测的方向不对，
真实机制是「以初始值作比较基线的差异判断，对「初值即目标态」永远失效」）。

**根因二（CSS 选择器层）**：即使类加上了也照样穿透。`input-fix.css` 里 `license-dialog-open` 的
隐藏规则**逐个列举容器类名**（`.slider-container` / `.collapse-content` / `.collapse-content-expanded` /
`.row-between`），而「不透明度 / 羽化」的 number 实际走在 `.row-start > .num-input-row` 里
—— **不属于任何一个被列举的容器** ⇒ 漏网。工具箱侧的 `body.adjustment-lock-open` 早就写成
「全部后代 input」的宽范围，反而是对的。

**修复**：
1. `src/app.tsx`
   - 新增 `syncLicenseDialogClass()`：**渲染期由 state 单向派生**（先读实际类、再按目标态 add/remove，幂等）。
   - `render()` 开头调用它 ⇒ 每次渲染都对齐，覆盖「首次加载 / 自动激活后 / 注销后重开」全部路径。
   - 删除 `componentDidUpdate` 里的 `!==` 判断块，以及 `handleLicenseVerified` /
     `handleTrialStarted` / `closeLicenseDialog` / `openLicenseDialog` 里 4 处手动 add/remove。
   - `componentWillUnmount` 里的清理**保留**（卸载时该清）。
2. `src/components/LicenseDialog.tsx`：删掉组件内 `[isOpen]` effect（它的 cleanup 会在卸载时
   无条件 remove，与父级派生式互相覆盖；且首次挂载时机不可靠）。
3. `src/styles/input-fix.css`：`license-dialog-open` 的 10 条列举式选择器 → **3 条后代选择器**
   （`#app .app-root > .panel` 下的 `input` / `textarea` / `sp-textfield`）。

**泛化铁律**：
- ⛔ **「用 `prev !== next` 判断状态变化来施加副作用」对「初始值即目标态」的场景永远失效** ——
  副作用必须**由状态派生**（渲染期幂等同步），不能以「差异」为触发条件。
- ⛔ **「弹层打开时隐藏穿透控件」的 CSS 不要逐个列举容器类名** —— 后代选择器才是与语义等价的范围；
  逐个列举必然漏掉后来新增的容器（本仓 `.row-start` 就是这样漏的）。
- ⚠️ 两块面板共用 `document.body`，改 body 类必须按面板限定作用域，否则串扰（既有铁律，本次沿用）。

## 第十二轮：修复专注模式与功能快捷键面板的状态不同步（首次加载显示「选区填充开关」）

**现象**：应用首次加载且已处于专注模式时，功能快捷键子面板里那条仍显示「选区填充开关」，
应为「选区填充」；切一次专注模式后就正确了。

**根因 A（主因，订阅侧）**：`FocusModeBus.subscribeFocusMode` 用**模块级共享 `cached`** 给去重基线播种：
```ts
let last: boolean | null = cached?.focus ?? null;   // ⛔ 播种
```
两个面板（`#app` 与 `#pixeladjustment`）在**同一个 HTML 文档、同一个 JS 上下文**里（`src/index.html` 第14/18行，
`index.tsx` 里两个 `createRoot` 同属一个 bundle）⇒ `cached` 是**跨面板共享**的。
启动时 App 把 `focus:true` 写进 `cached` → 用户**之后**才打开工具箱子面板 → 播种得 `last=true`
→ 首次 `tick()` 读文件也是 true → 「值没变」⇒ **回调永不触发** → `FuncHotkeyPanel` 的
`useState(false)` 初值成为最终值；后续轮询值一直相同 ⇒ **永久错误**。
这正好解释「切一次就对」：那时值真的变了，回调才被触发。
修复：`last` 恒从 `null` 起（新订阅者保证收到一次当前值）；`readRaw()` 返回 null 时**本轮不表态**
（直接 return，不更新 `last`）——文件不存在 ≠ 专注模式关闭，硬推 false 会把订阅方从 true 拽回 false。

**根因 B（伴生，写入侧时序）**：`app.tsx` 启动期在 `setState` 之后紧跟 `syncFocusMode()`，
而它读 `this.state`。React 19 自动批处理下此刻 `this.state` 仍是**默认 `false/false`**
⇒ 把 `false` 写进共享文件、**覆盖上次会话留下的 `true`**，之后才由 `componentDidUpdate` 纠回。
中间窗口里 `MainToggleBus.readFocusMode()` 读到 false ⇒ 主开关热键短暂失去「只开不关」的专注模式语义；
且每次启动多一次文件写。修复：`syncFocusMode(explicit?: boolean)` 支持显式传值，
启动期传「合并后两个前置选项」算出的 `focusAfterMerge`（合并规则与 `setState` 里逐字一致）。

**顺带消除首帧闪烁**：`FuncHotkeyPanel` 的 `useState(() => peekFocusMode() ?? false)`。
新增 `peekFocusMode(): boolean | null` 返回内存真值（**null = 未知，区别于确定为 false**），
利用「两面板共享模块实例」让初值一次就对，不靠首次回调纠正。

**改动文件**：`src/utils/FocusModeBus.ts`、`src/app.tsx`、`src/hotkey/FuncHotkeyPanel.tsx`

**验证场景（新增台架 `analysis/focus-mode/repro.mjs`，16 断言全通过）**：
用项目自带 tsc 就地转译 FocusModeBus.ts + 内存版 UXP localFileSystem 跑**真实代码**，6 个场景：
① 启动即专注模式→子面板首次唤出必须收到 true（主因）② 切换专注模式双向反映（回归）
③ 文件缺失→之后出现不得被拽成 false ④ peekFocusMode 的 null 语义 ⑤ 写入幂等+值变确实落盘
⑥ readFocusMode/peek 一致性、文件消失回落最后已知值。
**对照实验（关键）**：`node analysis/focus-mode/repro.mjs <旧版路径>` 跑修复前源码 ⇒
场景 1 回调序列 `[]`（失败）、场景 3/4 亦失败，而场景 2 全通过 —— 既证明台架有鉴别力，
也再次印证「首次有 bug、切换后就对」的现象出自根因 A。

⛔ **新增泛化铁律**：**订阅/轮询类回调的「去重基线」绝不能用跨上下文共享的缓存播种**——
必须从「未知」起，保证新订阅者至少收到一次当前值；否则「值恰好相同」会让订阅方永久停留在
错误的初值上，且后续轮询永不纠正（与本轮已修的 license-dialog `prev!==next` 属同一族：
**用「差异/去重」作触发条件，对「初值即目标态」永远失效**）。
⚠️ 台架纪律：**每个场景必须独立模块实例**（模块级 `cached`/`writeChain`/`memListeners` 跨场景共享会造假失败）；
内存 FS 必须实现 `folder.createFile`（缺了会被源码 `catch` 吞掉、只更新内存不落盘，误报「值变了但文件没变」）。

**构建**：`webpack --mode production` 通过（仅 3 个既有体积警告）。

### 根因（结构性，唯一支点）
整套防护只有一个结构性支点：`psAccess.psTryRead()` 的**第 ① 分支**

```ts
if (isInOwnModalScope()) { ...await fn()... }   // ← 直读＝裸 get，不经过 executeAsModal
```

它的判据最终是 `core.isModal()`。本机运行时核实（`Required/UXP/app.js`）：

```
e.isModal = function isModal(){ return getCoreModules().photoshopCore.isModal() }
```

只是转发到**原生绑定**，无 JS 实现 ⇒ **语义无法静态确认**。Adobe 文档措辞是
"the plugin is currently in a modal state"；但社区现场结论相反（Adobe 开发者论坛
2025-10-09「executeAsModal when refreshing UI?」，症状与本用户**逐字相同**：

> "I've got a setInterval going every 500ms ... occasionally at random (usually when
>  Photoshop is saving/flattening/opening) it brings up an error window: **'The command
>  "Get" is not currently available.'**"
>
> Jarda 回复："you could also run get action only when there is no modal state. But
>  **not only your plugin can start modal state and it is not easy to find out.
>  Built-in method does not work as expected.**"

⇒ 若 `isModal()` 在本插件**未**持有模态作用域时也可能为 true（把宿主/其它插件的模态态算进来），
则第 ① 分支会在**最需要保护的瞬间**把「受保护读取」退化成「裸 get」——这正是弹框来源。
而且它同时会**污染闩锁出口**：`probeHostIdle()` 第一句就是 `if (isInOwnModalScope()) return true;`
⇒ 闩锁会在宿主仍忙时被判「已可控」而提前释放，这正是「打开/关闭大文档始终高频弹框」的另一半。

**为什么「单次删除」比想象的更脆弱（delete 特有的不对称）**：
- `delete` **不在** `isDocLevelDescriptor` 里（只认 open/close/save/saveAs/select+document）
  ⇒ 只打 `QUIET_AFTER_EVENT_MS`(300ms) 短窗口，**不开启文档级闩锁**；
- `noteHostUnresponsive()`（作废「宿主可读租约」）只在 `beginDocLatch()` 里被调
  ⇒ **delete 不作废租约**；稳态下 3 个 300/500ms 轮询让 `hostOkStreak` 长期 ≥2、
  `lastHostOkAt` 永远新鲜 ⇒ `canSyncReadHost()` 实际退化成只看 `isPsBusy()`。

### 判别实验（决定性）：只改宿主模型一行
`outputs/isModal_semantics_probe.cjs`（真实源码 transpile + 三配置对比，其余一字不动）：

### 修复建议（两阶段，阶段一可立即止血）
- **修复 1（根治，必做）**：新增 `psAccess.runAsModal()` 作为**唯一**进入模态的入口并维护
  `ownModalDepth`；写路径（填充/描边/蒙版同步/ClearHandler/SingleChannelHandler/各 processor）
  的 `core.executeAsModal(` 改为 `runAsModal(`；随后 `isInOwnModalScope()` 改为**只看
  `ownModalDepth > 0`**，彻底不再采信 `core.isModal()`。
  ⛔ 不要只把 `if (isInOwnModalScope())` 改成 `if (readonlyDepth > 0)`：写路径直接调
  `core.executeAsModal` 不经过 psTryRead，`readonlyDepth` 为 0 ⇒ 会误拦、把填充打哑。
  ⛔ 也不要给直读分支加 `&& isPsBusy()` 前置条件：`isPsBusy()` 在窗口到期后已为 false，
  判不出「宿主仍忙」（本轮已实测：配置 3 第一版这么写，弹框数与配置 2 完全相同）。
- **修复 2（止血，独立成立）**：同步接口**永不遍历**——`getLayerSnapshot()` 的
  `if (!canSyncReadHost()) return cached;` 改为无条件 `return cached;`（或删除同步遍历路径），
  `MaskSyncEngine.buildLayerTree` 的裸兜底 walk 直接删掉（返回 `[]`）。
  理由：同步遍历是**乘法放大器**（一棵 16 层的树 = 80 次裸 get）。去掉它以后，
  上游判据再错，最坏也只是「数据旧」，不会变成「一屏原生弹框」。
- **修复 3（不对称补齐）**：`markPsBusyForEvent` 的**非**文档级分支也调
  `noteHostUnresponsive()`（作废租约）。理由：一次 delete 就是「宿主刚忙过」的证据；
  代价只是同步裸读多退避 800ms（而它本就该只读缓存）。同时给 `delete` / `make` / `move`
  这类结构事件开一段**短闩锁**或提高其窗口，堵住「命令尾部不可观测」的盲区。
- **修复 4（残余缺口收口）**：`HotkeyBridge.getSelectedBrushToolEnum()` /
  `getSelectedBrushNameId()` / `enumerateBrushes()` 本体仍是裸 `batchPlay get`，
  应各自包 `psRead`（或全部调用点收口）；`enumerateBrushes` 的启动首刷重试循环
  （`INITIAL_LOAD_ATTEMPTS=3`）**每轮之间没有复查 `isPsBusy()`**。
- **修复 5（顺手）**：`psTryRead` 在 `await spaceModalEntry()` **之后**没有复查 `isPsBusy()`
  —— 粗筛是在 `await sleep(gap)`（最长 300ms）**之前**判的，期间可能已收到 delete 通知。

## 第二轮（同日 20:1x）：`runAsModal` 三缺陷（真机三类 BUG 的根因）

详细报告：`outputs/modal-runasmodal-fix.md`；守卫：`node outputs/_modal_contract_guard.cjs`。
三个 BUG **不是同一个 bug** —— 是两个独立缺陷 + 一个事件覆盖缺口。

### Bug 1（缺陷 A）· 描边彻底失效 / 取色器失效
- **根因**：`runAsModal` 把 `opts` **无条件**作为第二实参传下去：
  `core.executeAsModal(wrapped, opts as any)`。`opts` 为 `undefined` 时**第二实参位仍被占用**，
  UXP 原生绑定对「显式 undefined 的 object 形参」严格校验 ⇒ 抛
  `Argument 2 has an invalid type. Expected type: object actual type: undefined`。
- **命中面（实测清点，写脚本扫的：`outputs/_modal_callscan.cjs`）**：全仓 24 个模态入口调用点，
  其中 **11 处不传 opts** —— `StrokeSelection.ts` 8 处（**每一条描边分支**的「保存前景色」步骤）、
  `ColorPicker.ts:32/49`（capture / apply 前景色）、`AdjustmentPanel.tsx:849`（还原特殊木刻基线）。
- **症状吻合度**：日志 `✅ 新建图层成功` → `❌ 普通描边失败: Argument 2 …` —— `make layer` 是
  step1（batchPlay，成功），step2 就是那处 `executeAsModal(fn)`。⇒ 12 组合里 3「仅描边」
  + 3「清除+描边」全挂；「仅清除」不进描边所以**本身生效**（但把缺陷 B 的模态放大暴露出来）。
- **修复**：实现分岔 `opts == null ? executeAsModal(wrapped) : executeAsModal(wrapped, opts)`。
  **修实现、不修 11 个调用点**（`executeAsModal(fn)` 是合法 API 用法）。

### Bug 2（缺陷 B）· 关闭图案/渐变子面板报「监听器注销失败」
- **根因**：`wrapDocLevelLogger(handler)` **每次都返回新闭包**，而 `add` 与 `remove` 各自调它一次
  ⇒ 注册用的引用 ≠ 注销用的引用。`removeNotificationListener` 按**引用**匹配 ⇒ 找不到目标
  ⇒ 抛 `Notifications could not be registered`（真机日志里 16 个事件名逐个失败，栈顶
  `psAccess.ts:132` ← `PatternPicker.tsx` / `GradientPicker.tsx` 的 cleanup）。
- **后果不只是刷屏**：子面板按 `[isOpen]` 挂载/卸载 ⇒ 每开合泄漏 16 个永不注销的回调 ⇒
  **此后每条 PS 通知被全部残留回调处理** ⇒ 事件驱动刷新（→ `psTryRead` → `executeAsModal`）
  随开合次数**累加**。这是本仓**唯一「无上限累加」形状**的模态命令放大器，与用户
  「Too many modal scope commands」红色计数 **153 → 240+ 持续上涨** 的形状一致。
- **修复**：`WeakMap` 按 handler 记忆化包装器（add / remove 恒拿同一引用）。

### Bug 3（缺陷 C）· 转换为智能对象偶发「命令"获取"当前不可用」
- **根因**：本仓口径下**事件名 == 描述符 `_obj`**（真机 `收到事件: set` / `📂 [PS事件] open` 一致）。
  「转换为智能对象」的通知描述符是 `{_obj:'newPlacedLayer', _isCommand:false}`，
  **不在 `PS_NOTIF_EVENTS` 里** ⇒ 该重命令**全程无忙碌窗口**（与 `open`/`close` 的历史缺口
  = 根因 R2 完全同型）⇒ 轮询读取照常发起 ⇒ 有几率撞宿主模态 ⇒ 原生弹框。
- **为什么按文档级**（而不是结构类 600ms）：宿主执行该命令内部要「新建临时文档 → 合成 → 置入
  → 关闭临时文档」，与 open/save 同型（自己握模态、可能数秒），常数窗口堵不住尾部盲区。
- **修复**：`psProbe.PLACED_LAYER_EVENTS`（`newPlacedLayer` + 同族 4 名）展开进 `PS_NOTIF_EVENTS`；
  `markPsBusyForEvent` 命中即 `beginDocLatch()`（**不**推进世代号 —— 文档实例没换）；
  包装器加零噪声日志 `🧩 [PS事件] newPlacedLayer` 供真机确证事件名。

### 验证
- `tsc --noEmit -p tsconfig.json` 过滤 `src/` ⇒ **0 错**（`@types/node` 基线 142 条与本改动无关）。
- `webpack --mode=production` ⇒ 通过（仅 size 警告）。
- 新增守卫 `outputs/_modal_contract_guard.cjs`（G1-B / G2-A / G2-B / G3-A / G3-B）⇒ **全绿**
  （G1-A 是「不传 opts」的知情清单，只打印不判失败 —— 不传 opts 本身合法，缺陷在实现）。
- 仍待真机：描边/取色器恢复、开合子面板不再报注销失败且告警计数不再上涨、
  `🧩 [PS事件] newPlacedLayer` 是否出现（不出现 ⇒ 事件名不对，需换名/用 Alchemist 录真机名）。

## 描边色板拾色器 · 灰色态初值缺陷（缺陷 D，2026-10-09 修复）

- **现象**：色 #b34d4d，开清除模式 → 色板灰成 #6b6b6b（0.299/0.587/0.114 ⇒ 107=0x6b，口径正确）。
  直接关清除模式 ⇒ 恢复 #b34d4d ✅；但若**先点开拾色器再关**，色板**永远停在 #6b6b6b** ✗。
- **根因**：`app.tsx` 的 `openStrokeColorPicker` 把 `this.getStrokeDisplayColor()`（**灰态下返回灰度值**）
  当成 PS 拾色器初值 ⇒ ① 打开即灰；② 用户确认后 `setState({strokeColor: picked})` 把**灰度写回真实色**
  ⇒ 原色永久丢失（灰态本应只影响显示）。这就是「先点开就不恢复」的机制。
- **为什么只有描边板**：渐变板 `GradientPicker.tsx` 的 stop 拾色器传的是 `parseCssRgb(stop.color)`
  （stops 从不灰化 = 真实色）⇒ 本来就正确。
- **修复**：`openStrokeColorPicker` 初值改取 `state.strokeColor`（真实色）；
  新增守卫 `outputs/_color_picker_contract_guard.cjs`（G1 全仓禁「显示色当初值」/ G2 限 `getStrokeDisplayColor`
  仅显示用途 / G3 两个调用点初值 + 数量稳定）⇒ 全绿。
- **同步修正**：`refs/fill-and-stroke.md` 原写「面板显示色 ↔ 拾色器初值必须同源（`getStrokeDisplayColor()` 是唯一事实来源）」
  —— 这条正是缺陷来源，已改为「拾色器初值 = 真实色；同源指同一个真实色，不是把显示值喂给拾色器」。
- **验证**：`tsc --noEmit` 过滤 `src/` ⇒ 0 错；`webpack --mode=production` ⇒ 通过（仅 size 警告）；
  守卫全绿。待真机：灰态下开拾色器应显示 #b34d4d，确认后退出灰态仍为 #b34d4d。

## 「宿主模态冲突」告警语义（用户提问，2026-10-09 解释）

- `⚠️ [PS访问失败] 读取X：宿主模态冲突（完整面包屑：控制台执行 __jwPs.dump()）` 由
  `psAccess.markPsAccess(label,'fail')` 发出（`psTryRead` catch 分支，`isHostModalError` 命中时）。
- 含义：插件要进 `executeAsModal` 做保护性读取，但**宿主（PS 自己/其它插件）正握着模态作用域**
  ⇒ `executeAsModal` 被拒（`error.number===9` 或消息含 `modal`）⇒ **设计内的「受控退避」**，
  不是崩溃：作废宿主租约 + `extendDocLatch()` 让所有读取一起退避，返回 `{ok:false}`。
- 触发场景：宿主自己跑 open/close/save 大文档、合并/拼合/删除、原生对话框开启、其它插件持锁。
- 该告警**1s 节流**；排查用 `__jwPs.dump()`（最近 60 条面包屑）/ `__jwPs.state()` / `__jwPs.trace(true)`。
- 设计要点：这正是「原生『命令"获取"当前不可用』弹框」的替代品 —— 曾经命中 message 就降级裸读，
  反而越兜越弹；现在失败即失败。
