# 2026-10-08 工作日志

## 选区纯色填充 0.5s 延迟定位与优化

### 背景
用户反馈：生成选区后需等约 0.5 秒颜色才填充完成。测试机为低配（Ryzen 5 3400G +
Vega 集显、16GB），目标是在低端硬件上接近即时响应。

### 根因定位（关键结论：不是像素遍历）
纯色填充路径**没有 JS像素循环**——颜色写入是 PS 原生 `fill` 命令
（`FillHandler.createBasicFillCommand`），由宿主多线程完成，耗时仅几毫秒。
0.5s 几乎全部来自 **① 300ms 人为固定等待 + ② 约 67 次串行同步 IPC 往返**。

逐环节拆解（默认配置：纯色/无羽化/无选区改造/无描边/autoUpdateHistory 开/deselect 开）：

| 环节 | 位置 | 同步 IPC |
|---|---|---|
| 忙碌闸门固定顺延 300ms | `app.tsx` handleSelectionChange + `psProbe.BUSY_AFTER_EVENT_MS` | 硬等 300ms |
| 外层 activeDocument + quickMaskMode | 外层 | 2 |
| 外层 getSelection | | 1 |
| 模态内**重复** getSelection | | 1 |
| `doc.historyStates`（整条历史数组）判空 | setHistoryBrushSource | 1 |
| `getActiveLayerInfo()` | LayerInfoHandler | **~18** |
| `fillSelection` 内**又一次**单通道判定 | | ~7 |
| 图层可见性 + foregroundColor | | 3 |
| fill + deselect 两次下发 | | 2 |

`getActiveLayerInfo` 单次 18 次的成因：`checkSingleColorChannelMode` 内部
**又完整调了一次** `checkLayerMaskMode`，两次的「取 mask 通道」全部重跑；
且 `checkLayerHasPixels` 对 `bounds` / `bounds.width` / `bounds.height` 各读一次。
填充后紧随的面板巡检还会再调 2 次 `getActiveLayerInfo`（每次 ~18）。

## 复核：性能改动是否破坏「切文档 / 快速删图层」的弹框防护

用户要求逐项核对本次改动与既有防护的关系。**复核中发现 2 个我自己引入的真实缺陷，均已修复。**

### 缺陷①（严重，已修）删除风暴末事件把忙碌窗口压到 60ms
「快速连续删除图层」时 PS 会交替派发 `delete` 与 `set`（删图层连带改选区），
`MaskSyncEngine.NOTIF_EVENTS` 含 `set`、app 的选区监听器也只监听 `set`。
⇒ 若风暴**最后一个**事件恰好是选区 `set`，整场删除的 300ms 窗口会被 60ms 覆盖
⇒ 宿主仍在忙⇒ 重新弹「命令"获取"当前不可用」，**正是 2026-10-07 修过的 bug**。

修法（`psProbe.ts`）：加 `lastLongEventAt` + `LONG_EVENT_NEIGHBOR_MS = 600`。
**只要最近 600ms 内发生过任何非选区事件，选区事件就并入保守窗口。**
不影响性能：删除/合并是低频、不在实时性关键路径；纯套索连点仍走 60ms 快路径。

### 缺陷②（中等，已修）背景图层的hasPixels 被误判为 false
我把 `readLayerDomInfo` 写成 `const bounds = isBackgroundLayer ? null : activeLayer.bounds;`
⇒ 背景图层 `hasPixels` 恒为 false。而 `hasPixels` 是 app.tsx 里
`hasTransparencyLocked && hasPixels` 的分支判据（6 处消费，含 PatternFill/GradientFill/
SingleChannelHandler/StrokeSelection）⇒ 背景图层会误走 `fillLockedWithoutPixels`
（多两次 applyLocking，可能改写用户的锁定状态）。旧 `checkLayerHasPixels` 对所有图层一视同仁。
修法：去掉这个 background 特例，背景图层照常读 bounds。

### 确认无影响的部分（逐项核对过）
- **切文档**：`selectionChangeListener` 只注册 `['set']`，doc-switch 的 `select` 事件
  **不会**进入 `handleSelectionChange`；`isDocSwitchDescriptor` 分支与 1200ms 完全未改。
- **忙碌窗口并集**：`markPsBusy` 是 `Math.max`，短窗口**永远无法缩短**长窗口。
  已写 `/tmp/busy_union_test.cjs` 穷举 5 种事件顺序验证（select1200→set60、
  set60→select1200、delete300→set60、set60→delete300、单独 set60），结果全部正确。
- **事件订阅/解绑**：未新增/删除任何 `addNotificationListener`；
  `componentWillUnmount` 原有清理全保留，仅追加 `selectionRetryCount = 0` + 缓存失效。
- **循环 import**：`LayerInfoHandler` 只 import `photoshop`，不反向引用 MaskSyncEngine ⇒ 无环。
- **通知回调内零 IPC**：`invalidateLayerInfoCache` / `shouldInvalidateLayerInfo`
  都只碰模块级变量与 descriptor 字段，无 DOM / 无 batchPlay ⇒ 符合「回调内唯一允许纯内存」的既有铁律。
- **空引用**：`layer.id` 已验证有效（`layerTreeSnapshot.ts:144` 同样在用）；
  `doc.id` 我反而去掉了（改用全局唯一的 layer.id），少一次 IPC。
- **重复绑定**：无。

## 【真机实测反馈】我上一轮的「复核结论」是错的 —— 用户实测报了 4 类新问题

用户实测反馈（11:23）：
1. 快速删除多个图层，超过某个速度**必报错**
2. 快速删图层后立刻套索**必报错**
3. 切换文档（含新开/关闭导致的自动切换）**有几率报错**；首次切换报错，之后速切不报错，
   但关闭再打开文档来回切又报错
4. **新引入**：快速蒙版下三种填充模式**全部报错**（之前没有）
5. 背景图层正常；开启清除模式会弹出**PS 原生描边对话框**，要求静默

### 真正的根因（我上一轮完全没想到）

**我缩短的是 `isPsBusy()` 这个「全局共享闸门」，它有 9 处消费者：**
`pollQuickMask`(300ms 轮询) / `pollToolChange`(300ms 轮询) / MaskSyncEngine 的
2s 轮询 + 两处同步入口 / AdjustmentPanel 探测 / `debouncePsProbe` / `runWhenIdle`
/ `handleSelectionChange`。
⇒ 把选区事件的全局窗口从 300ms 压到 60ms，等于让**那 9 处轮询/探测在 PS 仍忙碌时提前放闸**，
它们集体发 `get` ⇒ 宿主弹「命令"获取"当前不可用」。
四种症状全部由此而来（快速蒙版尤其明显：它持续派发选区 set ⇒ 闸门被反复压到 60ms）。

⚠️ **我的「邻居护栏」（`lastLongEventAt`）只护住了填充路径自己，护不住那 9 处轮询** ——
这就是为什么我"逐项核对过"却仍然漏判：我核对的是「填充路径会不会发 get」，
**没核对「缩短窗口后，别的消费者会不会提前发 get」**。

### 解法：全局闸门与填充冷却**解耦**（最终形态）
- `markPsBusyForEvent` **恢复两档、且选区事件也用 300ms**（不再有 60ms 档）；
- 新增 `fillReadyRemain()`：只给填充路径用的**私有冷却**（60ms），
  且「最近 600ms 有过任何非选区事件（含**切文档**）」时**自动退回全局剩余时间**；
- 切文档事件**必须**同时记 `lastLongEventAt`，否则「切文档→立刻套索」会走 60ms 快路径
  而撞上 1200ms 窗口（我第一版私冷却就漏了这条，靠场景断言才发现）。

⚠️ 同时修掉falsy 陷阱：`lastLongEventAt = 0` 是 falsy ⇒ `if (lastLongEventAt && …)` 短路
⇒ 保护在时刻恰为 0 时失效。改用 `-1` 哨兵 + `>= 0` 判定。

### 快速蒙版报错的根因（合并 batchPlay 的副作用）
`probeChannelState` 原本把「取 mask 通道」与「取目标通道」**合并进同一个 batchPlay 数组**。
快速蒙版下 `get channel mask` 会失败 ⇒ **第一条失败连带整批失败**，而宿主对失败命令的
原生报错框**绕过 JS try/catch** ⇒ 图案/渐变面板的灰色预览（也要调 getActiveLayerInfo）
与三种填充全部报错。
**修法**：① 快速蒙版下**跳过 mask 通道 get**（此时 `isInLayerMask` 本就无意义）；
② 两条 get 改回**分开下发**，各自 try/catch，恢复「一条失败不影响另一条」的语义。

### 清除模式弹原生描边框
截图是 **PS 原生「描边」对话框**（确定/取消/位置/混合），不是我们的子面板。
根因：`StrokeSelection.ts` 只在**描述符内**写了 `_options.dialogOptions`，
而 **batchPlay 的 options（第二参数）没写**；`stroke` 命令在
`mode = clearEnum` 下会忽略描述符内的 `_options` ⇒ 弹原生框。
**修法**：该文件全部 16 处 batchPlay 的 options 补`dialogOptions: 'dontDisplayDialogs'`。

### 沉淀：新增核对台 `outputs/gate_verify.cjs`
用 `ts.transpileModule` 加载**真实 psProbe 源码**（掐掉 photoshop import），
注入可控时钟，逐场景断言「填充等了多久」+ 不变量 `fillReadyRemain() ≤ psBusyRemain()`。
7 个场景全部通过。**这类回归编译不报错、类型检查不报错、UI 看不出来，只能靠场景断言。**
重点是删除风暴末事件、后台大文档套索、面板重载后的监听器状态。

## 修复：拾色器初始色 + 快速蒙版清除+描边色失效（同日 14:5x）

### 现象一：色板显示 A，拾色器打开成 PS 前景色 B

- **根因**：`showColorPicker` 是**无参**命令，描述符里没有任何「初始色」字段，
  PS 一律以**当前前景色**为初始值。旧代码在两处（`app.tsx:openStrokeColorPicker`、

  记下真前景色 → 把前景色设成 `initial`（HSB）→ 打开 → 读结果 → **finally 里还原**。

### d 的根因（**一处**，跑全 11 组）—— 回归，非新缺陷
`LayerInfoHandler.probeChannelState()` 里：
```js
const activeChannelsCount = doc0?.activeChannels?.length || 0;   // ← 图层蒙版激活时**抛异常**
if (activeChannelsCount > 1) return result;
```
**PS 在图层蒙版激活时读 `doc.activeChannels` 会抛 `Unknown or unsupported active channels`**
（Adobe 官方论坛 "Better way to see if a mask is active" + 旧版 ExtendScript 讨论均确认：
「图层蒙版被选中时访问 activeChannels 会抛异常」）。
该异常逃逸到 `probeChannelState` 的**外层** catch ⇒ 直接 `return {inLayerMask:false, inSingleChannel:false}`
⇒ **`isInLayerMask` 恒为 false**。
⚠️ **旧实现本就把这段包在内层 try/catch 里**（`checkLayerMaskMode` 内独立 try/catch，异常被吞掉后继续比对通道名）；

## 真机修复：普通像素图层完全不生效 + 背景图层选区外变白 + 内容错位（已改码，构建通过）

### 根因（全部来自 `@adobe-uxp-types/photoshop` 的 `ImagingModule.d.ts` 逐条核对，非推测）
1. ⛔⛔ **`getPixels` 的选项名是 `sourceBounds`，不是 `bounds`**。旧 `readLayerPixels` 传了 `bounds`
   —— 该字段在 `GetPixelsOptions` 里**不存在** ⇒ 等于没传 ⇒ PS 按「整个图层」取值，再用
   `targetSize`（= 选区外接矩形尺寸）把**整层重采样**进选区大小。写回后 = 整幅画面被压进选区
   ⇒ 用户看到的「选区外变白 / 内容错位 / 第二次更严重」。
   （本仓 `smartEdgeSmoothProcessor.ts` 头部注释早已记录过这个坑，本次是**同一坑第二次踩**。）
2. ⛔⛔ **`applyAlpha: true` 会把 RGBA 按白底压成 RGB**。官方原文：「If true, then RGBA pixels will be
   converted to RGB by **matting on white**. The returned imageData property will **not contain an
   alpha channel**.」旧代码写的是 `applyAlpha: !isBackground` —— 恰好对**普通像素图层**（唯一需要
   α 的目标）开了它 ⇒ 拿到 3 分量 ⇒ α 分支判 `components < 4` 直接跳过 = 那条 UXP 警告。
   正确做法：**一律不传** `applyAlpha`（默认 false ⇒ α 原样保留；背景图层本来就返回 RGB）。
3. ⚠️ **必须回读返回值里的 `sourceBounds`**：PS 会把请求区域**裁剪**到「真有像素」的范围
   （空白图层 / 局部图层），只有它就是数据真正覆盖的矩形。用请求值当地图 = 整体错位。
4. ⚠️ **不要传 `targetSize`**（不请求缩放才能 1:1）、**不要传 `colorProfile`**
   （读写都走文档工作空间才往返恒等；指定 sRGB 会两侧各转一次、留舍入残差）。

### 改法（`src/utils/ClearHandler.ts`）
- 新增模块级 `interface LayerPixelBlock { data, components, left, top, width, height }`

- `readLayerPixels(bounds, layerId)` 改为：请求区域 = 选区外接矩形 ∩ 文档（floor/ceil 取整），

## 清除模式 · 第二轮真机修复（普通像素图层 / 背景图层「选区外整层变透明/变白」）

用户报告：① 普通像素图层清除仍会把**选区外整层像素变透明**；② 背景图层同样，且要求改为
「先解锁 → 清除 → 再转回背景图层」（附真机监听的 `set layer.background` / `make backgroundLayer` 描述符）。

### 根因（不是算法，是 `putPixels` 的默认值）
官方文档 `putPixels` → `replace` 原文：
「If true, then existing pixels in the layer are **discarded** before adding new pixels. …
**The default value is true.**」
⇒ 第一轮虽然把 `sourceBounds` / `applyAlpha` / 返回几何都修对了，但**写回仍是「选区外接矩形 +
`targetBounds`」**，而 `replace` 缺省为 true ⇒ PS 的语义是**「先把整层内容清空，再把这块数据放到
targetBounds 处」**。选区外的整层像素因此被清空：普通图层→透明；背景图层不能透明→被 PS 按背景色
**填成白色**。两个症状同一个根因，与像素算法完全无关。
（本仓 `MaskSyncEngine` 头部第 3 条早就写过「局部写 `targetBounds`+`replace:false` 不可靠 ⇒ 改用整图写回」，
`pixelDataProcessor` / `knockoutBatchProcessor` 的写回也都是整图 —— 这一轮等于把这条铁律重新挖出来。）

### 修法（`src/utils/ClearHandler.ts`）
- 新增 `DocumentPixelBlock`：**文档全尺寸**写回缓冲（不是图层边界、也不是选区外接矩形）。
- `readLayerPixels(layer)`：按 `layer.boundsNoEffects` 读（不再按选区读，否则会漏掉「有像素但在选区外」
  的部分），`targetSize` 与请求同尺寸声明不缩放；数组形状取 `imageData.width/height`（dispose 前读），
  原点取返回的 `sourceBounds.left/top`；分量数既非 3 也非 4 ⇒ 返回 null。
- 新增 `expandToDocument(block, bounds)`：把图层像素块摊平成文档全尺寸缓冲，图层没像素处保持全 0
  （透明），越界自动裁剪并 warn。
- `writeLayerPixels(docBlock, layerId)`：**不传 `targetBounds`**（官方：不传即 insert at origin (0,0)），
  也不传 `replace`（默认 true = 整层被这份缓冲完整替换）。选区外字节 = 读出的原值 ⇒ 严格恒等。
- `applyBackgroundClear` / `applyLayerAlphaClear`：改成直接按**文档坐标**下标（`docY*width+docX`），
  不再有任何「块内偏移」环节；背景族只动 R/G/B、alpha 恒 255。
- 背景图层：新增 `unlockBackgroundLayer(layerId)` / `lockBackgroundLayer()`（描述符逐字取自用户真机
  监听，只把记录里的 `layerID: 4` 换成运行时 id）。还原写在 `finally`，且还原前校验活动图层 id 未变
  （描述符打 `targetEnum`，防止误把别的图层转成背景图层而不可逆毁掉其 alpha）。
- 顺带：`transparentPixelsLocked` 的读取挪到图层类型转换**之前**（转换后旧代理可能失效），并单独 try/catch；
  「自动删选区」的还原改为**无条件执行**（原先若「无像素可改」提前 return 会白丢一次选区）。

### 台架（`outputs/clear_pixel_geometry_verify.cjs`，重写 → 157 项全过）
- T1 / T7：**全缓冲逐字节 oracle**（独立算出期望值，整条缓冲逐字节比对），
  断言「选区外一格不动」「选区像素恰好改 3 个分量 / 恰好改 alpha」。
- T2：内建变异（行跨错一位）证明 oracle 有判别力。
- T3：`expandToDocument` 落位 / 越界 / 完全在画布外三种情形。
- T11：**静态契约扫描** —— `writeLayerPixels` 不得出现 `replace` / `targetBounds`；
  `clearPixelLayer` 必须先 `expandToDocument` 再写回、必须有 `unlock/lockBackgroundLayer`、
  `lockBackgroundLayer` 必须落在 `finally` 的 `if (backgroundUnlocked)` 分支内；
  `readLayerPixels` 不得传 `applyAlpha`/`colorProfile`、必须用 `sourceBounds` + `boundsNoEffects`。
- T12：**注入假 `imaging`/`app` 真跑 `readLayerPixels`** —— 断言请求参数、被 PS 裁剪时几何取自返回值、
  3/4 分量识别、分量数异常→null、抛错→null、空图层不发起 IPC。
- 变异测试：10 个变异（加回 targetBounds / 跳过 expandToDocument / 去掉背景还原 / `boundsNoEffects→bounds` /
  原点改用请求值 / 摊平改用选区宽 / 背景族改成改 alpha / 像素族改成改 RGB / 加回 applyAlpha /
  还原条件恒真）**全部被抓**。
- ⚠️ 抽取器细节：`extractMethod` 必须给 `static async` 方法补回 `async`（原实现把 `async` 一起吃掉 ⇒
  `await` 直接语法错误）；`stripTypes` 需加 `:\s*Promise<...>` 规则。

## 第三轮：背景图层「解锁后什么都没发生、也没还原」（真机）

### 证据链（不靠猜）
- 截图那条被截断的红字首行，全仓只有**一处**匹配：`ClearHandler.ts` 里 `unlockBackgroundLayer`
  旧版的 catch 文案。⇒ 那条 warn **就是**解锁命令的 catch 打的。
- 用户同时描述「背景图层最后已经变成普通像素图层」。⇒ 真相：**解锁命令抛错，但图层类型确实被改掉了**。
- 第二处失效：旧 `readLayerPixels` 在 try **之外**读 `layer.boundsNoEffects`，且 `clearPixelLayer`
  在转换后又读 `app.activeDocument.activeLayers[0]` ⇒ 撞上刚改过类型的图层，抛 `invalid target sheet`
  ⇒ 异常逃逸 ⇒ 整轮静默失败（没删内容 + 没还原，两个症状同源）。
- UXP 文档确认 batchPlay「目标非法」时多数是 **resolve 一个 error 描述符**，不是 reject。

### 修法
- ⛔⛔ **图层类型转换之后，一次 DOM 都不能读**。`docId` / 目标图层 id / 读区域全部在转换前
  捕获成普通数字（`readLayerPixels(layerId, docId, region)` / `writeLayerPixels(block, layerId, docId)`
  改成纯函数，不再吃图层对象、不再引用 `app.`）。
- ⛔ 解锁成败**只信回读 `isBackgroundLayer`**，不看有没有抛错；回读不到 ≠ 失败（否则背景图层永远清不掉）。
  新增 `readActiveLayer()`（活动图层 / id / 背景标记，**三步各自 try/catch**）、`batchPlayError(result)`（查返回列表里的 error 描述符）。
- ⛔ 还原背景图层**尽力而为**：只有**明确读到**活动图层换成了别的图层才放弃（读不到也照还；
  上一轮的缺陷正是「读不到就跳过 ⇒ 用户图层结构被永久改成普通图层」）。读区域改用 `readLayerBounds`（`boundsNoEffects` 优先）。
- 顺带把 `readLayerBounds` / `clearPixelLayer` 内的多步探测全部自带 try/catch。

### 台架（`outputs/clear_pixel_geometry_verify.cjs` → **203 项全过**）
- 新增 T13（`readLayerBounds` 行为契约：`boundsNoEffects` 优先 / 退化→null / 抛错→null）

## 根因分析（未改码）：三类操作必弹「命令"获取"当前不可用」

用户问：切文档（含新开/关闭后自动切换）、快速删图层、删完立刻选区填充三类操作必弹报错；
早期靠"长等待"（f556e3e）规避，性能优化后又复现。要求根因 + 兼顾填充性能的方案。

### 结论（写入 `outputs/busy-gate-fix-plan.md`）
**正确性建立在「猜 PS 要忙多久」之上；性能优化只是把这条隐藏依赖暴露出来。**

四条根因：
- **R1 闸门开环**：通知在命令**中途**派发 ⇒ 只能给出忙碌区间的一个采样点。命令尾部「无通知但仍忙」
  的盲区靠常数窗口（300/1200ms）堵，弱机+大文档必然不够。
- **R2 事件覆盖缺口（新发现，可 grep）**：`open` / `close` **全仓无人注册**
  （`app.tsx:439`、三个子面板、`AdjustmentPanel:671`、`MaskSyncEngine:150` 的 NOTIF_EVENTS 都没有）。
  而打开大 PSD / 关闭文档恰是最耗时的两条命令 ⇒ 全程 `isPsBusy()` 恒 false。
  解释了用户「关闭再打开来回切又报错」（关闭路径无闸门 + 残留缓存指向已销毁文档）。
- **R3 三处「顺延上限用尽即硬闯」是弹框的最终出口**：`psProbe.ts:182`(debouncePsProbe, 12 次)、
  `psProbe.ts:274`(runWhenIdle)、`app.tsx:929`(selectionBusyDeferrals<10)。超限后从「跳过」变「硬闯」，
  而硬闯后的第一个动作是 `app.tsx:951` 的 `app.activeDocument` —— **在 executeAsModal(:978) 之外**。
- **R4 优化为何复现**：① 固定等待 300→60ms 直接缩短边际；② 改造前 ≈67 次串行同步 IPC 自身耗时数十至数百 ms，
  **客观上充当了隐性等待**，合并/删除后路径更快抵达危险区；③ 300ms TTL 缓存由事件驱动失效
  （`shouldInvalidateLayerInfo`）⇒ 制造「delete 事件 ⇒ 缓存失效 ⇒ 紧随探测必然 miss 并发 get」的新耦合，
  恰落在忙碌窗口；④ 缩短共享闸门导致 9 处消费者连带提前放闸（已付过代价）。

### 方案要点
把「等多久」换成三个可观测事实：**F1 事件静默阈值**（`lastEventAt + QUIET`，普通 150 / 文档级 500ms，
删除风暴期间自动续期、安静期立即放行）、**F2 模态作用域**（新增 `src/utils/psAccess.ts` 的 `psRead()`，
用 `core.executeAsModal` 作官方互斥原语：排队等待而非被拒，最坏也只是可捕获的 rejection，
把"不可捕获的宿主弹框"降级为"可捕获的失败"）、**F3 文档世代号**（文档级事件 ⇒ 作废在途任务与缓存）。
配套：删掉三处硬闯出口；`app.tsx:951` 的 DOM 读移进模态 ⇒ 填充路径模态外零 PS 访问 ⇒
安静路径比现状更快、忙碌路径排队不弹框。

⚠️ **必须先真机验证的两条假设**（未验证前不迁移）：
① `open`/`close`/切文档的**实际事件名与描述符**（`clearEvent` 说明 UXP 事件名存在重命名，不能想当然）；
② `executeAsModal` 在 PS 忙碌时是「排队等待」还是「立即 reject」（后者 ⇒ 改有界退避重发，仍正确）。
备选：A 纯加长窗口（治标、性能倒退）；C 同步读改异步 batchPlay（DOM 属性读无法异步化，需 B 兜底）。

### 用户待决
方案已交用户评审，**未改任何源码**（本仓惯例：根因确认后再动手）。

## 第二轮：开/关文档仍高频弹框 ⇒ 文档级「持续忙碌」闩锁

### 用户现场反馈（第一轮之后）
快速删除、删完立刻选区填充 **已不报错**；但**打开/关闭文档仍高频弹框**，
**超大文档概率更高**，有时要**连点八下**「获取不可用」警告窗口。

### 根因（第一轮只解决「谁在忙碌期发 get」，没解决「忙碌期到底多长」）
- 静默阈值是常数（300/1200ms），而打开/关闭大 PSD **连着忙好几秒**；
  阈值一过期粗筛就放行 ⇒ 那些**没走 `psRead` 的同步裸读**照常发 get。
- **每一次被拒的 get = 一次原生弹窗**：`getLayerSnapshot()` 遍历 N 层树就是 N 次
  ⇒ **「连点八下」是同一次树遍历里的八次 get**，不是八个来源。

  ① Adobe 文档：`executeAsModal` **25.10 起是「排队重试」**、`timeOut` **默认 1 秒**、冲突码 `error.number===9`；

## 第三轮：冷启动 + 打开 400MB PSD 100% 弹框（6 次）⇒ 租约 + 双缺陷修复

### 现场

用户配置很强（9800X3D/32GB）⇒ 排除「机器慢」，是**机制缺陷**。

### 根因（两个）
- **D1**：`applyDocIdentity` 的「无文档→有文档」分支只记基准**不登记文档级变化**

  假阳性放行。弹框直接来源 = 同步裸读（图层树遍历每层 5 get 等）。

- `psAccess`：`__jwPs.dump()/state()/trace()` 取证工具 + 文档级事件固定日志 `📥 文档级事件: <名>`。

## 第四轮：真机出现「Too many modal scope commands」×60 ⇒ 模态命令节流

### 截图判读（重要现场证据）

  `spaceModalEntry()` 整形；`probeHostIdle` 太近跳过（**不作废租约**，跳过 ≠ 忙）。
- 写路径（填充/描边）不受节流（用户主动触发）。
