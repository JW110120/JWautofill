# 2026-10-08 工作日志

## 选区纯色填充 0.5s 延迟定位与优化

### 背景
用户反馈：生成选区后需等约 0.5 秒颜色才填充完成。测试机为低配（Ryzen 5 3400G +
Vega 集显、16GB），目标是在低端硬件上接近即时响应。

### 根因定位（关键结论：不是像素遍历）
纯色填充路径**没有 JS像素循环**——颜色写入是 PS 原生 `fill` 命令
（`FillHandler.createBasicFillCommand`），由宿主多线程完成，耗时仅几毫秒。
0.5s 几乎全部来自 **① 300ms 人为固定等待 + ② 约 67 次串行同步 IPC 往返**。

逐环节拆解（默认配置：纯色/无羽化/无选区改造/无描边/autoUpdateHistory 开/deselect 开）：

| 环节 | 位置 | 同步 IPC |
|---|---|---|
| 忙碌闸门固定顺延 300ms | `app.tsx` handleSelectionChange + `psProbe.BUSY_AFTER_EVENT_MS` | 硬等 300ms |
| 外层 activeDocument + quickMaskMode | 外层 | 2 |
| 外层 getSelection | | 1 |
| 模态内**重复** getSelection | | 1 |
| `doc.historyStates`（整条历史数组）判空 | setHistoryBrushSource | 1 |
| `getActiveLayerInfo()` | LayerInfoHandler | **~18** |
| `fillSelection` 内**又一次**单通道判定 | | ~7 |
| 图层可见性 + foregroundColor | | 3 |
| fill + deselect 两次下发 | | 2 |

`getActiveLayerInfo` 单次 18 次的成因：`checkSingleColorChannelMode` 内部
**又完整调了一次** `checkLayerMaskMode`，两次的「取 mask 通道」全部重跑；
且 `checkLayerHasPixels` 对 `bounds` / `bounds.width` / `bounds.height` 各读一次。
填充后紧随的面板巡检还会再调 2 次 `getActiveLayerInfo`（每次 ~18）。

## 复核：性能改动是否破坏「切文档 / 快速删图层」的弹框防护

用户要求逐项核对本次改动与既有防护的关系。**复核中发现 2 个我自己引入的真实缺陷，均已修复。**

### 缺陷①（严重，已修）删除风暴末事件把忙碌窗口压到 60ms
「快速连续删除图层」时 PS 会交替派发 `delete` 与 `set`（删图层连带改选区），
`MaskSyncEngine.NOTIF_EVENTS` 含 `set`、app 的选区监听器也只监听 `set`。
⇒ 若风暴**最后一个**事件恰好是选区 `set`，整场删除的 300ms 窗口会被 60ms 覆盖
⇒ 宿主仍在忙⇒ 重新弹「命令"获取"当前不可用」，**正是 2026-10-07 修过的 bug**。

修法（`psProbe.ts`）：加 `lastLongEventAt` + `LONG_EVENT_NEIGHBOR_MS = 600`。
**只要最近 600ms 内发生过任何非选区事件，选区事件就并入保守窗口。**
不影响性能：删除/合并是低频、不在实时性关键路径；纯套索连点仍走 60ms 快路径。

### 缺陷②（中等，已修）背景图层的hasPixels 被误判为 false
我把 `readLayerDomInfo` 写成 `const bounds = isBackgroundLayer ? null : activeLayer.bounds;`
⇒ 背景图层 `hasPixels` 恒为 false。而 `hasPixels` 是 app.tsx 里
`hasTransparencyLocked && hasPixels` 的分支判据（6 处消费，含 PatternFill/GradientFill/
SingleChannelHandler/StrokeSelection）⇒ 背景图层会误走 `fillLockedWithoutPixels`
（多两次 applyLocking，可能改写用户的锁定状态）。旧 `checkLayerHasPixels` 对所有图层一视同仁。
修法：去掉这个 background 特例，背景图层照常读 bounds。

### 确认无影响的部分（逐项核对过）
- **切文档**：`selectionChangeListener` 只注册 `['set']`，doc-switch 的 `select` 事件
  **不会**进入 `handleSelectionChange`；`isDocSwitchDescriptor` 分支与 1200ms 完全未改。
- **忙碌窗口并集**：`markPsBusy` 是 `Math.max`，短窗口**永远无法缩短**长窗口。
  已写 `/tmp/busy_union_test.cjs` 穷举 5 种事件顺序验证（select1200→set60、
  set60→select1200、delete300→set60、set60→delete300、单独 set60），结果全部正确。
- **事件订阅/解绑**：未新增/删除任何 `addNotificationListener`；
  `componentWillUnmount` 原有清理全保留，仅追加 `selectionRetryCount = 0` + 缓存失效。
- **循环 import**：`LayerInfoHandler` 只 import `photoshop`，不反向引用 MaskSyncEngine ⇒ 无环。
- **通知回调内零 IPC**：`invalidateLayerInfoCache` / `shouldInvalidateLayerInfo`
  都只碰模块级变量与 descriptor 字段，无 DOM / 无 batchPlay ⇒ 符合「回调内唯一允许纯内存」的既有铁律。
- **空引用**：`layer.id` 已验证有效（`layerTreeSnapshot.ts:144` 同样在用）；
  `doc.id` 我反而去掉了（改用全局唯一的 layer.id），少一次 IPC。
- **重复绑定**：无。

## 【真机实测反馈】我上一轮的「复核结论」是错的 —— 用户实测报了 4 类新问题

用户实测反馈（11:23）：
1. 快速删除多个图层，超过某个速度**必报错**
2. 快速删图层后立刻套索**必报错**
3. 切换文档（含新开/关闭导致的自动切换）**有几率报错**；首次切换报错，之后速切不报错，
   但关闭再打开文档来回切又报错
4. **新引入**：快速蒙版下三种填充模式**全部报错**（之前没有）
5. 背景图层正常；开启清除模式会弹出**PS 原生描边对话框**，要求静默

### 真正的根因（我上一轮完全没想到）

**我缩短的是 `isPsBusy()` 这个「全局共享闸门」，它有 9 处消费者：**
`pollQuickMask`(300ms 轮询) / `pollToolChange`(300ms 轮询) / MaskSyncEngine 的
2s 轮询 + 两处同步入口 / AdjustmentPanel 探测 / `debouncePsProbe` / `runWhenIdle`
/ `handleSelectionChange`。
⇒ 把选区事件的全局窗口从 300ms 压到 60ms，等于让**那 9 处轮询/探测在 PS 仍忙碌时提前放闸**，
它们集体发 `get` ⇒ 宿主弹「命令"获取"当前不可用」。
四种症状全部由此而来（快速蒙版尤其明显：它持续派发选区 set ⇒ 闸门被反复压到 60ms）。

⚠️ **我的「邻居护栏」（`lastLongEventAt`）只护住了填充路径自己，护不住那 9 处轮询** ——
这就是为什么我"逐项核对过"却仍然漏判：我核对的是「填充路径会不会发 get」，
**没核对「缩短窗口后，别的消费者会不会提前发 get」**。

### 解法：全局闸门与填充冷却**解耦**（最终形态）
- `markPsBusyForEvent` **恢复两档、且选区事件也用 300ms**（不再有 60ms 档）；
- 新增 `fillReadyRemain()`：只给填充路径用的**私有冷却**（60ms），
  且「最近 600ms 有过任何非选区事件（含**切文档**）」时**自动退回全局剩余时间**；
- 切文档事件**必须**同时记 `lastLongEventAt`，否则「切文档→立刻套索」会走 60ms 快路径
  而撞上 1200ms 窗口（我第一版私冷却就漏了这条，靠场景断言才发现）。

⚠️ 同时修掉falsy 陷阱：`lastLongEventAt = 0` 是 falsy ⇒ `if (lastLongEventAt && …)` 短路
⇒ 保护在时刻恰为 0 时失效。改用 `-1` 哨兵 + `>= 0` 判定。

### 快速蒙版报错的根因（合并 batchPlay 的副作用）
`probeChannelState` 原本把「取 mask 通道」与「取目标通道」**合并进同一个 batchPlay 数组**。
快速蒙版下 `get channel mask` 会失败 ⇒ **第一条失败连带整批失败**，而宿主对失败命令的
原生报错框**绕过 JS try/catch** ⇒ 图案/渐变面板的灰色预览（也要调 getActiveLayerInfo）
与三种填充全部报错。
**修法**：① 快速蒙版下**跳过 mask 通道 get**（此时 `isInLayerMask` 本就无意义）；
② 两条 get 改回**分开下发**，各自 try/catch，恢复「一条失败不影响另一条」的语义。

### 清除模式弹原生描边框
截图是 **PS 原生「描边」对话框**（确定/取消/位置/混合），不是我们的子面板。
根因：`StrokeSelection.ts` 只在**描述符内**写了 `_options.dialogOptions`，
而 **batchPlay 的 options（第二参数）没写**；`stroke` 命令在
`mode = clearEnum` 下会忽略描述符内的 `_options` ⇒ 弹原生框。
**修法**：该文件全部 16 处 batchPlay 的 options 补`dialogOptions: 'dontDisplayDialogs'`。

### 沉淀：新增核对台 `outputs/gate_verify.cjs`
用 `ts.transpileModule` 加载**真实 psProbe 源码**（掐掉 photoshop import），
注入可控时钟，逐场景断言「填充等了多久」+ 不变量 `fillReadyRemain() ≤ psBusyRemain()`。
7 个场景全部通过。**这类回归编译不报错、类型检查不报错、UI 看不出来，只能靠场景断言。**
重点是删除风暴末事件、后台大文档套索、面板重载后的监听器状态。

## 修复：拾色器初始色 + 快速蒙版清除+描边色失效（同日 14:5x）

### 现象一：色板显示 A，拾色器打开成 PS 前景色 B

- **根因**：`showColorPicker` 是**无参**命令，描述符里没有任何「初始色」字段，
  PS 一律以**当前前景色**为初始值。旧代码在两处（`app.tsx:openStrokeColorPicker`、

  记下真前景色 → 把前景色设成 `initial`（HSB）→ 打开 → 读结果 → **finally 里还原**。
  两个调用点改为传「面板当前显示色」：

### d 的根因（**一处**，跑全 11 组）—— 回归，非新缺陷
`LayerInfoHandler.probeChannelState()` 里：
```js
const activeChannelsCount = doc0?.activeChannels?.length || 0;   // ← 图层蒙版激活时**抛异常**
if (activeChannelsCount > 1) return result;
```
**PS 在图层蒙版激活时读 `doc.activeChannels` 会抛 `Unknown or unsupported active channels`**
（Adobe 官方论坛 "Better way to see if a mask is active" + 旧版 ExtendScript 讨论均确认：
「图层蒙版被选中时访问 activeChannels 会抛异常」）。
该异常逃逸到 `probeChannelState` 的**外层** catch ⇒ 直接 `return {inLayerMask:false, inSingleChannel:false}`
⇒ **`isInLayerMask` 恒为 false**。
⚠️ **旧实现本就把这段包在内层 try/catch 里**（`checkLayerMaskMode` 内独立 try/catch，异常被吞掉后继续比对通道名）；

## 第四轮：渐变轨道色标灰色态 + 描边设置混合模式禁用态 + 背景图层「描边+清除」

### 用户三条需求
1. （补上一轮 c 的遗漏）渐变**轨道上那排方形色标**（`.color-slider-thumb`）在灰色态下也要同步灰化。
2. 描边设置里混合模式「不能正常使用」时**不再整行隐藏**，改为标签 + 下拉都显示禁用态。
3. 图层**背景图层**的 12 组合里 3 种「填充 + 描边 + 清除」失效：会弹原生「描边」框、
   随后把描边**填成描边色**。期望：以该描边的灰度删除描边内部的内容，且静默。

### 根因与修复
- **①** `GradientPicker.tsx` 的 `.color-slider-thumb` 仍用裸 `getRGBColor(stop.color)`
  （上一轮只改了同行「颜色」区的 `.color-preview`）⇒ 改为 `getDisplayColorHex(stop.color, grayDisplay)`。
- **②** `StrokeSetting.tsx` 原为 `{!clearMode && (<混合模式行/>)}` ⇒ 改为始终渲染；
  标签 `className={clearMode ? 'label-4 label-disabled' : 'label-4'}`，`Select` 加 `disabled={clearMode}`。
  ⚠️ `.label-4`（common.css ~140）与 `.label-disabled`（common.css ~1839）同为 (0,1,0)，
  **同文件内后置规则取胜** ⇒ 不需要两级类（与 app.css 那条跨文件冲突不同）。
- **③ 根因（单点，Adobe 文档可查）**：`clearEnum`（清除混合模式）**在背景图层不可用**，
  也**在开启「锁定透明像素」的图层上不可用** —— 官方原文
  「The Clear blending mode will be unavailable for a background layer, or if preserve
   transparency is enabled on the target layer」。PS 遇到不可用的 `clearEnum` **不抛错**：
  弹原生「描边」对话框 → 按普通填充把描边画成描边色（= 用户看到的现象）。
  ⇒ `StrokeSelection.ts` 新增**分支 9 `strokeSelectionOnOpaqueLayer`**：
  `isBackground || hasTransparencyLocked` 时走它，混合模式**固定 `blendSubtraction`（减去）**，
  减去量 = 描边色灰度 × 不透明度 ⇒「以该描边的灰度删除描边内部的内容」，全程静默。
  · 描述符形状与分支 2 同档（`width: {pixelsUnit}` / `_enum: 'strokeLength'` / `color: RGBColor`）。
  · 本分支不修改前景色 ⇒ **不做**无用的「保存-恢复前景色」（省 2 次同步 IPC）。
  · 普通像素图层 + 清除**仍然**用 `clearEnum`（核对台有回归护栏，未一刀切）。
  · `StrokeSelection.ts` 的局部 `LayerInfo` 接口补 `isBackground?` / `hasTransparencyLocked?`
    （`LayerInfoHandler.LayerInfo` 早已带这两个字段，只是描边侧没声明）。
