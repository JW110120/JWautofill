## 二次修复（用户反馈 3 个运行时 bug，22:36）

- **A. 选择文件报错 `e.trim is not a function`**：根因是 `getFileForOpening` 的 `types` 写成了 DOM 风格的 `{description, accept}` 对象数组；UXP 内部对每个 types 元素调 `.trim()` → 对象没有该方法而崩。正确签名是**扩展名字符串数组** `types: ['exe','bat']`。已修正，并归一化返回值（单文件/数组两种返回），catch 安全字符串化。
- **B. 唤起安装器失败 `could not find an entry of plugin:/native`**：`getPluginFolder().getEntry('native')` 在沙箱下找不到 native 目录。改为用 `getPluginFolder().nativePath` 拿真实系统路径再 `shell.openPath(完整路径)`，绕开沙箱。安装器/卸载器都走这个 `getBundledNativePath` + `openBundled` 帮助函数（openPath 成功返回空串、失败返回错误串）。
- **C. 笔刷未能自动枚举**：原 `enumerateBrushes` 用 `get` + `brushPreset ordinal all`，取到的结构里拿不到 name 列表。改为读 application 描述符的 `presetManager`（第 0 组 = Brush Presets，第 7 组 = Tool Presets），并优先尝试 `app.brushes.get()`。结构解析做了多重兼容（presetManager 可能是分组数组，或带 preset/brushPreset 容器；结果可能直接是 presetManager 描述符）。`HotkeyBridge.ts` 已 `import { app }`。
- 生产构建验证通过（仅资源体积 warning，无 ws/error）。
- **关键坑记录**：UXP `getFileForOpening` 的 `types` 是字符串数组（非 DOM 对象数组）；插件内定位文件优先用 `getPluginFolder().nativePath` 而非 `getEntry`（沙箱下 native 目录不可见）。

## 第三次修复（22:54，录制 + 守护进程区重构）

- **A. 录制组合键真正根因（之前归因 window/document 是错的）**：UXP 官方明确「面板只有自身持有键盘焦点时才会派发 keydown，且无全局快捷键能力」。旧代码在 `startRecord` 里调用 `document.activeElement.blur()`，把面板焦点整个丢掉 → 按键全跑去了 Photoshop → document 监听器永远收不到。修复：录制时**不 blur**，改为聚焦一个隐藏 `<input>`，让面板稳稳持有焦点，keydown 打到该 input 的 `onKeyDown`。同时去掉了挂在 document 上的监听器。
- **B. 守护进程交互重构为两个按钮**：
  - 「安装守护进程」：`getFileForOpening({types:['bat']})` 让用户选 install.bat → `shell.openPath` 运行；因 install.ps1 末尾自带 `Start-Process ... --autostart` 启动守护进程，面板侧再做兜底——`autoEnableDaemon` 每 4s 轮询，未连接就 `launchDaemon(预期路径)`，连上即停（避免重复拉起实例）。
  - 「卸载守护进程」：直接 `openBundled('native/HotkeyDaemon/uninstall.bat')`（nativePath 方式）。
  - 移除了「守护进程路径」的面板显示（用户不需要知道）；连接状态（已连接/未连接）保留。
- `uninstall.ps1` 已确认安全：仅按精确进程名停进程、仅删我们写的 HKCU\Run 项、仅删 `%LOCALAPPDATA%\JWautofill\daemon`（带父目录/leaf 校验防误删）、清理 temp 发布目录、hotkeys.json 默认保留（询问后删）。
- 生产构建验证通过（仅资源体积 warning）。

## 第四次修复（23:xx，安装失败 dotnet publish 无 SDK）

- **根因**：`install.ps1` 用 `dotnet publish` 现场编译守护进程，但用户机器（家机）只装了 .NET **运行时**、没有 **SDK** → 报 `No .NET SDKs were found`，编不出 exe。实测本机环境同样只有运行时（Microsoft.NETCore.App 8.0.13/15）无 SDK。
- **正确方案：预编译「自包含单文件 exe」随插件分发，安装只复制、不编译**。`csproj` 已配 `PublishSingleFile=true / SelfContained=true / RuntimeIdentifier=win-x64`，`dotnet publish -c Release -r win-x64 -o publish` 产出单文件 exe（含 .NET 8 运行时，65MB，任意机器零依赖）。
- **装 SDK 的坑**：
  - 本机无 SDK，需先装。用官方 `dotnet-install.ps1` 装到用户目录 `$LOCALAPPDATA/dotnet-sdk`（无需管理员）。
  - 第一次装出来 `sdk/8.0.424/Sdks/` **缺 `Microsoft.NET.Sdk` 基础包**（只有 WindowsDesktop/NuGet.Build.Tasks.Pack），导致 `dotnet publish` 报「无法解析 SDK Microsoft.NET.Sdk」。原因：旧的残缺 SDK 目录没清掉，`dotnet-install` 认为已装好就跳过。**必须用 PowerShell `Remove-Item -Recurse -Force` 清掉再重装**（bash 的 `rm -rf` 被 safe-delete 包装把 Windows 路径拼坏，删不掉；报 `safe-delete][diag] genie-trash failed ... CanonicalizePath`）。
  - 运行用户目录的 `dotnet.exe` 时要设 `DOTNET_ROOT` 指向它，否则 NuGetSdkResolver 会误用 `C:\Program Files\dotnet`（只有运行时）作 root。
- **安装脚本改为预编译优先**：`install.ps1` 第 1 优先复制 `$PSScriptRoot/publish/JWautofillHotkeyDaemon.exe`（无 SDK 也能装）；第 2 回退 `dotnet publish`（开发者有 SDK）；都没有则报错。并加「已运行则不重复拉起」判断。脚本保持 **ASCII-only**（避免 GBK 语法坑）。
- **.gitignore**：新增例外 `!native/HotkeyDaemon/publish/JWautofillHotkeyDaemon.exe`（bin/obj 仍忽略）。该 exe 入库后约 65MB（自包含运行时的代价），家机 pull 后即可零依赖安装。已知权衡：若想保持仓库精简可改用 Git LFS。
