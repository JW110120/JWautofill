## alpha对齐 v4（`src/adjustments/alphaAlignProcessor.ts`）

**用户反馈**：v3 对粗线细线识别不错，但细线还差一口气——①两根细线(<5px)交叉 ②细线与粗线交叉 ③色块内部小面积高不透明度杂点(半径<5px)，点击后只统一化一部分，剩高不透明度像素，怎么点都无法统一化。

**根因（合成图实验定位，测试代码在 %TEMP%\aa_test\，Node 可跑）**：
1. **软笔刷细线被拉过暗/斑驳**：v3 的"众数"判据对软笔刷细线失效——细线 core 仅 1~2px 宽，k4 环带 [4,7] 里羽化带（42）像素数 > core（150）像素数 → 众数=42 → 交叉中心 212 被拉到 42、线 core 被误拉低。
2. **环带无众数时卡死**：色块内部 alpha 不均匀（波动/渐变）时，环带直方图无显著众数（占比不达标）→ needLarge 门槛挡死 → 杂点像素永不修改 → "怎么点都无法"。
3. **k112 大环带孤立值污染**：线端羽化/孤立低值在 k112 环带 cnt 极小时成为众数 → 单线 core 被误拉低。
4. **第一遍顺序依赖**：逐行处理时凸包像素被提前拉平，中心像素环带统计漂移（212 计数 8→4）→ 平坦拦截失效。

**v4 方案**：
1. **多尺度环带 RING_SCALES=[1,4,14,42,112]**：k1 捕捉极细线 core，k4/14/42/112 逐级出凸包。
2. **"自身平台"拦截（平坦度判据）**：环带 [alpha..255] 像素 ≥4（绝对数，防软笔刷细线 core 计数少）且 [alpha, alpha+8] 内占 ≥50% → 像素在自身平台（线 core/羽化/凸包中心）→ 放大尺度；否则找参照。
3. **高端区间参照 [max-60, max]**：从环带最大值向下找第一个计数达标簇（≥max(5,10%环带)）——线 core 在环带高值区，羽化带（42/73/109/138）是中低值被排除；凸包值（≥alpha）跳过继续放大。
4. **三态判定**：参照显著低于 alpha（<alpha-5）→ 采纳（多尺度取最低候选，纠正小尺度误选过渡值如 181→150）；参照接近 alpha → 非凸起（flatAll，第二遍跳过）；参照 ≥alpha → 凸包内继续放大。
5. **第一遍固定读原始 alpha（readSrc=aR）**：判定与处理顺序无关（消除顺序依赖）；第二遍读修改后 curA。
6. **中位数回退**：所有尺度无稳定平台（色块波动）→ 用"cnt≥128 的最大有效尺度"直方图中位数（不能只依赖 k112，色块贴边时 k112 cnt=0 → 回退 k42）。受"中尺度(k14/k42)平坦且无非平坦"保护（防线端 core 被 k112 混入的另一条线羽化带污染）。
7. **flatAll 数组**：第一遍判定"非凸起"的像素第二遍跳过（防环带污染误伤）。

**验证**（硬边+软笔刷渲染，二次点击确认无残留）：
- 线宽 1~12px 横竖交叉：中心全 150、残留 0、误拉低 0（v3 的偶数宽度误伤清零）；
- 细粗交叉（软笔刷 4×40）：残留 0（v3 残留 131）；
- 色块+杂点（均匀/±20~30 波动/双杂点）：残留 0（v3 卡死 103）；
- 斜交叉 30°/45°、1px/2px 极细线、T 形相接、线端杂点：全部 0；
- 二次点击全部 0 改动（无斑驳）。
- 剩余边缘（可接受）：soft 5px 残留 4 像素（十字臂 160）、soft 8px 误拉低 8 像素（交叉外围 core→109），合计 12 像素/9 万，视觉无感。

**经验**：环带统计里"众数"对软笔刷细线不可靠（羽化带像素多）——应从**环带最大值向下找高端簇**；"自身平台"用**绝对数阈值**（相对占比在细线场景永远追不上 core 的固定计数）；中位数回退须防"大环带混入另一条线内容"（用中尺度平坦性保护）；两遍处理中第一遍必须读原始数据避免顺序依赖。

## alpha对齐含背景（同日追加）

**需求**：alpha 对齐按钮右侧新增"alpha对齐含背景"按钮。场景：alpha=50 的色块（背景）上画 alpha=118/128 的两根线交叉（同一图层），统一化交叉区域的凸起，**不影响背景色块的不透明度**，适配各种线宽交错。

**与普通 alpha 对齐的区别**：普通模式在"背景+线"场景会把交叉区拉向背景（200→50，中位数回退被背景 50 主导）；含背景模式参照排除背景。

**实现**（`processAlphaAlign` 增加第 6 参数 `withBg`，`handleAlphaAlign(withBg)` + 新按钮）：
1. 每尺度先估计背景水平（环带中位数 med），只统计 >med 的"线上像素"（cntHigh）做参照——簇阈值 bMin 基于 cntHigh 而非全环带（细线在背景主导环带也能命中，修复 1px 交叉中心被拉向背景）；
2. 参照须比 alpha 低至少 BRIGHT_DELTA=10（只修明显凸起，保护"线自身 vs 另一条略不同线"：153 竖线 vs 145 横线差 8 不改）；
3. 参照查找下限 loV = max(max-60, med+1)（高于背景）；
4. 中位数回退取 >med 像素的中位数（线主体水平），同样要求差 ≥10；
5. midFlat 保护：含背景模式只要 k14 平坦就保护线 core（k42/k112 混入另一条线羽化带时也不误伤）；非含背景保持 midFlat && !midNonFlat。

**验证**（背景 50 + 118/128 线交叉，硬边+软笔刷）：
- 硬边 3/1/20px、软 4px：交叉凸起残留 0、背景 50 被改 0、线像素被改 0（用户核心例子完美）；
- 软 2px：残留 2（十字臂 160，差 7 <10 不修）；
- 软 10px：残留 0、16 个线像素 153→140（差 13，轻微）；
- 细粗（软 4×40）：主交叉区 200→145 修好，细线穿过粗线羽化区边缘约 20 个像素过度拉低（159→79，med2 被粗线羽化带主导，边缘情况）；
- 非含背景模式全量回归通过（与 v4 最终版一致，无回归）。

**经验**："背景+线"场景的关键是**排除背景的统计**（cntHigh=环带>中位数的像素数，bMin 基于它）+ **参照差门槛**（BRIGHT_DELTA，保护线自身）+ **中尺度平坦保护**（线 core 不被大环带混入的其他线羽化带污染）。细粗交错+低透明背景+细线穿过粗线羽化区是已知边缘情况（med2 被羽化带主导），尝试过"med2 与 alpha 差 ≤60 上限"会引入等宽线场景回归，暂保留。

## 背景保护（线条侵蚀修复 + 按钮改名，同日第三次）

**用户反馈 2 点**：①按钮"alpha对齐含背景"改名"背景保护"；②选区内线条的一部分被背景 alpha 侵蚀（如软笔刷 4px 交叉区外缘线 core 153→125、细线穿粗线 154→79），选区选得不够大时算法难分线条/背景，要求"识别线条像素并保护，除交叉区外线条全保护"。

**根因（小选区复现 153→125）**：交叉区外缘竖线 core(153) 的 k112 大环带（距离 112-115px，恰好避开交叉区）采到另一条线的羽化带值 125 → bestRef=125 被采纳；而 `midFlat` 保护写在 `bestRef` 返回**之后**，被短路。

**修复（含背景模式 analyzePixel 6 处）**：
1. **midFlat && !midNonFlat 保护提前到 bestRef 返回之前**（含背景：中尺度确认像素在自身平台 → 任何尺度参照都不可信，直接保护）；
2. **含背景候选取"最高"**（bestRef 初始 -1）：大尺度环带污染是"羽化带低值"（125/54），取最高=线 core；非含背景保持取最低（交叉过渡 181>150 由大尺度纠正）；
3. **"接近 alpha 的簇"（差<refDelta）一律保护**（不再跳过找更低）：160 附近有 153×8 线 core 说明像素在线水平附近；跳过会继续找到羽化带 125；
4. **bMin 比例 5%（含背景）**：cntHigh 过滤背景后 10% 过大，软 4px 线 core 在环带仅 8 个，10%×cntHigh=8~11 卡达标线，5%+绝对数下限 5 兜住；
5. **sawAbove 保护**：所有尺度都"v1≥alpha"（像素低于周围线 core，如软 10px 羽化带 135）→ 禁用中位数回退（med2 是羽化带）；
6. **平坦判据含背景改用绝对数**（nearCount≥4）：k42 大环带混入交叉高值（198×1）使 highCount 虚高、占比判据失败；只要 [a,a+8] 内 ≥4 个同水平像素即拦截；
7. **中位数回退前 nearSelf 检查**：环带 [a-refDelta, a+CLOSE_DELTA] 内 ≥4 个接近 alpha 的像素（细线 core 153 穿过粗线羽化带叠加 154）→ 保护，防 med2=粗线羽化带(79)。

**验证**（含背景，背景 50 + 118/128，硬边+软笔刷，全图选区）：
- 硬边 1/3/20px：残留 0、背景 0、线 core 0 改动、侵蚀 0（用户场景完美）；
- 软 2/4/10px：线 core 0 改动、侵蚀 0；软 10px 残留 5（中心 200→180，未完全拉平）；
- 软 20px：残留 141（凸包边缘过渡 159-162 差<10 保护保留）、侵蚀 4；
- 细粗 4×40：线 core 0 改动、侵蚀 2（原 32）；
- 非含背景全量回归通过（A-L、线宽 1-12px、软笔刷、细粗、色块杂点均无回归）。

**教训**：midFlat 保护必须放在 bestRef 返回之前否则被大尺度参照短路；"取最高/取最低"在"羽化带污染大尺度"（软笔刷取最高）与"凸包过渡污染小尺度"（硬粗线取最低）间矛盾，3× 下移（高簇被 ≥3× 大簇替换）会误伤"细线在粗线上"（粗线羽化带是大簇），已回退；硬 20px 凸包中心 200→177 残留为已知局限（"取最高"策略代价，非侵蚀）。

## 选区自动填充提速 + 套索连点 bug 修复（`src/app.tsx`，同日第四次）

**用户反馈两点**：
1. 低配电脑选区生成后有明显填充延迟，希望提速。
2. 套索快速连续画两个选区时，第二个选区被错误填充成"整个文档"，体验差。

**根因诊断**：

1. **响应延迟**：`handleSelectionChange` 入口有 `await sleep(50ms)`、`applyFeather` 内还 sleep 50ms、`fillSelection` 入口又 sleep 50ms，三个加起来白送 150ms+ 纯延迟；`feather=0` 时仍跑 `applyFeather`（内含一个多余的 `getSelection` + `setState({SelectionA})`，而 `SelectionA` 在仓库里**只写不读**）；`fillSelection` 里 `LayerInfoHandler.getActiveLayerInfo()` 一次填充内被调 2~3 次（每次 3 次 batchPlay）。
2. **填充整个文档的 bug**：原 `isListenerPaused` 在第一个 `await sleep(50)` **之后**才置位，导致它之前的窗口期里多次 `handleSelectionChange` 并发进入。流程：
   - 选区 A 事件 → handleSelectionChange #1 进入 50ms 等待
   - 用户在等待期间画选区 B → 事件 #2 触发 handleSelectionChange（isListenerPaused 还是 false，照常进入）
   - 两者都通过 `getSelection` 读到 B，并先后进入 `executeAsModal`
   - #1 完成后 `deselectSelection`（默认 `deselectAfterFill=true`）清空选区
   - #2 的 executeAsModal 在队列里恢复执行时选区已空 → fill 命令无选区 → Photoshop 默认"填整个图层" → 视觉上是"填了整张图"

**修复方案**（`src/app.tsx`）：
1. **同步锁取代延迟锁**：`isListenerPaused` → `isFilling + pendingSelection`，在最早处（`getQuickMaskMode` 之后、第一次 await 之前）同步置 `isFilling = true`；并发进入只置 `pendingSelection = true` 并立即返回，**不再并发覆盖**。`finally` 里清 `isFilling`、若 `pendingSelection` 为真则 `setTimeout(0)` 递归触发一次 —— 套索连点不会丢选区。
2. **干所有 50ms 延迟**：`handleSelectionChange` 入口、`applyFeather`、`fillSelection` 入口的 `await sleep(50)` 全删。Photoshop UXP 的 batchPlay `synchronousExecution: true` 已经保证与 PS 主线程串行，不需要额外让路。
3. **跳过无效分支**：
   - `feather=0` → 不进入 `applyFeather`（旧版本还会触发一次 `getSelection + setState({SelectionA})`，`SelectionA` 整库只写不读，删掉）。
   - `selectionSmooth/Contrast/Expand 全 0` → 不进入 `applySelectionModification`。
   - 把 strokeEnabled/deselectAfterFill/autoUpdateHistory 等判断从 reactive state 提到循环外一次性求值（`const needsStroke = this.state.strokeEnabled`），避免 modal 回调里反复读 React state。
4. **executeAsModal 内防御性重校验**：第一句就重读 selection，若已被前一轮 `deselectSelection` 清空则直接 return，**绝不**对空选区调 fill（这是"填整个文档"bug 的兜底）。
5. **`fillSelection(layerInfo?)` 接受外部传入的 layerInfo**：避免单次填充内 2~3 次重复查询；`LayerInfoHandler` 把 `LayerInfo` 改为 `export`（之前是 `interface` 局部导出，main.tsx 要 import 所以提了出来）。
6. **edit 入口检查解耦**：把"`!this.state.isEnabled || this.isListenerPaused`"拆成两段前置 if：`isEnabled` 检查在最外层；`isFilling` 同步锁紧跟其后。

**`applyFeather` 改签名**：从读 `this.state.feather` 改为形参 `(featherAmount: number)`，调用方已经求出，统一在调用前判断 `needsFeather = featherAmount > 0`。

**验证**：
- `webpack --mode=development` 与 `--mode=production` 均通过，无新 TS 错误（只剩原有的 bundle 大小 warning，跟本次改动无关）。
- 行为预期（待用户实际验证）：
  - 低配电脑：纯色填充（feather=0、selectionSmooth/Contrast/Expand=0）路径从 150ms+ 等待降到只剩 batchPlay 往返时间。
  - 套索连点：第二选区不会被错填整个文档；要么在第一轮填充完后被重新触发，要么在 executeAsModal 内 select 校验失败时安全 return，绝不"涂满图层"。

**额外小事**：`getSelection` 只用来判 null 而 result 直接丢弃，是合理的，毕竟 batchPlay 是读 selection 的唯一可行 API，省不掉；但校验点（outer + modal 内部两次）故意保留，外层判"是否要进入填充流程"，内层判"进入时是否已被并发覆盖掉"。

## 禁用控件 hover 光标统一改为 not-allowed（`src/styles/styles.css`，同日第五次）

**用户反馈**：清除模式开启时，新建图层开关处于 disabled 状态，但鼠标悬停仍是 `pointer` 光标，不符合禁用语义；要求举一反三——任何 disabled 控件 hover 时都要显示 `not-allowed`。

**现状**：代码里只有 `sp-picker[disabled]` 有 `cursor: not-allowed`；`sp-switch/sp-button/sp-action-button/sp-radio` 这些 Spectrum 控件在被 React 端传 `disabled={true}` 时，组件内部只是变灰、不拦截 cursor，光标还是默认 `pointer`。

**修复**（`src/styles/styles.css`）：
```css
sp-switch[disabled],
sp-button[disabled],
sp-action-button[disabled],
sp-radio[disabled] {
  cursor: not-allowed;
}

/* 开关禁用时，左侧标签文字也变灰，hover 同样显示禁止光标 */
.switch-container:has(sp-switch[disabled]) .switch-label {
  cursor: not-allowed;
  color: var(--disabled-color);
}
```

**效果**：
- 清除模式 ↔ 新建图层 互斥：被禁用的那个开关本体 + 左侧"清除模式/新建图层"标签 hover 都是禁止光标（`:has(sp-switch[disabled])` 用子选择器命中父容器）。
- 快速蒙版状态下"新建图层"也被 disabled（`disabled={this.state.clearMode || this.state.isInQuickMask}`），同样自动命中。
- 之后任何新加的 disabled Spectrum 控件无需再写 CSS。

**Webpack dev 构建通过**（24s，dist/styles.css 含新规则）。

**经验**：Spectrum Web Components 的 `[disabled]` 属性只控制视觉灰度与事件拦截，**不**自动改 cursor；插件项目里需要在全局 CSS 一次性把所有"可点击 + 禁用"组合写齐，扩展时只需 React 端写 `disabled={...}`。

## 蒙版同步分区（`src/utils/MaskSyncEngine.ts` + `AdjustmentPanel.tsx` + `adjustment.css`，同日第六次）

**需求**：调整面板新增与"边缘处理"同级的"蒙版同步"大分区。内部有 +号按钮新建"同步任务N"子卡片（圆角矩形，分割线分三段：样本/目标/开关+删除），双击标题可重命名。样本=某像素图层的灰阶/R/G/B/A 通道（可反相）；目标=有用户蒙版的图层或组；同步=把源通道灰度实时复制到目标图层蒙版。任务按文档持久化（关掉 1.psd 打开 2.psd 列表为空，重开 1.psd 恢复）。

**关键 API（官方文档确认，勿自造）**：
- 读蒙版：`imaging.getLayerMask({ documentID, layerID, kind:'user', sourceBounds(全文档), componentSize:8 })` → 单通道灰度 imageData
- 写蒙版：`imaging.putLayerMask({ documentID, layerID, imageData(整图尺寸灰度1分量), commandName })`，**不带 targetBounds、不带 replace（默认 replace:true）**，需包 `core.executeAsModal`——⚠️ targetBounds+replace:false 局部写在 UXP 中不可靠（静默失败），参见下方"蒙版同步修复"
- 读样本：`imaging.getPixels({ documentID, layerID, sourceBounds, targetSize, componentSize:8 })` → RGBA(4)/RGB(3)；灰阶亮度 `(r*54+g*183+b*19)>>8`
- 判图层是否有用户蒙版：batchPlay `get` + `_target:[{_property:'hasUserMask'},{_ref:'layer',_id:id},{_ref:'document',_id:doc.id}]` → `hasUserMask` 布尔，可批量放一个 batchPlay 数组（分批 40/批）
- 文档像素尺寸：batchPlay get document → `width._value * resolution._value / 72`（DOM d.width 不可靠）

**同步策略（性能优先兼顾响应）**：
1. 事件驱动防抖 500ms（NOTIF_EVENTS: set/select/clearEvent/delete/make），操作停止后才同步；
2. 内容去重：读源通道 vs 目标蒙版逐像素比较，无差异跳过写回（天然防 putLayerMask→通知→再写循环）；
3. 脏矩形局部写：只把差异 bbox 区域 putLayerMask（targetBounds 定位），大图局部变化写回成本极低；

**持久化**：`settings/mask-sync-state.json`（UXP data folder），`byDocument: { [doc.name]: task[] }`。**关键点：文档重开后 layerId 会变，任务存图层"名称路径"（path: string[]，从根到图层的名称链），切换文档/重开时 `reconcileTasks()` 按路径重解析 layerId，路径失效则置 null（UI 显示占位让用户重选）**。引擎用引用计数（init/dispose 配对）支持多面板实例。

## 蒙版同步修复（同日追加）

**用户反馈 4 点**：①反相文字深灰深色主题看不见；②同步标签+switch 要左对齐；③反相在通道右侧导致两下拉不对齐，要求把反相挪到目标蒙版下方；④**功能没同步成功**，怀疑 imaging API 对蒙版用法错误，让参考 ClearHandler 如何对蒙版删除图案。

**根因（对照 ClearHandler 已验证代码）**：
- ClearHandler 写蒙版是 `imaging.putLayerMask({ documentID, layerID, imageData })`——**整图尺寸**单通道灰度 ImageData，**不带 targetBounds、不带 replace**（默认 replace:true）；
- 我此前用的 `replace:false + targetBounds` 局部写组合在 UXP 中行为不可靠（静默失败）→ 同步不生效；
- ClearHandler 读蒙版 `getLayerMask` 显式带 `sourceBounds`（全文档）+ `componentSize: 8`；文档像素尺寸用 batchPlay 拿 point 值×resolution/72 换算（不是 DOM 的 d.width）。

**修复（MaskSyncEngine.syncTask 重写）**：
1. 文档尺寸改用 `getDocPixelSize`（batchPlay + point×res/72 换算，兜底 DOM width）；
2. getPixels/getLayerMask 显式加 `componentSize: 8`，getLayerMask 加全文档 sourceBounds；
3. 写回改为整图灰度 ImageData + putLayerMask 不带 targetBounds/replace（对齐 ClearHandler.updateLayerMask）；
4. 保留"差异检测无变化则跳过"（防循环+省开销），即只在内容真变化时整图写一次；脏矩形局部写注释保留说明不可靠原因；
5. syncAll 加结果 console 日志（`蒙版同步[任务名]: 已写入蒙版/跳过(reason)`）方便排查。

**UI 调整**：反相 checkbox 从通道行移到"目标蒙版"行下方独立行（右对齐 `.mask-sync-invert-row`）；`.mask-sync-checkbox span` 显式 `color: var(--text-color)`（修深灰）；`.mask-sync-switch` 加 `justify-content: flex-start` 覆盖 adjustment-swtich-container 默认居中（左对齐）。

**经验**：UXP 的 `putLayerMask` 局部写（targetBounds+replace:false）不可靠，项目内已验证路径是整图写；写蒙版/读蒙版都要显式 componentSize:8 与 sourceBounds；文档像素尺寸要用 batchPlay 换算而非 DOM width。

## 蒙版同步修复二（同日第三次）

**用户反馈**：还是不同步，"目标蒙版无论怎么画都是空白的"，让检查写入蒙版的数组；反相文字颜色 CSS 修复无效。

**真正根因（getPixels 数组尺寸错位）**：旧代码 `getPixels({ sourceBounds: 全文档, targetSize: 全文档尺寸 })`——**当样本图层像素不覆盖全文档时（用户画几笔的小图层），sourceBounds 会被 PS 裁剪到图层实际像素区域**，返回数组尺寸 ≠ docW×docH×comps → `comps = raw.length/(docW*docH)` 算出非 3/4 → 'unsupported-components' 静默跳过 → 蒙版从未被写（保持初始空白）。项目标准模式（pixelDataProcessor.processPixelData）是**先取 layer.bounds，再 `getPixels({ sourceBounds: 图层bounds, targetSize: 图层宽高 })`**，两者一致不会裁剪错位。

**修复（syncTask 数据流重写，对齐 pixelDataProcessor）**：
1. `getLayerBounds(docId, layerId)`：batchPlay get layer → bounds（top/left/bottom/right 像素）；宽高 ≤0 视为空图层跳过（'empty-layer'）；
2. `getPixels({ sourceBounds: 图层bounds, targetSize: {width: layerW, height: layerH}, componentSize: 8 })`；comps 用 layerW×layerH 计算；
3. extractChannel 得到图层坐标系通道数组，再按 bounds 偏移映射到全文档数组（图层外=0=黑=隐藏，透明区域对应蒙版黑）；
4. getDocPixelSize 加单位判断：`_unit` 含 'pixel' 直接取 `_value`，否则按 `×resolution/72` 换算（point 文档在非 72dpi 下直接换算会放大 4 倍）；
5. 其余不变（getLayerMask 全文档+componentSize:8、差异检测跳过、putLayerMask 整图写）。

**反相颜色**：CSS 类选择器 `.mask-sync-checkbox span` 在 UXP 中对 label 内 span 不生效（两轮验证），改为 **React 内联 style `color: 'var(--text-color)'`**（内联优先级最高，GradientPicker 的 JS 设 style 也走 var() 证明可行）。

**经验**：getPixels 的 sourceBounds 会被裁剪到图层实际像素区域——**读图层必须先取 layer.bounds 再按 bounds 读，sourceBounds 与 targetSize 保持一致**；否则数组尺寸错位。UXP 里 CSS 类选择器改不动 label 内 span 颜色时直接用内联样式。

## 蒙版同步修复三（同日第四次，终于修好）

**用户截图报错**：`Error: The requested functionality is only allowed from inside a modal scope. See https://www.adobe.com/go/ps_executeasmodal for details.`

**根因**：之前我以为"只有 putLayerMask（写操作）需要 executeAsModal，读操作可以脱离 modal"。**错**——UXP 的整个 imaging API（getPixels / getLayerMask / createImageDataFromBuffer / putLayerMask）都必须在 `core.executeAsModal` 回调内调用，否则一律抛 "only allowed from inside a modal scope"。ClearHandler 之所以正常是因为 `app.tsx` 已经在 executeAsModal 里调用它；我的引擎从定时器/通知回调直接调用，整个流程都在 modal scope 外 → 第一次 `getDocPixelSize`（batchPlay，可能也受影响）后第一个 imaging 调用就抛错 → catch → 'error' 跳过 → 蒙版从未被写。

**修复（syncTask 重构）**：把整个同步流程（读+写）包进**同一个** `core.executeAsModal(async () => { ... }, { commandName: '蒙版同步' })`。modal 内部用局部变量 result 收集 reason，最后同步结果返回给外层；外层仅包 try/catch 做兜底错误处理。这样既符合 UXP 约束，也避免嵌套 executeAsModal（之前在 modal 内调 executeAsModal 也是错误用法）。

**经验**：
- **整个 imaging API 都要在 executeAsModal 内调用**——不仅是 putLayerMask，getPixels/getLayerMask/createImageDataFromBuffer 同样要求。文档里只对 putLayerMask 示例里包了 modal，造成了"只有写需要 modal"的误导。
- 在 UXP 里"独立运行的同步引擎/定时器回调"必须自己包 executeAsModal，不能假设调用方已经在 modal scope 内。
- executeAsModal 不可嵌套（modal 内不能再调 executeAsModal），把读+写放同一个 modal 里是最干净的做法。
