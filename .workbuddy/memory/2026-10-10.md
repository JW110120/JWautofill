## 修复：渐变「不透明度中点」与「颜色中点」共用同一字段（预存在缺陷，非死码清理引入）

### 现象
渐变设置面板里，两个**不透明度色标**之间的 midpoint 拖拽时行为与下方**颜色色标**之间的 midpoint 完全一致
（拖哪个另一个也跟着动），无法独立调整不透明度中点。

### 根因（已用 git 证据定性：不是删除死代码造成的）
- 数据模型里**只有一个** `midpoint` 字段（`GradientStop` / `ExtendedGradientStop`），
  而**颜色插值**与**不透明度插值**函数都读它、两个中点拖拽 handler 也都写它 ⇒ 二者永远联动。
- 证据①：`git diff HEAD` 显示上轮死码清理只删了 `setIsDraggingMidpoint(...)` 这类**从未被读取**的标志位，
  `handleOpacityMidpointMouseDown` 的写入目标（`stops[index].midpoint`）**一字未改**。
- 证据②：`git log -S "opacityMidpoint"` 为空 ⇒ 该字段**历史上从未存在**，即「独立的不透明度中点」从未实现。
- 结论：属**预存在的功能缺失**，与删除死代码无关。

### 修复（统一模式：`midpoint` 只服务颜色，新增 `opacityMidpoint` 只服务不透明度）
- **数据模型**：`types/state.ts` 的 `GradientStop` 与 `GradientPicker.ExtendedGradientStop` 各加 `opacityMidpoint?`。
- **`GradientPicker.tsx`**：两个 opacity 插值函数（preset/非 preset）改读 `leftStop.opacityMidpoint`；
  `handleOpacityMidpointMouseDown` 读写 `opacityMidpoint`；不透明度中点滑块左右定位改用它；
  初始 stops / 新增 stop / 删除归一化 / 预设保存加载 / 缩略图预览 全部带上 `opacityMidpoint`（默认 50）。
  ⚠️ **颜色侧一律保持 `midpoint` 不动**（插值 145/278、handler 1163、定位 1664/1692、预设读写）。
- **`GradientFill.ts`**：`generateTransparencyStops`（发往 PS 原生 `transferSpec` 的中点）改用 `opacityMidpoint`；
  `interpolateGradientColorWithOpacity` 增 `forOpacity` 形参——**灰度/颜色路径传 false（用 midpoint）**，

  PS 任何一次选区/图层操作都会点亮 300~1200ms 忙碌窗口，切文档/打开/关闭/保存会点亮**文档级闩锁**
  （数秒）⇒ 点刷新时撞窗口概率极高 ⇒ 表现为可复现失败。改前是**裸 get**（照样发，多数能成，但会弹框）。
- **修法（保持「忙碌期绝不裸读」策略）**：`HotkeyBridge.ts` 把原 `enumerateBrushes` 拆为
  `enumerateBrushesOnce()`（单次尝试，私有）+ 新的 `enumerateBrushes(opts)`（对外唯一入口）：
  粗筛命中时**不发 get、只顺延等待放行**（每次最多睡 400ms 以便闩锁一释放立刻重试），
  放行后再尝试；总预算 `BRUSH_ENUM_TOTAL_WAIT_MS=4000` + `BRUSH_ENUM_ATTEMPTS=4`，超限交上层重试。
  ⛔ **不用 `bypassCoarseGate` 硬闯**（会在闩锁期把读取排进模态队列、加剧 "Too many modal scope commands"）。
  ⚠️ `detectAllBrushTypes` 内部也调 `enumerateBrushes`（第 814 行），一并受益。

### 2) 枚举失败后刷新按钮不渲染
- **根因**：刷新按钮原为 `{usePicker && (<div className="icon-button">…)}`；枚举失败会 `setUsePicker(false)`
  切手动输入，按钮随之消失 ⇒ 失去「重新枚举」的唯一入口。
- **修法**：`BrushHotkeySection.tsx` 去掉 `usePicker &&` 门控，**始终渲染**刷新按钮。
  图标组恒为 3×28px、该格一直存在 ⇒ 无布局位移；手动输入态点它即再枚举一次，成功自动切回下拉。

### 3) 重名笔刷录制产生两条记录
- **根因**：`startRecord` 只按 **combo** 查重（`entries.find(e => e.combo === combo)`），
  对**同名笔刷换一个键**不查重 ⇒ 直接 append 新条目 ⇒ 列表出现两个「圆头」，同名匹配多键。
- **修法**：`startRecord` 新增「同名笔刷」判定 `sameName = entries.filter(applyBrush && brush===selectedBrush)`：
  · 同名条目**不参与** combo 占用判定（否则自己占自己误报）；
  · 同名已存在 ⇒ **保留首条并替换其 combo**，其余同名条目一并删除（顺带合并历史冗余）；
  · 仅一条且 combo 相同 ⇒ 提示「无需重复录制」。
  手动输入与枚举选择最终都走 `startRecord(selectedBrush)`，两条路径行为一致。
- **另加归一化**：模块级纯函数 `dedupeBrushEntries(list)`（同名 applyBrush 只留一条，
  优先保留已绑定 combo 者；`runFunc`/`toggleMain` 不参与），在 `onConfig` 收到配置时应用，
  有变化则 `pushConfig` 回推落盘 ⇒ 自动修复历史遗留的重复条目。
  ⚠️ 纯函数必须放模块级（避免本仓「组件体内 const 被上方引用 ⇒ es5 var 提升 ⇒ 白屏」的坑）。
  `reRecordEntryById` 也同步做同名合并，口径一致。

## 修复两处：数字输入框文字偏上 + 图案预览不随角度倾斜

### 1) 所有数字输入框文字不在垂直中央（偏上）

- **根因**：UXP 的原生 `input` **不按 CSS `line-height` 做行盒居中**（`line-height:24px` 被忽略）。
  用思源黑体度量反推：墨迹落在「内容盒上缘 + (ascent − capHeight)」= 内容盒上缘 + 5.1px，
  与实测 5px 吻合 ⇒ **原生控件把字体行盒顶在内容盒上缘往下画**，故整体偏上。
  （旁证：`license.css` 老注释已记录「UXP 原生 input 实际绘制区高于其 CSS 盒」。）

### 2) 图案预览不随角度倾斜
- **根因（关键平台事实）**：**UXP 不支持 `<img>` 上的 CSS `transform`**。Adobe 官方口径：
  transform 目前只对 **Border / Outline / Color background / shadow / SVG** 生效；
  加在 `<img>` 上的 `rotate()` 被**静默忽略**（就算开了 `featureFlags.CSSNextSupport: true` 也一样）。
  ⇒ 原 `PatternPicker` 最终预览那行 `transform: … rotate(${angle}deg)` 从来没生效过。
- **修法**：把预览元素由 `<img className="pattern-final-preview">` 换成 **`<svg>` + `<image>`**，
  旋转走 **SVG 的 `transform` 属性**（SVG 核心能力，与 CSS transform 支持无关）：
  - `viewBox="0 0 <容器宽> <容器高>" preserveAspectRatio="none"` ⇒ 1 用户单位 = 1px；
  - `<g transform="translate(cx+offsetX, cy+offsetY) rotate(angle)">`，`<image>` 以原点为中心
    ⇒ 旋转天然绕图片中心；`zoom/scale` 仍按「占比缩放、不放大小图」换算成 `<image>` 的 width/height
    （等价旧 `max-width/max-height` 语义）。
  - `pattern.css` 的 `.pattern-final-preview` 改为 absolute inset 0 + 100%/100%（不再需要 CSS transform）。
- **连带重构**：预览容器尺寸用 `useLayoutEffect` 实测（新 state `previewSize`）；
  预览图原始像素尺寸改由**缩略图 onLoad 捕获**（缩略图与最终预览用同一 URL）存 `previewNaturalRef`，
  因为 `createPatternFromImage` 原来靠 `document.querySelector('.pattern-final-preview').naturalWidth`
  取图幅 —— `<img>` 换 `<svg>` 后该查询失效，故所有 `imgElement.naturalWidth/Height` → `nat.w/nat.h`。
  同时修掉该 onLoad 里一个**既有运行时 bug**：`imageSize: \`${img.naturalWidth}…\`` 引用了不存在的
  `img` 变量（`transpileOnly` 构建查不出），改为先取 `e.currentTarget.naturalWidth/Height`
  （合成事件在 await 后 currentTarget 会被置空，必须提前取值）。

## 第二轮：数字框垂直居中改「移盒子」；图案旋转改「烘像素」（用户实测反馈后）

### 结论一：UXP 的 CSS transform **只有 translate/scale**

## 第三轮：图案旋转预览重设计（外接矩形 + 真透明）；数字框改用「移盒子」

用户反馈：① 旋转后图案看着像**平行四边形、两个角被裁**；② 矩形外的补色在 light 主题下仍是**黑色**、很突兀。
要求：预览边界按「旋转后的实际形状」重设，补外接矩形，**外接矩形内、旋转矩形外必须透明**。

### 根因（两条，都被用户现象直接印证）
1. **旧实现输出与源同尺寸**（`out = width*height*3`，绕中心反向映射）⇒ 旋转矩形的四个角跑到画布外被裁掉
   ⇒ 60° 以上看着就是「平行四边形、缺两个角」。
2. **矩形外用 `--dark-bg-color` 补色**。该变量 darkest 主题 = `rgb(30,30,30)`（近乎纯黑）；
   且旋转图缓存键只有 `图案|角度|灰度`、**不含主题/底色** ⇒ 换成 light 主题后缓存命中不失效，
   那块「黑三角」原样留着 —— 用户看到的正是这个。

### 关键平台事实（本轮定论）
⛔ **UXP 的 `imaging.encodeImageData` 只支持 JPEG**（官方类型定义原文：*must use jpeg/base64 encoding
when assigning to an image element*）⇒ JPEG 无 alpha ⇒ **「透明」在 UXP 里无法由该 API 表达**，
只能自己编码 PNG。UXP 又无 Canvas / 无 zlib ⇒ **手写**。

### 改动
- **新增 `src/utils/pngEncode.ts`**：极简 PNG 编码器（colorType=6 RGBA8）。
  - CRC-32 查表 + Adler-32 + 手写 chunk（IHDR/IDAT/IEND）；
  - deflate 只发**存储块**（BTYPE=00，每 64KB 5 字节头）：零依赖、零算法风险、膨胀仅 ~0.008%
    （固定 Huffman 反而 8~9bit/字节更大）；数据量由调用方封顶；
  - `bytesToBase64`：分块 `String.fromCharCode` + 一次 `btoa`（UXP 有 `btoa`）。
- **`PatternPicker.rotatePatternPreview` 重写**：
  - **输出 = 旋转后矩形的外接矩形**（`|w·cos|+|h·sin|` × `|w·sin|+|h·cos|`），
    长边封顶 `MAX_ROTATED_PX=512`（45° 时外接矩形是原图 1.41 倍；封顶同时锁死重采样开销与体积）；
  - 旋转矩形之外 **alpha=0**，不再补任何底色 ⇒ 与主题无关，缓存键也无需带主题；
  - 采样改 **双线性 + 预乘 alpha**：预乘避免「透明像素的脏 RGB」混出黑边；越界按「完全透明」参与
    （不是 clamp 边缘像素，否则会拖出边缘色带）；边界自然得到 1px 抗锯齿；
  - 去掉了 `readPreviewBackground`（整函数删除）与 `imaging.encodeImageData` 依赖，函数改**同步**返回 `{url,w,h}`。
- **渲染侧尺寸**：旋转图自然尺寸 = 外接矩形，比原图大 ⇒ 新增 `natScale = 原图自然宽 / 数据宽`
  把外接矩形换算回原图尺度（不换算就会被当 1:1、显示尺寸突增数倍）；
  参考系（未旋转=nat / 已旋转=外接矩形换算值）都走 `min(1, 容器内 contain)` ⇒ **斜角下整体缩小以完整展示**，
  角度回 0 时无缝接回原尺寸。`rotatedPreview` state/缓存值加带 `w/h`。
- `pattern.css` / TSX 里 3 处过期注释（「切换角度大小不变」「四角补底色」）同步改写。

### 自建台架（本轮新增，可复跑）
- `outputs/_png_probe.cjs`：把 `rotatePatternPreview` 的**源码片段**从 tsx 里取出（只剥 TS 形参/返回类型标注）
  → 直接跑真实代码，覆盖角度 0 / 45 / 118 / 灰度3通道 / 全透明源 / 无数据 6 组；
  前置：`tsc src/utils/pngEncode.ts --outDir outputs/_png --target es2017 --module commonjs`。
- `outputs/_png_verify.cjs`：用 **Node 自带 `zlib.inflateSync` + `zlib.crc32`**（与被测实现无关）解回 PNG，
  逐 chunk 校验 CRC、反滤波后核对 alpha —— 等价于「有独立解码器的端到端验证」。
- 结果：角度 0 **逐字节无损**；45° 四角 alpha=0、四条边都有不透明像素（外接矩形贴边=没裁角）；
  118° 竖图不透明占比 45.3%（= w·h/(外接矩形面积)，与推导吻合）；3 通道源矩形外同样透明；全透明源全 0。
- 体积参考：512×391 → PNG 801KB（base64 ≈1.07MB）；120×40 → 19KB。

### 校验
- `webpack --mode=production` 通过（仅 3 条既有体积告警）；`css_comment_check.cjs` 9 文件结构完好。
- `tsc`：`src/utils/pngEncode.ts` **零错误**；`PatternPicker.tsx` 仍只有既有 8 条（photoshop 模块 /
  currentBgColorRef / originalFormat / patternName / Select props）。
- 产物反查：`readPreviewBackground` 归零 ✅；`data:image/png;base64,".concat(…)` ✅；IHDR/IDAT 块类型字节 ✅；`[0]=137` ✅。
