## HUD 显示错误根因（已定位，与断流无关）

`smooth_engine.c:3217` `DWORD pktAge = (DWORD)(now - (DWORD)g_snMs);`
`now` 是 worker 线程读的，`g_snMs` 由 PS 线程（detour）更新；跨线程竞态下 `g_snMs`
可能比 `now` 大十几 ms ⇒ **无符号下溢**成 ~4.29e9 ⇒ `pktAge < HUD_IDLE_MS(250)` 为假
⇒ `activeNow=0` ⇒ HUD 该显示却不显示。
日志铁证：`[hud] 未显示: ... active=0(t=4294967280ms) gate=1(toolOk=1 penDown=1) ...`
（4294967280 = 2^32−16；同一行 gate=1 说明笔正落纸面）。13 笔里出现 6 次以上。
同坑另两处：`smooth_engine.c:3173`（snAgeG）、`:2762`（ageP）。
修法：`(LONG)(DWORD)(now - (DWORD)g_snMs)` 有符号比较（负数=刚有包=活跃）。

### 「画了圆弧但选区线不出现」= 拉绳模式的固有行为（不是 bug）
拉绳 = **定长绳**：`dist ≤ rope` ⇒ **输出点完全不动**（见 MEMORY 铁律）。
用户半径 40 逻辑 px，笔在半径内游走时输出点原地不动 ⇒ 交给 PS 的是一串**相同坐标**
⇒ PS 无从画线；等累计位移超过绳长，输出点才开始跟随（恒定滞后 rope）
⇒ 用户眼里就是「那条弧线忽然一次性出现」。**标准模式（mode=0）没有这个现象。**
⇒ 想边画边看线，要么用标准模式，要么把半径调小。（HUD 的「圆心 vs 光标」正是这件事的可视化。）

## 其他算法要点

- **坐标写回 = 逐轴仿射**：`X_out = X_in*ctx[0x1014] + ctx[0x101c]`，Y 同理（`0x1018`/`0x1020`）；
  写回包偏移 `ctx[0xfe8]`/`ctx[0xfec]`（`-1` = 无此字段）。
- **速度 = 平方距离 EMA（不做 sqrt）**：`ema += alpha*(d² − ema)`，`alpha = ctx[0xc80]`；另维护 max 与 sum。
- **抬笔时 1.0px 硬死区**：`|Δx|<1 && |Δy|<1` ⇒ 输出**吸附到上次滤波输出**并返回 0（调用方不写回）。
- **`ctx[0x260]` = 加锁原子发布的「整数像素」滤波输出** ⇒ **Overlay 画辅助线的数据源**（辅助线基于滤波后点）。
- **包内无坐标时回落 `GetCursorPos`**（与 JWautofill「采样源=系统光标」同思路）。
- **同步守卫**：`ctx[0x1034]` 每包 ++，为 0 即报 `ERROR: sync problem!`；`ctx[0x102c]/[0x1030]` = 坐标替换次数/预算。
- **脚本化滤波 DSL**（`PenOps::setDistortionExpression`）：用户可写表达式（变量 `x,y,ox,oy,s,ss`，函数 `mix`,`smoothStep`）。
  - `speed smooth` 族：`g = 1 − smoothAmount*smoothStep(minSmoothSpeed, maxSmoothSpeed, ss)`，带 `inertiaAccel/inertiaDecel` 非对称惯性。
  - **`Dynamic/weighted.xml` = 质量-阻尼二阶滤波**：`a=F/m; v=(v+a)(1−drag); o+=v` ⇒ 输出有速度连续性，**急转向处优于一阶**，值得 JWautofill 试。

### ★★ 坐标口径 —— 代码级铁证（推翻一切猜测）

`FUN_18000ea30` = `LNP::WTPktUtil::prepareCoordTransform`：
```c

if (|xc,yc| != lcSysExt) log "WARNING: screen size != lcSysExt";
```

偏移归属用日志格式串反推、逐个精确对上（`lcOutOrg→0xa4`、`lcOutExt→0xb0`、`lcSysOrg→0xcc`、`lcSysExt→0xd4`，基准互差 0xF40）。

### ★★ 断流机制（本轮核心结论）

LNP 的输入面 = **Wintab×7 + Windows Ink×3 + GetCursorPos + 消息泵×4**，三条收敛到同一滤波分发
`FUN_18002a0d0`：
- Wintab：`WTPacketsGet`(×4 detour) / `WTPacket` / `WTDataPeek` / `WTGetA` / `WTGetW`
- **Windows Ink**：`GetPointerPenInfo` / `GetPointerPenInfoHistory` / `GetPointerFramePenInfoHistory`
- 光标：`GetCursorPos`（`FUN_180027e80` 队列回放 + 就地改写）
- 消息泵：`PeekMessageA/W` `GetMessageA/W`（`FUN_18000fb00` = messageHandler）

`FUN_18002c260` = WM_POINTER 统一入口：入参 `POINTER_PEN_INFO*`（sizeof `0x78`=120，与历史数组步长吻合），
HIMETRIC→像素（`ctx[0x278]/0x27c`，由 `FUN_18002c140` = `initWMPointerRange` 算），滤波后
**就地改写** `ptPixelLocation`(0x20)/`ptPixelLocationRaw`(0x30)/`ptHimetricLocation`(0x28/0x38) + 压力(0x68)。

关键日志事实：`SM_PENWINDOWS: 0`（无 Wintab provider）+ `SM_TABLETPC: 1` ⇒ **本机 PS 笔输入实走 Windows Ink**。
⇒ 断流场景（calls 涨/packets 冻/**笔迹照画**）自洽：PS 走 Windows Ink 照画，LNP 挂着 GetPointerPenInfo 所以不断；
**JWautofill 只挂 WTPacketsGet ⇒ Wintab 一停就彻底瞎**。这不是 bug，是**只押一条通道**。

其他可抄机制：
- `GetPointerPenInfoHistory` 一次交付**整帧历史**（每样本带 `dwTime`）⇒ 补齐时间线，比 GetCursorPos 拟合精确且**带压力**。
- `FUN_18002a6e0` = `interpolatePkts`：**在 app 缓冲内插值增包**（先 memcpy 到临时缓冲防自读自写），
  上限 = app 传的 `maxPkts`（`ctx[0xef0]`），超限报 `ERROR: maxPktsOut` 并放弃；1px 收敛即停。
  ⚠️ `WTPacketsGet` 返回的包数**可能大于驱动给的**。
- 消息**扣留/重放**：抬笔 `WM_LBUTTONUP` 被改写成 `0x84`(WM_NCHITTEST) 暂存，插值补完后 `PostMessageA` 补发。
- **Wintab 重载自愈**：`0x7ff7` 分支比对模块句柄 → 重取上下文 + 释放/重分配包缓冲 + 重算仿射。

### B. 过冲根因：恢复冲包**按包数拦不住**（决定性）

```
[18:19:37.939] [dead] 恢复：包流恢复（断流约 5531 ms；★冲包量=48 包
                       （≈驱动队列容量 ⇒ 停摆期是「攒着」不是「丢」）…）
```

统计量直接判了旧守卫的死刑：

| 指标 | 全日志分布 | 结论 |
| --- | --- | --- |
| `最大单次=N` | `0×174`、`1×1`、`3×3`、**`4×54`**、`5×1` | PS 每拍最多只要 4~5 包 |
| `≥25包次数` | 恒 `0`（233 次采样） | 单次包数门限**永不到达** |
| `丢冲包` | 恒 `0`（239 次采样） | ⇒ 守卫是**死代码** |

48 包的恢复冲包被 PS 拆成**十几拍**、拍拍 <25 ⇒ 全部原样放行：
补流已把笔尖喂到**当下**，驱动再把 **240ms 前**的旧坐标追加在后面 ⇒ 选区路径**倒退再猛追** = 过冲。

## 第十八轮（0x0111 → **0x0112**）：接上 `'slct'` + 过冲判据重做 ★★

### A. `'slct'` 进程内工具闸门（新文件 `native/PiSmooth8li/ps_tool.c`，≈300 行）

反编译证据源 = `MouseHookPro64.dll` 的 `PluginMain`(`0x18002eb40`) /
`AcquireSuites`(`0x18002ea20`) / `PSSelectEventCallback`(`0x18002e800`)。

- `SPBasicSuite = md+0x18`、`self = md+0x08`（照 `SPMessageData`）。
- 三套 suite：`sPSActionReference df135117-c769-11d0-8079-00c04fd7ec47` /
  `sPSActionControl bc1e4d70-f953-11d0-8d9f-00c04fd5f7ee` /
  `sPSActionDescriptor df135115-c769-11d0-8079-00c04fd7ec47`，**version = 整数 2**。
- 注册 `ctrl+0x20(refcon, 'slct'=0x736c6374, proc)`；注销 `ctrl+0x28(refcon,'All '=0x416c6c20)`；
  释放 `basic+0x08(uuid, 2)`。
- 偏移：`desc+0x28` GetCount、`+0x18` GetKey、`+0x10` GetType、`+0x100` GetReference、
  `ref+0x18` GetDesiredClass、`ctrl+0x18` TypeIDToStringID。
- 工具判据：条目 `GetType()=='obj '`(`0x6f626a20`) → 取引用 → 取类名 → `strstr(buf,"Tool")`。
- ⛔ 方法指针**返回类型一律 `short`**（LNP 只读 `ax`）；引用槽**给足 16 字节**
  （LNP 用 `longlong[2]`，少给就是栈越界写）。
- 闸门值 = 工具名含 `lasso`？1:0 —— 与面板 `App.isLassoTool()` 的 `/lasso/i` 逐字同义。
- **三态接管**（宁可不用不可误用）：`0=不可用`/`1=已注册未读数`/`2=已接管`。
  只有 `2` 才让面板停轮询；任何一步失败退回旧行为（fail-open）。
- 有效性实测：LNP `log_photoshop.txt` 里 `16:29:37 setPSTool(): PS tool name: lassoTool,
  type: 21, enabled: 1` + `App path: …Adobe Photoshop 2026\Photoshop.exe`

### B. 过冲根因：0x0111 的「陈旧回包合并」是**死代码**（真机定案）

真机：150/151 次采样 `陈旧包=0` 恒成立、`陈旧回包合并` 一次没触发、`丢冲包=0`。

- 根因① **护栏② 用「陈旧幅度」反推「时间基是否相同」**（`|now−pkTime| ≤ 5000`）。
  停摆 13281ms / 111188ms ⇒ 恢复包**天生** 13s/111s 旧 ⇒ 判「不同基」⇒ 整条放弃。
  ⛔ 量纲混淆：「包有多旧」≠「时间基是否一致」。
- 根因② 护栏① 窗口以「补流结束」为起点（3s），真机补流 `18:33:51.077` 结束、
  恢复 `18:34:01.610` = **10.5s 后** ⇒ 窗口早过。

**0x0112 修法（三条）**：① `g_pkBaseOk` 用**正面证据**（见过 `age ≤ 400ms` 的包 ⇒ 同基，
此后前沿比较不受幅度限制）；② `g_lastRecovMs` 把窗口改成「停摆恢复后 4s」
（`prevRealAge >= RI_STALL_MS(250)` 打点，**必须在更新 `g_lastRealMs` 之前取**）；
③ 新增按包龄判据（`age > RI_PKT_STALE_MS(1500)`），覆盖「停摆期没补流」那条路。
两条判据**并列**，只丢队首连续段，三道护栏任一不成立**一个字节都不动**。

### C. modal scope 暴涨根因：300ms 巡检**恰好把预算吃满**

`MIN_MODAL_GAP_MS=300` ⇒ 上限 3.3/s，面板工具巡检**就是 300ms** ⇒ 请求率 ≈ 上限。
叠加自动填充（本身必弹模态）即超吞吐；低配机填充更久 ⇒ 叠加窗口更长 ⇒「暴涨」。
停掉即解除：`syncSmoothToolWatch()` 里 `toolSrc===2` ⇒ 不建/停表；
`applyToolGate()` 开头 `return`（**唯一咽喉**：`pollSmoothToolGate` 与 `pollToolChange`
都走它）；`write_params()` 接管后不再写 `I_TOOLGATE`（两边都写 = 互相覆盖）。

### D. 自查出的静默缺陷（值得记档）
