## 修复「快速连续删除图层」弹出「易修: 命令"获取"当前不可用」

### 根因
PS 通知（delete/make/set）在命令执行**中途**派发，此刻 UXP DOM 属性
（`app.activeDocument` / `doc.layers` / `layer.name`）是惰性的，每次读取都向宿主发
`get` 描述符；撞上忙碌窗口被宿主拒绝 → 弹原生框。
**该弹框绕过 JS try/catch 与 `_options.dialogOptions`，唯一有效防护是「不发 get」。**
既有 `psProbe.ts`(提交 f8a2073) 只覆盖 4 处组件蒙版探测，删除图层另有一条**未防护**
主因：`AdjustmentPanel.tsx:480` 在通知回调里同步读 activeDocument + 递归遍历整棵
图层树做签名对比（80ms 防抖只护住了后面的刷新，覆盖不到这三行）。

### 改动（3 文件，+227/−62）
1. **`src/utils/psProbe.ts`**：新增忙碌守卫 `markPsBusy` / `isPsBusy` / `psBusyRemain`，
   以及 `runWhenIdle`（顺延不丢弃，给"必须执行一次"的场景；本次未接入，备用）。
2. **`AdjustmentPanel.tsx`**：
   - 第一处 effect：回调内三行同步读取**全部移入防抖**；签名对比改由
     `debouncePsProbe(PROBE_IDLE_MS)` 承载；`if(timer) return` 的节流改为真防抖（顺延）。
   - 第二处 effect（文件树刷新）：`if (timer) return` 节流 → `debouncePsProbe`。
     **原节流是主因之一**：首个事件锁死窗口、后续删除事件被丢弃，刷新恰好落在忙碌期。
   - 新增 `PROBE_IDLE_MS = 300`（原 80/120/200 偏短，连续删除时静默期常被打断）。
3. **`MaskSyncEngine.ts`**：`handleNotification` 里的同步 `refreshActiveDoc()` 移入定时器
   （新增 `scheduleSync(delay, checkDocFirst)` 参数）；`doTimedSync` 入口加 `isPsBusy`
   闸门（事件与轮询的共同收口点）；2s 轮询 tick 前加 `isPsBusy` 闸门——轮询与用户操作
   完全异步，是"有一定概率"弹框的关键来源。

### 踩坑（3处，均已修）
- **TDZ**：`const scheduleStructureProbe` 必须在 `handleNotification` **之前**定义，
  否则回调执行时抛 ReferenceError。
- **忙碌窗口自我延长**：`markPsBusy` **不可**放在探测函数体内/其被复用的路径上
  （探测自身再次触发 → 一直等不到空闲）。只在**事件到达瞬间**打标记。
- **守卫自锁**：`doTimedSync` 入口查 `isPsBusy`，故调用方（轮询）**不可**先
  `markPsBusy` 再调它，否则同步永不执行。窗口改由 `doTimedSync` 通过守卫后自己预留。

### 铁律补充
「通知回调内禁止任何同步 DOM 读取」；防护只能加在**发起 get 之前**，
加在 try/catch 之后无效（宿主弹框不经 JS 异常通道）。

### 验证
`webpack --mode=production` 通过（3 warnings 为既有体积告警）；
`tsc --noEmit` 对本次改动标识符零报错（注意 ts-loader `transpileOnly` 不做类型检查，
必须另跑 tsc）；三个文件行尾仍为 LF。

## 修复两个 UI Bug（线稿参考下拉层级 + 同步按钮 hover）

### 前置：按铁律先加载项目技能 `.workbuddy/skills/uxp-frontend-spec/`（改样式前必做）

### Bug 1：线稿参考下拉与特殊木刻数字框的遮挡/反转
**根因不是 z-index / stacking context**（`.select-pop` 早有 `z-index:99998` + portal 挂面板根）。
真因是 Adobe 官方 UXP 硬限制：**`input[type=number]` 无视 z-index 永远画在最上层**
（"Text fields and areas will always render the text editor above everything else"），
所以 `popOverlay.ts` 采用官方出路②：把与菜单**相交**的输入框 `visibility:hidden`。
错在**判定矩形**与真实菜单不匹配，两头发散：
- `update()` 原取 `Math.max(measuredH, fallbackH)`，而 `estimatePopRect` 兜底高度
  `min(200, max(90, n*24+12))` 有 **90px 下限** ⇒ 短菜单（2/4/6 层）判定带被撑到 90px
  → 菜单没盖到的数字框被误判相交 → **无谓隐藏**；
- 7+ 层时真实菜单被 CSS `max-height:200px` 截断，判定带封顶同样 200px 但**起点/覆盖范围错位**
  → 菜单溢出判定带 → **数字浮在菜单上方 = 层级反转**。
- 「5 层恰好正常」正是 `max` 恰与真实值重合的巧合，佐证此根因。

**改法**（`src/utils/popOverlay.ts`）：① 高度改为**实测优先**（`measuredH >= 8` 就只用实测，
仅退化时退兜底），判定带贴合真实菜单；② `PAD` 由 **8px 降到 2px**（原值会把菜单外露的数字框
也圈进遮挡带）；③ 新增 `POP_MAX_HEIGHT = 200` 常量（与 common.css 的 `.select-pop{max-height}`
对齐，**改 CSS 必须同步改这里**），把判定带裁到菜单**可见范围**（溢出部分被 `overflow-y:auto`
裁掉、屏幕上不存在，绝不能计入遮挡）；④ 兜底公式改`min(200, n*24+6)`（24=行高，6=padding+描边），
去掉 90px 下限。

### Bug 2：蒙版同步「同步一次」按钮无 hover
**根因不是缺 hover 规则**（`common.css` 早有 `.icon-button:hover .icon-fill`），
而是 `SyncIcon`（`src/styles/Icons.tsx`）两个 path 写成 **内联 `fill="currentColor"`**，
内联属性优先级高于样式表 `fill` ⇒ hover/禁用规则对它**静默失效**。
对比 `DeleteIcon` 用 `className="icon-fill"` 故正常。`SyncIcon` 全仓仅此一处使用，改动零波及。
→ 两个 path 改为 `className="icon-fill"`，走既有 hover/禁用通道。

### hover 四态补齐（common.css `.icon-button`）
- 基础类加**占位透明描边** `border:1px solid transparent`（UXP 禁 outline；无占位则 hover 出边框时内容偏移 2px）
  + `transition`（背景/边框/颜色/缩放）；`.icon-button:hover` 补 `background:var(--hover-bg)`、
  `border-color:var(--primary-color)`、`color:var(--hover-icon)`，与 `.action-button-*` 观感统一。
- ⚠️ **禁用态必须反向覆盖** `.icon-button-disabled:hover`（清底/清边/回灰/`transform:none`）：
  二者同为单类选择器，靠**写在后面**取胜，否则禁用按钮悬停仍亮主色、看着像可点。
- 尺寸影响：`.icon-button` 有固定 24×24 + `box-sizing:border-box`，占位边框不改变外部尺寸，全仓 10+ 处复用安全。

### 验证
`webpack --mode=production` 通过（3 warnings 为既有体积告警）；`tsc --noEmit` 零报错；
CSS 规则顺序已复核（禁用态 1588 晚于 hover 1462）；三文件行尾仍 LF。

## Bug 1 补充修复：遮挡**实时性**（展开状态下增删图层不刷新）

### 背景
上一轮修了「判定矩形与真实菜单不匹配」，但用户实测反馈**实时性**仍有问题：
展开菜单后增删图层，数字框显隐停留在展开那一刻，必须折叠再展开才刷新。
本轮进一步发现**两个独立根因**（第二个只影响「最下方的边缘强度」，
正好解释「色阶数/边缘阈值已正常、唯独最下行失效」）。

### 根因 A：`update()` 的提前 return 跳过还原 ⇒ 隐藏态残留
`popOverlay.ts` 原 `if (w <= 0 || h <= 0) return;` **直接返回，跳过了下面的还原分支**。
UXP 偶发返回退化尺寸时，本轮update 提前退出 ⇒ 上一轮 hidden 住的输入框**永远留在隐藏态**，
直到整个会话 restore（即折叠菜单）才恢复。同源缺陷还有 `querySelectorAll` 抛错分支的裸 `return`。
→ 改为**先`restore()` 再退出**（三处退化路径统一）。

### 根因 B：菜单**自身滚动**不触发遮挡重算（只影响最下方一行）
`Select.tsx` 的 `onScroll` 原对 pop 内部滚动**直接 return**
（`if (popRef.contains(e.target)) return;`）。但 `.select-pop` 是 `max-height:200px + overflow-y:auto`，
**7+ 层时必然出现内部滚动条**：滚动会改变「哪些选项真正可见」⇒ 改变下方输入框是否被覆盖。
离菜单底边**最近**的那一行（边缘强度）因此在滚动后显隐不实时 —— 与用户观察精确吻合。
→ 改为：pop 内部滚动也调 `occlusionRunRef.current?.()`，并按帧合并（scroll 触发频率高，
逐次重算会白跑 DOM 测量）；面板滚动分支也补一次（`reposition` 对 <1px 去重，pos 不变时 effect 不重跑）。
新增 `occlusionRunRef` 把遮挡 `run` 暴露给滚动回调复用，cleanup 时置 null + 取消 rAF。

### 连带修复（我自己引入的缺陷）
- ⚠️ **上轮编辑引入了 2 个真实 NUL 字节**（U+0000）到 `Select.tsx` 的模板字符串里，
  成了字面分隔符。已清理，并改用**可见分隔符** `|` 与 `~`（脆弱的不可见控制字符不要用于拼接）。
  检测方法：`node -e` 扫字节统计 NUL/控制符（grep 会把文件当binary，`grep -c $'\0'` 会给出误导性的 255）。
- ⚠️ **TDZ**：`occlusionRunRef` 必须声明在 `onScroll` **之前**（`const` 暂存区，同一次渲染中先于声明调用会抛
  ReferenceError）。我第一版放在 effect 之后，已上移到 hooks 区（第74 行）。

### 根因 A/B 的定位方法（可复用）
「部分元素正常、部分不实时」⇒ 不要只看 DOM 深度（三个输入框结构完全一致），
而要问**哪个输入框离菜单边界最近** → 指向「菜单自身滚动改变了可见范围」这条路径。

### 验证
`webpack --mode=production` 通过；`tsc --noEmit` 零报错；两文件 NUL/控制符均为 0、仍为 LF。
**用户已回退 common.css 的改动**（`git diff src/styles/common.css` 为空）——
Bug 2 只保留 `Icons.tsx` 的 `SyncIcon` 改 `icon-fill`（图标变色生效），
背景/边框 hover 反馈已随回退移除；如需恢复须做成**局部类**，不得再动全局 `.icon-button`。

## Bug 1 三次修复：7+ 层时菜单挡住边缘强度但数字始终显示

### 用户实测证据（决定性）
「≥7 层时菜单确实挡住边缘强度数字框，但数字始终显示；折叠展开、增删图层实时性都试过。」
这直接否证了我前两轮的方向：**不是实时性、不是还原残留，而是判定矩形算短了**。

### 按截图反推的真实尺寸（面板 250px，截图 342px ⇒ 缩放 1.37）
| 场景 | 菜单高 | 反推行高 |
|---|---|---|
| 3 项 | ≈68px | ≈22.7 |
| 6 项 | ≈175px | ≈29.2 |
| 7 项 | ≈192px | ≈27.4 |
| 9 项 | **≈218px** | ≈24.2 |
⇒ **菜单真实高度超过 CSS `max-height:200px`**（9 项 218px），证明 **UXP 下该上限并未把菜单裁到 200**；
  真实行高在 24~29 之间波动（font-size:12 + padding 4×2，但 UXP 行盒高于 12）。

### 我的错误（两轮都是错的方向）
1. 第一轮：取 `max(实测,兜底)`，兜底带 90px 下限 → 短菜单**无谓隐藏**（方向对了一半）。
2. 第二轮：改成"实测优先" **并加 `if (h>200) h=200` 硬裁** —— 这条裁剪是**错的**：
   判定带被压到 200 < 真实 218px ⇒ 边缘强度落在带外 ⇒ 判不相交 ⇒ **明明被挡住却不隐藏**。
   我当时假设"菜单会被 max-height 裁掉、溢出部分是滚动不可见区"，被实测直接证伪。
3. 兜底行高沿用 24 也偏低，菜单越长低估越多（9 项差 ≈36px）。

### 正确结论（务必记住）
- **不要在遮挡判定里按 CSS `max-height` 裁剪**。判定带必须 **⊇ 屏幕上真实存在的菜单区域**，
  宁可略高（多藏一个刚出界的输入框，下一帧即还原）也**不可略低**（直接穿帮）。
- 兜底高度：`optionCount * 28 + 8`（行高按实测取 28 偏保守，chrome 8 留余量），**不封顶**。
- 实测阈值从 `height>=24` 放宽到 `>=8`（24 会被真实 24~29 的行高误判为"没量到"）。
- 宽度同样"实测优先 + 退化用 pos.width"，横向也不可只信实测。
- 已删除 `POP_MAX_HEIGHT` 常量（其"与 CSS 双写"的注释是误导，实测证伪）。

### 方法论教训（本次最值得记的一条）
前两轮我都在**源码里推演**"菜单应该被裁到 200"，而没有去质疑这个前提。
用户提供"**看起来挡住了，但数字没藏**"这一矛盾现象后，反推才暴露真因。
⇒ 当"视觉重叠"与"代码判定结果"矛盾时，**先怀疑自己的几何假设**，用可观测事实
（截图反推尺寸 / 矛盾现象）去校准，**不要在假设上继续叠加补丁**。

## 笔刷列表启动首刷：加 PS 忙碌窗口防护（用户确认「保持现状」不做自动类型检测）

### 先纠正一个误判（记录以免重犯）
用户问「是否有必要加载插件时自动执行一次刷新笔刷列表」——**自动刷新本来就存在**
（`BrushHotkeySection.tsx` 的 `useEffect` 里 `loadBrushes(false, false)`），并非缺失。
用户随后反馈「**有笔刷名但没图标**」⇒ 枚举其实**成功了**，所以「延后+空结果重试」
那套方案**解决不了**（无失败可重试）。真实链路：
`loadBrushes(notify, detect)` 只有 `detect=true` 才调 `detectAllBrushTypes()` 填 `brushTypes`；
启动传 `detect=false` ⇒ `setBrushTypes({})` ⇒ `tag: brushTypeTag(brushTypes[b] || '')` 为空 ⇒ 无图标。
手动刷新传 `loadBrushes(true)`，`detect` 默认取 `notify`=true ⇒ 类型被检测 ⇒ 图标出现。
**这是当年刻意的设计**（`detectAllBrushTypes` 会逐支 selectBrushForDetection 切换用户当前笔刷、
包在 executeAsModal 里，属改动文档状态），已向用户说明并由用户拍板**保持现状**。

### 本次实际改动：只加忙碌窗口防护
1. `src/hotkey/BrushHotkeySection.tsx`
   - 首刷由裸调用改为 `initialLoadRef.current?.()`（runWhenIdle 调度，空闲后才发get）。
   - 新增 `brushesRef` 镜像 `brushes`：**重试循环要判断本次枚举是否拿到笔刷，
     而 setBrushes 异步、闭包里 `brushes` 是旧值**，必须读 ref（沿用文件内
     `entriesRef`/`daemonConnectedRef` 的既有模式）。
   - 有限静默重试：最多 `INITIAL_LOAD_ATTEMPTS=3` 次、间隔 500ms×n 递增、**全程 notify=false**
     （静默不打扰，只有手动刷新才给反馈）。
   - unload 时 `initialLoadRef.current?.cancel()`，避免面板已卸载仍发 get。
   - ⚠️ 调度器用 **`useRef` + 懒初始化**持有而非 `const`：`runWhenIdle` 每次渲染返回新函数，
     用 const 既是 TDZ 隐患（useEffect 回调在声明前定义）也会在重渲染时丢调度。
   - 常量：`BRUSH_LOAD_IDLE_MS=600` / `ATTEMPTS=3` / `RETRY_MS=500` / `MAX_DEFERRALS=5`。
2. `src/utils/psProbe.ts`（`runWhenIdle`）
   - 新增第3参 `maxDeferrals`（**0=不限**）与内部 `deferrals` 计数。
   - ⚠️ **修掉一个我自己埋的隐患**：原实现忙碌时 `wrapped()` **无限自我重排**且永不放弃
     ⇒ PS 持续忙碌时该任务**永不执行**（对「启动加载」这类一次性任务等于功能永久缺失）。
     现在超限后直接执行：宁可承担一次被拒绝的风险，也不能不做事。
     铁律：**「不做就永久缺功能」的调用必须传有限 maxDeferrals；「周期性探测」才可传 0。**

### 铁律
- UXP 里凡 `batchPlay get`（枚举笔刷/presetManager、读图层名、getDocPixelSize…）在
  **插件启动期**都有很高概率撞上忙碌窗口；启动期的一次性加载**必须**走 runWhenIdle 守卫。
- 排查「刷新一下就好了」类问题要先分清是**枚举失败**（列表空）还是**下游数据缺失**
  （有名字无图标）——两者根因与修法完全不同，**别一律当成时机问题**。

用户要求按下时有可见变化，且**明确不要边框和背景变化**；并指出"按下前基本已经 hover 了"，
故新颜色必须比 hover 更深才看得出差别（现有 `:active { transform: scale(0.94) }`

## ToggleSwitch 形状修正：加长 5px + 修「纺锤形/音频波凸起」

### 用户反馈（截图对照目标图）
「形状有点不美观」：① 长度 +5px；② 左右两端有「像音频波一样的小凸起」，
且两端是**尖的**，希望是**完美半圆**，「不希望 switch 看起来像个纺锤」。

### 根因（三处，缺一则形状不完美）
1. **`border-radius: 999px` 在 UXP 下未被按「高度一半」解析成胶囊** ⇒ 实测渲染接近矩形、
   两端尖角 → 纺锤感。**UXP 圆角一律写显式数值**，并补 `-webkit-border-radius`。
2. **伪元素溢出容器 → 两端鼓包（"音频波"）**：`.toggle-switch` 占位盒原为 28px，
   而伪元素胶囊 `width:28px` 但两端圆角解析失败 ⇒ 溢出部分在左右各鼓出小三角。
   **铁律：占位盒宽必须 == 伪元素胶囊宽**，否则必现两端凸起。
3. 伪元素用 `:before` 而非独立元素，在 UXP 下与父级圆角/裁剪叠加时更易出边缘瑕疵
   （保留 `:before` 方案，仅靠「同宽 + 显式圆角」修正，避免改成真元素带来的盒模型变动）。

### 改动（`src/styles/common.css` + `ToggleSwitch.tsx` 注释同步）
| 项| 旧 | 新 |
|---|---|---|
| 胶囊宽 / 占位盒宽 | 28px | **33px**（+5，两处必须相等） |
| 胶囊圆角 | `999px` | **`8px`** = 16px 高的一半（+ `-webkit-` 前缀）|
| 圆点右移位| `left:14px` | **`left:19px`** = 33−12−2 |
| 圆点圆角 | `50%` | `50%` + `-webkit-border-radius:50%` |

几何自检（脚本验算）：圆点开启态左留白 19 / 右留白 2 ⇒ 圆点贴右端，
与目标图 2 一致；`19+12=31 ≤ 33` 不越界；`8 = 16/2` 完美半圆。

### 铁律
- **UXP 圆角不写超大值**（`999px`/`9999px` 不会被解析成胶囊），写**显式像素值= 高/2**。
- **伪元素绝对定位做"胶囊本体"时，父占位盒的宽高必须与伪元素完全一致**，
  否则溢出端会出现小凸起（本次"音频波"现象的真凶）。
- 改胶囊长度时**必须同步**圆点位移 `left`（= 胶囊宽 − 圆点 − 内边距），否则圆点不贴端。

### 验证
`webpack --mode=production` 通过；无 `999px` 残留（仅注释提及）。待用户实测形状。

## 折叠/展开在大量图层下卡顿、点击无响应（性能优化）

### 根因（四条，均作用于主线程）
折叠代码本身开销极小；卡顿来自与**图层数成正比**的路径在点击到达时被叠加执行。
关键前提（项目既有铁律）：**UXP 的 `layer.id`/`name`/`kind`/`layers`/`isBackgroundLayer`
每读一次都是一次向宿主的同步 IPC `get`** ⇒ 遍历 N 层树 ≈ 3N~5N 次同步往返。

1. **三处独立实现的全树遍历同时在跑**（同一棵树、同一类哈希，各走一遍）：
   - `MaskSyncEngine.docSignature()` —— **2 秒兜底轮询无条件执行**（3 次读/层）
   - `AdjustmentPanel` 的 `scheduleStructureProbe` → `computeLayerSignature`（3 次/层）
   - `refreshLineReferenceOptions` → `buildLineReferenceOptions`（4 次/层）
   ⇒ 500 图层时稳态每 2 秒约 1500 次同步 IPC；通知密集时再叠加一轮。
   **主线程被占满 ⇒ click 事件排队 ⇒ 「点击无响应」的直接原因。**
2. **折叠改顶层 `sections` state ⇒ 整面板重渲染**，而 AdjustmentPanel 是
   3800 行单组件、所有分区 JSX 写在一个 return 里 ⇒ 折叠一个分区会让**所有**已展开分区
   （含 UXP 原生 `input[type=number]`，同步成本极高）全部重新 reconcile。
   且每次重渲染都重做 O(图层数) 分配（见下）。
3. **O(图层数) 的每帧分配**：三个下拉的 `options` 在 JSX 里现 `.map(...)`
   ⇒ 每次重渲染为每个下拉重建 N 个对象；`Select.tsx` 的 `optionsSignature`
   **无 memo，每次渲染全量重建签名**；`maskSyncSampleOptions.find()` 每任务一次 O(N)。
4. **同一防抖回调内重复建树**：`refreshMaskSyncOptions()`（内含 buildLayerTree）
   紧接 `reconcileTasks()`，后者未拿到 tree 时**又建一次全树 + 2×(N/40) 次 batchPlay**。
5. 次要：`resyncNativeWidgets()` 每次调用都排一个 rAF 读 `scrollHeight/clientHeight`
   （强制同步布局），同帧内多次触发会重复强制重排。

### 改动（8 个文件）
- **新增 `src/utils/layerTreeSnapshot.ts`**（核心）：共享快照。一次遍历同时产出
  **结构签名 + 扁平条目表**，两类消费者共用；带 `dirty` 标记 + `maxAge` 复用。
  API：`getLayerSnapshot(maxAgeMs)` / `invalidateLayerSnapshot()`（**纯内存、零 IPC，
  可在通知回调里直接调**）/ `isLayerSnapshotDirty()` / `findInSnapshot()`。
  ⚠️ 签名改为**先序遍历顺序 + id + kind + name + depth** 参与 FNV-1a
  （顺序参与 ⇒ 移动图层也能识别；旧实现栈式 pop 顺序不敏感）。
- `MaskSyncEngine.ts`：`docSignature()` **删除**（调用点直接读快照）；
  `buildLayerTree(doc?, snapEntries?)` 支持外部注入条目以跳过遍历；
  `reconcileTasks(tree?, snapEntries?)` 透传；`doTimedSync` 加两道短路 ——
  **无任务直接返回**（最常见状态，省掉全部轮询开销）、**仅 `hasPaths` 才取签名**；
  通知回调加 `invalidateLayerSnapshot()`。
- `AdjustmentPanel.tsx`：`computeLayerSignature`/`buildLineReferenceOptions`/
  `refreshLineReferenceOptions` 全部改走快照；结构探针改为
  **先问 `isLayerSnapshotDirty()`，干净就直接跳过整轮刷新**（省掉「为确认没变化
  而做一次全树遍历」这种反向开销）；新增 `refreshMaskSyncAndReconcile()` 复用已建树；
  三个下拉 options 全部 `useMemo` 化；`maskSyncSampleIndex`（Map 查表）替代每任务 `find`；
  通道选项走模块级 `CHANNEL_OPTIONS_CACHE`（稳定引用）；
  `resyncNativeWidgets` 改为**帧内幂等合并**（模块级 `resyncScheduled` 标志）。

- `BrushSelect.tsx`：`options.map` 加 `useMemo`。

### ⛔ 白屏事故复盘（用户实测报障，紧接上一节优化之后）
**症状**：UXP 报 `TypeError: Zt is not a function`，堆栈 `at Array.map` → `Object.Qi [as useMemo]`

`tsconfig` target = **es5**，ts-loader 把 `const` 降级为 `var`（**提升但值为 undefined**）

（靠「调用点在 return 之后的 JSX 里」才安全）—— 若将来有人把该函数改成组件体顶层同步
调用，会立刻白屏。想彻底免疫应把这两个纯函数提到模块级（同文件已有
`interpolateColorAtPositionForPreset` 的模块级先例）。

### ✅ GradientPicker 同类隐患修复（用户要求，把上一节点名的「侥幸安全处」也做掉）
**原隐患**：`getPreviewGradientStyle`（原 632 行）调用组件体内**更下方**才声明的
`interpolateColorAtPosition`(664) / `interpolateOpacityAtPosition`(729)。
原代码只是「侥幸安全」——唯一调用点在 return 之后的 JSX 里（此时组件体已执行完）。
**风险**：一旦有人把 `getPreviewGradientStyle()` 改成组件体顶层同步调用（如
`const style = getPreviewGradientStyle()`），预览条立刻白屏。

**修法（提到模块级，删组件内副本）**：四个东西都只依赖入参、不读组件 state：
- `interpolateColorAtPosition` → 模块级 210 行
- `interpolateOpacityAtPosition` → 模块级 272 行
- `rgbaRegex` / `rgbaWithAlphaRegex` → 改名 `GRADIENT_RGBA_REGEX` /
  `GRADIENT_RGBA_WITH_ALPHA_REGEX` 提为模块级 206/207 行
  （改名原因：与上方 `...ForPreset` 版本内部的局部同名正则区分，避免混淆）
- 组件体内 113 行旧副本整体删除（793~906 区段）
⚠️ **`getGradientStyle`(794) 本来就安全**（声明在两个插值函数之后），无需动，
不要为「对称」而无谓搬动。

⚠️ **`interpolate*AtPositionForPreset` 与组件版不可合并**（易被误认为重复代码）：
算法同构，但 (a) 入参类型 `any[]` vs `ExtendedGradientStop[]`；
(b) **透明度正则的 alpha 组语义不同** —— ForPreset 版是**可选**
（`/rgba?\((\d+),\s*(\d+),\s*(\d+)(?:,\s*([\d.]+))?\)/`，兼容无 alpha 的 `rgb()`），
组件版是**必需**（`/rgba?\((\d+),\s*(\d+),\s*(\d+),\s*([\d.]+)\)/`，不匹配则回退 1）。
合并会把 `rgb()` 无 alpha 的兜底行为改掉。

**验证（沿用上一节的 es5 产物验证法，不能只看 webpack）**：
① es5 产物里 `GRADIENT_RGBA_REGEX`(222)/`GRADIENT_RGBA_WITH_ALPHA_REGEX`(223)/
   `interpolateColorAtPosition`(225)/`interpolateOpacityAtPosition`(279)/

   `getPreviewGradientStyle`(779) 也已晚于 `interpolateColorAtPosition`(225) ✓；
② 把模块级四件套从 es5 产物原样抽出、在 vm 里执行，逐一核对数值：
   中点插值 color(50)=127.5、半透明 opacity(50)=0.500、同位置分支 opacity=0.350、
   `rgb()` 无 alpha 兜底=1 —— **与搬移前语义一致**；
③ webpack 生产构建通过；tsc 报错 731 行＝基线无回归
   （GradientPicker 的报错全是既有 es5 lib 限制：Set/Promise/padStart/startsWith）。
