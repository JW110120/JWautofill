## pattern-preset 四格等距布局（修正）

`thumb-box` 原 56px 在 4 格下必换行，根因是可用内宽远小于 4×56：

- **面板宽度链（实测，纠正记忆里"面板 248"）**：manifest.json 图案面板 `width:250` → `.panel`(`box-sizing:border-box; padding:10`)= 内 230 → `.preset-area`(直接子、border-box、border1×2)= **内 228**。
- `.thumb-box` 本就 `box-sizing:border-box`，56px 即含 1px 描边的外尺寸；4×56=224 已几乎吃满 228，无空间放 5 段间距。
- **等距公式**（左右边缘间距=格间距=M，容器 border-box 使 `4×B + 5×M = 228`）。整数解仅 (52,4)/(47,8)/(42,12)。取最贴近 56 的 **B=52、M=4**：4×52+5×4=228 整除、零换行零余量。
- 改动：common.css `.thumb-box` 56→52；pattern.css `.pattern-preset` 加 `box-sizing:border-box`、`padding:0 4px`，并保留 `.pattern-preset .thumb-box{margin-right:4px}` / `:last-child{margin-right:0}`。gradient.css 的 35px 盒是别类、不受影响。
- ⚠️ 之前记忆称"面板宽 248"有误，实为 250；后续任何面板内部件等距/整除排版都按 228 内宽（图案面板）起算。

## PatternPicker 性能大优化（5 张 70KB 图即卡 → 对齐 PS 原生手感）

瓶颈三层，全在「重复全量 I/O + 渲染循环 + 全尺寸 imaging 编码」：

**① PresetManager.savePatternPresets（最致命）**
- 旧：逐字符 `+=` 拼 base64（单张图案 patternRgbData+grayData+originalGrayData+data ≈ 2.5MB 字符串）+ `JSON.stringify(,null,2)` + 临时文件写 + 全文读回 JSON.parse「验证」×2 + 备份搬移 + 最终文件**二次写**。单次保存阻塞主线程数秒。
- 且被 3 处重复触发：patterns 变化 500ms 防抖、「组件卸载强制保存」effect（cleanup 语义=每次变化都触发！）、30s 定时。
- 新：分块 `String.fromCharCode.apply(0x8000)` 快速 base64 + 查找表解码；`lastPatternJson` 相等**最先短路（零 I/O）**；不 pretty-print（体积 -30%）；删全部读回验证与二次写（保留备份重命名 + 单次覆盖写）。

**② 灰度预览级联循环（PatternPicker）**
- 旧：三个 effect 互相触发（patterns 变化 / 蒙版模式 / 灰度就绪），其中之一把 `grayPreviewUrls` 放依赖又在内部 setState → 渲染循环；`getPreviewUrl` 在**渲染期**发起生成 + setState；PS 事件通知（set/select/make…）每次都 batchPlay。且**按图案原始尺寸**走 imaging.encodeImageData（一张几百 ms）。
- 新：合一为单 effect（deps：patternsGraySig(mem) + 4 模式位 + grayCacheEpoch），pending 集合去重、缓存 ref 镜像不进依赖；`getPreviewUrl` 纯查找；**灰度预览降采样到 GRAY_THUMB_MAX=104px**（52 盒的 2x）再编码，成本 ~1/25。

**③ 常驻开销**：删每秒 getComputedStyle 轮询（matchMedia+MutationObserver 已覆盖）；主题事件 4 连发→2 次；删两个纯调试 effect（DOM 尺寸测量=强制重排、grayData 日志遍历）；onLoad 冗余日志精简。currentBgColor state→ref（旧闭包捕获过期值会重复重建）。
- webpack 构建通过。UXP 实机待核对：灰度缩略图观感（104px 上限）、保存/加载数据完整性、主题切换后预览刷新。

## 二轮修正（保留 1px/2px 描边态 + 拖拽排序性能）

- **选中缩图（保留 1px/2px 状态）**：用户自己改回基础描边 1px + 选中 `border-width:2px`，并试过 `outline-offset`（UXP 不支持，且其文件里只有 offset 没有 outline 属性，本就不生效）。最终方案：`.thumb-box img` 从 `max-w/h:100% + padding:2px` 改为 `max-width/max-height:46px`（46 = 52 − 2×1px 描边 − 2×2px 呼吸边距）——图片渲染尺寸与 content-box 解耦，描边加宽不再缩图。若改 .thumb-box 尺寸须同步 46。drop-target 的 outline-offset 同步删除，虚线画盒外侧（格间 4px 间隙容纳）。
- **拖拽排序卡顿根因**：每次 savePatternPresets 都把每图案 4 块二进制（data/patternRgbData/grayData/originalGrayData）全量重编 base64（单图案可达数 MB 字符串、主线程）；拖拽只改顺序却全量重编。修复：PresetManager 加 `patternFragCache`（WeakMap<pattern, {sig, frag}>），签名覆盖全部被序列化字段+各缓冲区 length（全 O(1)），命中直接复用 JSON 片段，最终 `'[' + frags.join(',') + ']'` 拼装（与整表 stringify 输出一致，lastPatternJson 短路逻辑不受影响）。原地改写 pattern 对象会使签名失配自动重编，不会存脏数据。
- ⚠️ UXP 不支持：flex gap、outline-offset（新坑记录）。

## 三轮修正（拖拽落点双重描边 + 导入 1MB 卡 3 分钟）

- **落点双重描边 BUG**：选中格(2px 实线)作为拖拽落点时，outline 虚线叠加成"实线+虚线并存"。修复：drop-target 不再用 outline，直接 `border-color/style(dashed)/width:2px` 复用 border 本身——特异性 3 类 > 选中态 1 类，dashed 天然取代实线，永远只有一圈；img 已固定 46px，加宽不缩图。
- **导入 3 分钟卡顿元凶**：PatternPicker.processFile 的 `arrayBufferToBase64` 仍是逐字符 `+= String.fromCharCode` 旧实现（1MB = 百万次字符串拼接，UXP 引擎下数分钟）——与 PresetManager 中已修的同类问题，此处漏网。修复：优先 `file.read({format: formats.base64})` 原生直读（零 JS 编码），catch 退回 0x8000 分块快速编码。⚠️ 教训：修 O(n²) 编码时要全仓 grep `fromCharCode` 排查同类。

- 补刀：PresetManager.uint8ArrayToBase64 第二步（每 3 字节 result += 4 字符）对 12MB RGBA 仍是数百万次大串追加，改为直接从 Uint8Array 编码 + number[] 累积 + 每 0x8000 一次 fromCharCode.apply，并省掉中间二进制串。全仓 grep 确认无其它逐字符 += 残留。
