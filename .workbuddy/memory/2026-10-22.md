### ① 灰度极性反了（用户真机发现，已修根）

**现象**：该实心的地方在 PNG 里是黑的、该透明的地方被涂黑 ⇒ PS 里笔尖图案整体反相。
**根因**：PS 的画笔遮罩语义与 alpha 相反 —— **0(黑)=100% 不透明，255(白)=100% 透明**；
`rgba_to_mask()` 返回的是 alpha 语义（255=实心），写文件时漏了 `255 - v`。
**修法**：`krita_bundle_export.py::main()` 写 PNG 前 `bytes(255 - v for v in mask)`。
⛔ **只在写文件端反相**：`stamp_mask / render_preview` 按 alpha 语义工作，跟着反会让预览变成
「透明底上几乎看不见的浅痕」。已验证：重跑后 6 支 `preview.png` 与现有**逐字节一致**。
备注：用户在 PS 里手工反相了 dist 里 6 张图（src 均值 27→228 = 255-x），已回收为源文件；

### ② impasto / impasto-detail 的「位移」根因 = gih 帧头

`gih_first_frame()` 旧实现用 `data_start = len(blob) - cells*frame` 假定各帧紧贴文件末尾。
实际 **每帧前面还有 29 字节帧头**（hdr_size/ver/w/h/bpp/"GIMP"/5 字节参数），
起点整体后移 **116 字节 = 4bpp 下 29 像素** ⇒ 图像水平错位、右侧混进下一帧内容。
修法：逐帧读帧头、按 `hdr_size + w*h*bpp` 前进；解析结束位置必须恰好等于文件长度
（实测 5 帧 × 284829 + 50 = 1424195 = 文件大小，闭合）。
⚠️ 用户已手工缩放对位；新算法内容宽度与手工版一致（148px），仅差 4~5px 偏移。
**保留用户手工版，不重跑覆盖**。

## 08:45 改口：半透明不是流量，是「灰度被当 alpha」

⛔ **上一段 ④ 的结论作废**。用户真机核对：手动反相图案后自建 PS 笔刷，流量与不透明度
**都是 100%**，但图案仍半透明。原因 = 图案本身是**深灰**，而 PS 把灰度当 alpha ⇒ 深灰即半透明。
流量那套解释（「印章只蘸三成墨」）只适用于 flow<100 的情况，本次不适用。

### 真正的差异：Krita 的图像笔尖是「带光照的印章」，PS 的只是「漏空模板」

源码链（Krita，GPL）：
`KisBrush::generateMaskAndApplyMaskOrCreateDab` → `preserveLightness` 为真时走
`KoColorSpacePreserveLightnessUtils.h::fillGrayBrushWithColorPreserveLightnessRGB`：

```cpp
brushMaskL = qRed(*brush)/255;                      // ★ R 通道 = 亮度
finalAlpha = min(qAlpha(*brush)/255, colorA);       // ★ alpha 通道 = 透明度
finalLightness = (2-4z)*L² + (4z-1)*L;              // z = 前景色亮度
setLightness(r,g,b,finalLightness);                 // 保留色相饱和度，只换亮度
```

**两个通道分工**：alpha 管透明，R 管亮度。所以白前景 + 白底仍能出灰（L<0.5 输出灰、L≥0.5 推满白）
⇒ 凹槽=阴影、凸起=高光=浮雕感。z=0.5 时曲线退化为恒等映射。

笔尖 XML 开关：`ColorAsMask="1" preserveLightness="1" BrightnessAdjustment ContrastAdjustment AdjustmentMidPoint`。

### PS 的结构性缺失（不可修）
PS 只有一条通道：`输出颜色 = 前景色（恒定）`、`输出 alpha = 笔尖灰度`。
纯白前景 + 白底 ⇒ 全像素 (255,255,255)，alpha 再低也是白 ⇒ **物理上看不见**。
⇒ 单支 PS 画笔**无法**完整复现；缺的是一条颜色通道，不是某个开关。

## 09:45 弹框真凶 = `dialogOptions` 选错档位（silent vs dontDisplay）

用户第三次反馈：还弹「新建画笔」框、每次点都让重装、首次选中还是喷枪。
根因不是"漏写 dontDisplay"，而是**dontDisplay 本身就是允许弹框的那一档**。

### Adobe 文档原文（batchPlay → Command execution options）
| 取值 | 行为 |
|---|---|
| `silent`（**默认**） | 不出 UI；**命令需要额外参数时返回脚本错误** |
| `dontDisplay` | 不出 UI，**但出错 / 命令需要额外参数时仍显示 UI** |
| `display` | 出 UI |

`defineBrush` 需要的"额外参数"= 画笔名称 ⇒ dontDisplay 照章弹框。
⇒ 全仓改 `silent`。**顺带解开老坑**：`select` + dontDisplay 为什么"弹宿主错误框、
还不进 catch"—— 因为出错时要显示 UI。silent 下它就是普通异常，可捕获。
（另：`dialogOptions` 只认**描述符自己的 `_options`**；batchPlay 第二参数只认
 synchronousExecution / continueOnError / immediateRedraw / modalBehavior，
 之前以为它"会盖掉描述符设置"是误判，那一处本来就没生效。）

### 不再用差集定名（这是"每次点都让我重装"和"首次选中喷枪"的共同根因）
- 旧链：定义前后各读一次画笔清单，差集新增项 = 真名。真机上差集**恒空**
  （presetManager / app.brushes 的缓存不新鲜），于是抛
  "定义命令返回成功，但画笔清单里没有新增笔尖" ⇒ 后面的 select/set/delete 全没跑
  ⇒ 预设留在面板（正是用户说的"留下把柄"）、工具上还是上一支笔（喷枪）。
- 现在：笔尖文件名 = 预设名（PS 用文档名）⇒ `BRS-impasto-detail.png` 是**确定的**，
  不猜不读清单。存在性判定改用 **`select` 当探针**（选不中会抛异常）。

### 顺序（用户口径，已严格对齐）
切画笔工具 → 清残留 → **定义 → 选中 → 下发参数 → 删除**。
`delete` 挪进 `finally`：参数下发失败也不许把预设留在面板。

### 两个新武器（来自 Adobe 论坛实测）
- `currentToolOptions.brush.name` = 当前画笔名 ⇒ 校验"真的选中了我们的笔尖"。
- 设工具选项：`get currentToolOptions` → 改字段 → `set` 到 `{_ref:'paintbrushTool'}`，
  比"只 set 两个键"稳（交回去的是 PS 自己刚吐出来的结构）。

### 删除的安全阀（风险不对称，不能赌）
校验结果三分：`match`（删）/ `unknown`（读不到名字，信 select 结果，删）/

```

→ app.load(File("...<n>-<m>.tpl"))
```

**⛔⛔ 核心结论：样本装的是「工具预设 tool preset」，不是「画笔预设 brush preset」。**

`zhushou.jsx` 是另一形态：内联 `toolRecording` 二进制 + `executeAction('toolRecording')`，
连预设都不留。格式私有、与大版本绑定。

样本是 **CEP**（有 ExtendScript `app.load(File)`）；我们是 **UXP**（manifestVersion 4，无 CSXS），
**没有 app.load**。UXP 只能 batchPlay，而"载入预设文件"的命令名/参数无公开文档。

自造文件也不划算：`.tpl` 的笔尖是 `8BIM/tpbd` 私有资源 + `sampledData` UUID 引用；
样本 `.abr` 与 PS 2026 自带 `Legacy Brushes.abr` 都是新块结构（`00 0a 00 02` + `8BIM`/`samp`），

## 12:00 破案：`set` 裸发几何把采样笔尖换成 `computedBrush`（喷枪回退根因）

### 铁证（`brushstate/_last-run.json`，11:34 那次点击）

```json
"currentToolOptions": {
  "_obj": "currentToolOptions",
  "brush": {
    "_obj": "computedBrush",
    "diameter": {"_unit":"pixelsUnit","_value":820},
    "hardness": {"_unit":"percentUnit","_value":0},
    "angle": 90, "roundness": {"_value":68}, "spacing": {"_value":10}
  }
}
```
`820 / 68% / 10%` 全是我们从 `brush.json` 下发的值 ⇒ **这支 computedBrush 是我们自己造出来的**。
它没有 `name`、没有 `sampledBrush.sampledData` ⇒ 视觉上就是一支软边喷枪。

### 因果链（一个 bug 解释三个症状）

1. `setBrushGeometry` 发 `set BRUSH_TARGET to {_obj:'brush', 只有 6 个几何键}`
2. PS 把当前笔刷**整体替换**成 `computedBrush` ⇒ 采样笔尖（毛刷像素）**被扔掉**
3. 于是 `cto.brush` 存在但 `name` 为空 ⇒ `capture` 旧判据（`currentBrushName` 非空）恒失败 ⇒ **黄点1**
4. `stored=false` ⇒ 不删预设 ⇒ **黄点2**
5. 用户看到的是喷枪 ⇒ **"笔尖始终为喷枪"**
   ⚠️ 而且偏偏发生在「下发画笔参数」显示**成功**的那次（失败反而什么都不写、笔尖不丢）
   —— 所以"上一轮看着对了、这一轮又坏了"，不是回归，是当时参数没下发成功。

### ⛔⛔ 新铁律

**在 PS 里 `set` 一支 brush，`to` 必须带上笔尖身份（`_obj` + `name` + `sampledBrush`），
否则等于"换成计算笔刷"。** 判据 = 写完回读 `sampledBrush.sampledData` 是否还是原来那串 UUID。

```
清理预设    黄  命令已被接受，但清单里仍列着「BRS-impasto-detail.png」
```

### ⛔⛔ 两条新铁律

1. **PS 27 换笔尖的正确形态 = `select + brush _name + makeVisible:false`**
   （= ExtendScript 的 `slct`+`Brsh`+`MkVs:false`）。比纯 `select` 多的就是 `MkVs`，
   带上才是"应用"，不带的只是"面板高亮"。`set+brush` 在 PS 27 报 **-1715**，
   `set+brushPreset` 报 **-25920** ⇒ `set` 这条路在 27 上死了。
2. **`brushes` / `presetManager` 属性是惰性快照，删掉的预设照样列着**
   ⇒ 绝不能用它当"删除成功"的判据（11:41 就把它误判成黄）。
   可靠探针 = **按名 `select`**：名字不存在 PS 必报错，
   所以「删完还能按名选中」= 真没删，「按名选不中」= 删掉了。

### 顺带发现的隐患

缓存里 `diameter=399 / roundness=100` —— 不是我们要的 820/68。
⇒ 「整份带 sampledBrush 一起 set」**仍会丢笔尖**，守门重装后几何被打回预设默认值。
修法：几何改走 **`set paintbrushTool to 整份 cto（只换 brush 里的几何键）`**，
和已验证不丢笔尖的 `setToolOpacity` 同一套路；`set BRUSH_TARGET` 降为回退。
回读判据 = `sampledData` 没变 **且** 直径真改了。

## 12:05 长黄条破案：**每条失败的 batchPlay 都被 PS 画成一条黄色通知**

### 铁证（`_last-run.json` 11:51 那次点击，`source: "cache"` 全绿）

`commands` 里 16 条命令，**13 条是 `_obj:"error"`**，全是同一句：

```
悦绘: 命令“选择”当前不可用。（-25920）
悦绘: 命令“设置”当前不可用。（-25920）
```

来源三处，全都在「功能本来不需要它们」的地方：

| 位置 | 失败条数 | 为什么会失败 |
|---|---|---|
| `ensureBrushTool` 第 1 条形态 `{_ref:'tool',_enum:'ordinal',_value:'paintbrushTool'}` | 1/次点击 | PS 27 不认这条 ordinal 写法 |
| ① 扫描：`trySelect(main)` + `trySelect(alt)`（各试 2 种形态） | 4/次点击 | 预设早就删了，名字不存在 ⇒ 必报 -25920 |
| ② `applyPreset([main, alt])` 各试 6 种形态 | 8/次点击 | 同上 |
| `readToolOptions` 前 3 条形态里不可用的那些 | 若干 | 同上（不走 `bp()`，不在 `commands` 里） |

⇒ 结论：**黄条 = 失败命令的条数**，一条一条累上去就是用户看到的那"很长一段"。
功能没坏，是我们在拿「按名 select」当存在性探针，而探针**天生靠报错**给答案。

### ⛔⛔ 新铁律

⇒ 凡是**正常路径**，失败命令数必须为 **0**；能用"读状态"判的，绝不用"试一下会不会报错"判。

## 12:10 更正：那条"黄条"不是 PS 的通知，是**我们面板自己的状态条**（`.notify-bar`）

用户录屏截图里那段铺满整屏的中文：

```
「BRS-impasto-detail」没能装上：#1 应用画笔「BRS-impasto-detail」（set+brush）: 悦绘: 命令"设置"当前不可用。（-25920） / #2 … / #6 …
```

这是 `applyFailure()` 的**拼接串**（`#1 … / #2 … / #6 …`），只可能由我们自己的
`onLog(\`「${n}」没能装上：${r.detail}\`)` 产生，被 `.notify-text` 换行铺满。
PS 自己的黄条长这样：**只有一句**「悦绘: 命令"选择"当前不可用。（-25920）」。

- 文本里的名字是 `BRS-impasto-detail`（**没有 .png**）= `alt` 候选，新代码只在"清单读不出来"时才会试它；
  旧代码在 `ours` 为空时永远试 ⇒ **这一帧来自重新加载插件之前的那次点击**。
