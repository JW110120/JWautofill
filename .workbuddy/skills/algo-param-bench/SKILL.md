### 三个够用的度量（远好于"看起来还行"）
- **一阶差分粗糙度** = `mean(|a(x,y) − a(x±1,y)|)`（alpha>0 像素，横/纵分开）。斑驳与条纹的直接代理量。
- **3×3 中位数离群点占比** = `|a − median(3×3)| ≥ 20` 的比例。专抓棋盘格式斑驳。
- **直方图不同值数** + **输出均值 vs 选区众数**：一眼判断"对齐是否彻底、落到了哪一层"。

### 逐像素参照类算法的通病（本项目 alpha 对齐 v5 踩到）
逐像素**独立**估计参照 → 邻域内相邻像素选中不同层级（实测 73 / 157 交替）→ 斑驳；
沿笔触方向连成线就是条纹；大量像素判为"不改"→ 对齐不彻底。
**修法不是再调阈值，而是给参照场加一次"窗口共识"**：窗口内出现次数达标的参照取极值
（下对齐取最低、上对齐取下中位数），并对"没拿到参照"的像素按落差补判。
补判门槛取 `参照量程/2` 这类**有语义的锚点**，不要选扫描出来的数值最优 —— 那是在过拟合单张素材。

## 标准流程

1. Glob 找素材 → 解码 → 打印尺寸/均值/σ 与偏离分布直方图（先确认素材范围，比如是否含面板 UI）。
2. 定分档阈值（看直方图的谷底；天然可分才用单指标判据）。
3. 参数扫描：一维网格扫每个候选参数，对每个取值报**分档改动幅度 + 百分比 + 区分比**。
4. 传输曲线：`原始偏离 → 处理后的偏离`，把"背景带"和"特征带"标出来。这比任何指标都好读。
5. 单调性/伪影检查：扫定义域找极值点，报反转量；同时给出解析临界值互相印证。
6. 落盘脚本 + 输出 markdown 表格，给出"推荐值 + 为什么，以及不要选其他值的原因"。

## PNG 解码器（8bit、非隔行；复制即用）

```js
const fs = require('fs'), zlib = require('zlib');
function loadPng(file) {
  const buf = fs.readFileSync(file);
  if (buf.readUInt32BE(0) !== 0x89504e47) throw new Error('not png');
  let off = 8, w = 0, h = 0, bd = 0, ct = 0, il = 0, plte = null;
  const idat = [];
  while (off < buf.length) {
    const len = buf.readUInt32BE(off), type = buf.toString('ascii', off + 4, off + 8);
    const d = buf.subarray(off + 8, off + 8 + len);
    if (type === 'IHDR') { w = d.readUInt32BE(0); h = d.readUInt32BE(4); bd = d[8]; ct = d[9]; il = d[12]; }
    else if (type === 'PLTE') plte = Buffer.from(d);
    else if (type === 'IDAT') idat.push(Buffer.from(d));
    else if (type === 'IEND') break;
    off += 12 + len;
  }
  if (bd !== 8 || il !== 0) throw new Error('只支持 8bit 非隔行');
  const chN = { 0: 1, 2: 3, 3: 1, 4: 2, 6: 4 }[ct];
  const raw = zlib.inflateSync(Buffer.concat(idat));
  const stride = w * chN, px = new Uint8Array(h * stride);
  let p = 0;
  for (let y = 0; y < h; y++) {
    const f = raw[p++], line = raw.subarray(p, p + stride); p += stride;
    const cur = px.subarray(y * stride, (y + 1) * stride);
    const prev = y > 0 ? px.subarray((y - 1) * stride, y * stride) : null;
    for (let i = 0; i < stride; i++) {
      const a = i >= chN ? cur[i - chN] : 0, b = prev ? prev[i] : 0, c = (prev && i >= chN) ? prev[i - chN] : 0;
      let v = line[i];
      if (f === 1) v += a; else if (f === 2) v += b; else if (f === 3) v += (a + b) >> 1;
      else if (f === 4) { const pa = Math.abs(b - c), pb = Math.abs(a - c), pc = Math.abs(a + b - 2 * c); v += (pa <= pb && pa <= pc) ? a : (pb <= pc ? b : c); }
      cur[i] = v & 255;
    }
  }
  const at = (x, y) => { const i = y * stride + x * chN;
    if (ct === 2 || ct === 6) return [px[i], px[i + 1], px[i + 2]];
    if (ct === 0 || ct === 4) return [px[i], px[i], px[i]];
    const q = px[i] * 3; return [plte[q], plte[q + 1], plte[q + 2]]; };
  return { w, h, at };
}
```

内缩 6px 避开截图外框；亮度用 `0.299R + 0.587G + 0.114B`。
**判据用亮度、RGB 欧氏 RMS ≈ √3×σ_L 说明偏离全在明度轴上时才成立**（先验证这条再简化）。

## 分档度量的写法

```js
const mAbs = (arr, f) => arr.reduce((s, d) => s + Math.abs(f(d)), 0) / arr.length;
// 每档同时报：绝对改动级数 与 改动百分比 —— 百分比暴露"选择比"，级数暴露"是否看得见"
console.log(`背景 ${mAbs(bg, f).toFixed(2)}级/${(mAbs(bg,f)/mAbs(bg,d=>d)*100).toFixed(0)}%`);
```

**"选择比" = 特征带压缩率 / 背景带压缩率**，是判断"只压特征、不动背景"是否达成的核心指标；
不要用"剩余偏离之比"，那个方向相反，容易读反。

## 已知结论（本项目）

分块平均的「对比减弱」：`k = coeff/255 × s × t/(1+t)`，`t = u/τ`，`u = |亮度 − 所在连通块均值亮度|`，`τ = max(σ_L, 6)`。
**p 固定 = 1（不暴露给用户）**，**`s = 强度 × 0.07`**（强度 1–10 → k 上限 7%–70%）。
p=1 时严格单调（`1 + (1−s)(2t + t²) > 0` 对 `s ≤ 1` 恒成立），压缩后偏离大小关系不变 —— 这是用户的硬条件。
（p=1.5 / p=2 在 s 接近 1 时会让深像素反转，已弃用。）详见 `.workbuddy/memory/MEMORY.md` 与当日日志。

混合颜色带柔化：`phi = 1 − λ·clamp((u − 1.5σ)/4.5σ, 0, 1)`，`λ = 柔化级/10`，
RGB 用 `1 − w·k·phi`，alpha 用 `1 − w·k`（不乘 phi）。功能上等价于「把减弱结果与原始按 phi 混合」。
两条已证实的取舍：
- **必须有平台段**（`u ≤ 1.5σ` 时 phi=1）。照 PS 原参数把四个手柄收到均值（平台宽 0、端点 0/255）会让
  背景压缩从 24% 掉到 5%，且强度随选区均值在色阶中的位置漂移 —— 端点固定的斜坡不能照搬进「偏离归一化」的公式。
- **柔化与选择比是对冲的**：把「偏离大的像素」保留回来，正是差值驱动机制的产出，二者不可兼得。
  本图实测线条带保留率从 51%（无柔化）→ 61%（λ=1），选择比 2.04 → 1.62。

## 三条标定铁律

1. **滑块上限用解析锚点定，不要用某个分档百分比去凑**。换曲线形状（p）之后，
   「k 上限相等」和「各分档压缩百分比相等」不可能同时成立，只能守恒一个；守恒 k 上限语义才稳定。
2. **大数组不要用 spread 求极值**：`Math.max(...arr)` 在 20 万元素时抛
   `RangeError: Maximum call stack size exceeded`，改用循环累计。
3. **先问清「有没有质量约束」**（如"顺序/大小关系不能变"）。这类约束往往直接排除掉一半候选公式，
   比事后调参便宜得多 —— 本项目就是靠它把 p 从 1.5 定到 1。

## 不变量测试（改/还原算法前先架好，比参数扫描更早做）

算法的正确性可以拆成几条**可断言的不变量**，用合成图 + 跑真函数，一次跑完就有结论
（`outputs/alias_smooth_test.cjs` 是本项目最能复用的一份）：

| 不变量 | 断言写法 | 防的是什么 |
|---|---|---|
| **幂等** | 同一输入连跑两次，第二次改动像素数 == 0 | 连点越改越实/越粗；也是"阈值或参照水平在漂移"的探测器 |
| **集合不变** | 输出按同一阈值二值化，mask 与输入逐像素一致 | 形状被吃掉 / 被外扩 |
| **单侧单调** | 分类后逐像素比大小：内侧只削不抬、外侧只补不削 | 半透明内容被"描边"推实（湿边） |
| **上界** | 输出最大值 ≤ 本体水平（形状自身的实心不透明度） | 轮廓比本体更实 |

**用例矩阵**：硬边不透明 / 硬边半透明 / 软边半透明 / 长台阶直边（触发分化分支）——4 个就够。
**穿过轮廓的一行 alpha 剖面**（原图 vs 结果并排打出来）比任何指标都好读，一定打。

⚠️ **幂等断言是性价比最高的探测器**：本轮残留只有 7~14 个像素、每次差 1 级，肉眼绝对看不出，
但它准确指向"某个中间量在两次运行之间变了"。**别把小残留当噪声放过 —— 那是设计缺陷的指纹。**

## 改「平滑/距离场类」算法时的对拍口径（2026-09-18 lineSmooth 细线修复）

**基线怎么取**：不要用 `outputs/*.bak`（可能是几轮之前的），直接 `git show HEAD:<path>` 导出到
`analysis/line_vis/_old/<name>_head.ts`，台架同时 `import` 新旧两版做 A/B。Node 22 能直接 import `.ts`。

**两个必须同时报的度量，缺一会漏判**：
1. **vs 旧版**（回归）：形状差（输出 mask 成员变化）/ 强差 `|Δα|≥128` / 弱差 / 占比。
2. **vs 原图**（能力）：`改动像素数 + 平均Δα`，以及**跨轮廓的 alpha 剖面**与**边缘过渡带宽**。
   只报第 1 项会漏掉「改动更少、看起来每条线都对，但平滑能力整体退化」——
   本轮就这样让粗线锯齿的改动量从 3106 像素/平均Δα 53.2 掉到 880/2.9 才发现（差异占比仍只有 0.9%）。

**四条踩过的坑**：
1. ⚠️ **局部的「到最近背景距离」(EDT) 不能当作该处线宽**。任何形状的边界像素到背景都只有 1px，
   于是粗线边缘被误判成"细线"→ σ 被压到最低档 → 高斯核不再跨过边缘 → **平滑能力掉到 1/4**（见上）。
   正确判据要问「**附近有没有足够粗的结构**」：以 i 为中心、半径 `1.5σ` 的窗口内是否存在
   内切半径 ≥ `1.25σ` 的线内像素（等价 σ ≤ 0.4×线宽）。窗口存在性用积分图查询，O(1)/像素。
   粗线边缘的问法答案为"有"（0.5σ 内就有更深的内部像素）、细线的答案为"没有" —— 这才是判别式。
2. ⚠️ **抗锯齿带宽 `band` 随 σ 缩放时，最高档必须保持原 `bandMax`**。否则在力度 50% / 半径 12
   这类 σ_user 偏小或偏大的参数下，粗线边缘与旧版不一致（实测 maxΔα 200、1441~2516 像素）。
   改完必须跑一遍 radius×strength 的参数矩阵对拍（8 组，纯粗线场景），差异应 ≤0.02%。
3. ⚠️ **密度抛光（对 alpha 做高斯）只在最高档做**。细线宽度与 σBody 同量级 → 高斯把线外的 0 掺进来
   = 结构性衰减 → 中值归一 `medOrig/medBlur` 把它当"整体变暗"放大 → **中不透明度细线被整体提亮**
   （实测 α150 的 3px 线 → 186）。非最高档直接用原 alpha，既省一次卷积也更准。
4. **分档 σ 的跳变会在边缘留下非单调剖面**（255,251,254）。只要保证「粗线整条落在同一档」就不会出现；
   σ 在细/中结构内部跳变时 cov≡1，看不出来。真要消掉再用「相邻档线性插值」。

**结论口径**：距离场平滑只作用于宽度 ≳ 2.5σ 的结构，而 σ 必须 ≤ 0.4×线宽才不塌缩 ⇒
**≤4px 的线在数学上无法被距离场平滑**（σ≈1.2 时 cov 恒为 1，输出 == 输入）。
这类细化抗锯齿应交给 `aliasSmoothProcessor` 的细线几何重建路径，别在本算法里硬凑。

## 验证台两个必踩的坑（细线验证时中招）

## 真实工况复现手段：直接解码用户截图
用户报"功能没有任何效果"时，别只用自己的合成图猜 —— 先把他给的截图 PNG 解码，灰度反推 alpha 剖面：
- 纯 Node 手写 PNG 解码（zlib.inflateSync + 逐行反过滤），支持 colorType 2/6/0，无第三方依赖。脚本样板见
  `outputs/analyze_clip.cjs`（本仓 outputs/ 已 gitignore）。
- 若笔触是纯黑压在白底上：alpha ≈ 255 − 灰度。逐行打印"非白像素区间 + 剖面值"，一眼看出：
  · 边缘是 255→本体 的硬阶跃，还是 255→半覆盖→本体 的灰过渡（后者说明 PS 已抗锯齿）；
  · 本体灰阶沿线的漂移（压感/叠加笔触）；
  · 截图是否被最近邻放大过（成片的等值块 + 宽度是整数倍）。
本次就是这样定出"用户线的边缘基本是硬阶跃、只有 5% 的极淡毛刺" → 直接指向"闸门太严"而非"算法没生效"。

## 直方图/阈值估算的三条通用坑
1. **按像素计数 vs 按墨量投票**：细线的过渡像素（毛刺）常常比本体像素还多（1px 线每行 ~2:1），
   `hist[bin]++` 会让毛刺档胜出、阈值塌到个位数；改成 `hist[bin] += alpha` 即恢复。
   「本体水平」在物理上是"墨量最集中的那一档"，不是"像素最多的那一档"。
2. **基准要逐行/逐段取，不要用全局极值**：用「全链最大 alpha」当基准，会把压感渐细的那一段
   整体误判成"淡边/已平滑"；逐扫描线取本行游程内最大值就免疫。
3. **档内取"下边界"而不是均值**：均值会被本轮新生成的过渡像素带漂移 → 二次运行结果不一致。

## "是否已经处理过"的判据（幂等闸门）通用写法
- 反例："窗口内出现任何中间 alpha 就跳过" —— 真实笔触边缘永远有一圈极淡抗锯齿像素，于是全部被跳过。
- 正解：判"过渡里是否已经把亚像素位置编码进去"：以本行本体水平为基准，出现 0.25~0.75 基准的中间档才算"已成过渡"；
  并按行数过半决定整条是否跳过。
- 但要接受一个物理事实：**处理后的 1px@满不透明度 与 天生的 2px@半不透明度 像素值完全相同**，
  任何纯局部判据都分不开 → 只能保证"再点一次是恒等或小幅收敛"，不能保证严格零改动。验收标准应是
  "峰值不降、线心误差随点击单调收敛"，而不是"二次改动必须为 0"。

## 平台/阶梯类插值的端部截断
平台中心插值（用平台中心当锚点、在相邻平台中心之间线性插值）在**链的两端**会失效：
首/尾平台被区域边界截断，观测到的中心不是真实中心 → 端部十几行亚像素位置偏最多半个平台长。
修法：先算"典型平台长度"（内部平台长度的中位数），首平台按 `e - typ + 1` 向左补足、尾平台按 `s + typ - 1` 向右补足，
再用补足后的中心当锚点。修复后 1:40 斜坡的线心偏差从 0.35px 降到 0.011px。

## 重分布类算法的墨量守恒
凡"先算目标值、再按上限截断"的写法（如内圈只减不增、外侧只补不削），都要问一句：**被截掉的那部分去哪了？**
丢了就会每次运行少一点墨（峰值逐次下降）。正解是把截断差额转投到"另一侧仍有余额"的像素上（cap 由另一侧上限定），
总墨量守恒后多次运行才收敛到不动点。

## 验收指标（补充上一节）
- 与"锯齿消没消"直接对应的是 **max|重心 − 真值线心|**（真值在合成图里是已知的）：硬阶梯 ≈0.25~0.50，好的 AA ≤0.05。
  只用"改动像素数"区分不出"变淡"和"消锯齿"；抖动 Δ²（重心二阶差分）受整数舍入影响大，当粗筛可以，当验收不行。
- 端部效应要单独看：把误差按行铺开找 max 落在哪几行，本次就是靠它发现"两端各十几行偏 0.38px"。
- 复跑验收矩阵：{近垂直, 近水平} × {线宽 1,2,3,4} × {本体 90,130,255} × {纯硬, 5% 毛刺, 50% 毛刺, 软笔刷}，
  外加"压感渐变（本体沿线变化）"与"连点 3~6 次看是否收敛"。改完算法**必须把旧验证台也一起跑**（主路径 4 案例 + 细线 7 案例）。

## 兼容性回归三件套：变化集代数刻画 / 定向探针 / 差异像素分类（2026-09-18 宽度拉平二次修复）

用户要求「修 A，但不能影响 B」。**别用「跑一堆合成场景看数值有没有变」来回答** —— 那只能证伪、不能证明。
正确顺序：先用代数性质把「这次改动的全部影响范围」缩成一个**精确集合**，再定向取证。

### ① 变化集代数刻画（最强的一步）
把新旧判据写成集合关系。本轮：细支门槛从 `H1 < T` 改成 `ref < T`，而 `ref ≥ H1` **恒成立**
⇒ 新豁免集 ⊆ 旧豁免集 ⇒ **唯一变化集 = { H1 < T 且 ref ≥ T }**（不必再猜别的分支有没有被碰到）。
剩下只是「它多大 / 落在哪」，而那是可测量的。
**推论：任何「参照量替换」都要先问新参照与旧参照的大小关系（≥ / ≤ / 不可比）。**
本轮 `ref ≥ H1` ⇒「限幅也改用 ref」**不可能削弱任何原有行为**（削平强度因此与旧版逐值相同）；
若不可比，就必须逐场景取证。

### ② 定向探针：把变化集打出来（trace 定位法的「差分」用法）
在**门槛行之前**插一条记录（`[col, row, ref, H1, T]`），跑完后只筛变化集里的格子。
本轮一次就解释了「为什么某处多了 1px」：6 个格全落在竖干肩部 y=358~373，根因是
「H1 被散播从相邻粗段抬高到 2.4~3.5，**恰好卡在旧阈值 3.57 之下**（＝旧版固有的临界豁免）」——
不插探针只会得出「大概是窗口太大」这种无用结论。

### ③ 差异像素分类（比「差异数」更有说服力的验收口径）
跑 OLD vs NEW 后**按类别统计差异像素**，别只报总数：

| 类别 | 判据 |
|---|---|
| 亚阈值碎片被清 | `0 < a0 ≤ THR` 且 OLD 保留、NEW 清零 ⇒ 本次要修的目标 |
| **墨像素(≥THR) 变化** | **必须为 0 才能说「没动本体」** |
| RGB 同时变化 | 查有没有误改颜色 |

本轮真实笔触 flat250：差异 1232px =「亚阈值碎片被清 1232 / 墨像素变化 **0** / 亚阈值但保留 0」
⇒ 一句可交付的结论，比「差异像素很少」强得多。

### ④ 变体源单常量扫描（标定 MIN/DIV 这类常数）
本处理器文件**自包含、零 import** ⇒ 把「只改一个常量的副本」写到任意目录（`_var/lsp_divN.ts`）即可
`await import('./_var/lsp_divN.ts')`，一个脚本跑完 `DIV × flatR` 完整网格（本轮 4×4=16 组），
用**同一台架的同一场景**取舍参数。判定表必须同时列**目标指标**（凹陷补偿）与**代价指标**（T 形是否被碰），
否则会只优化一边。本轮正是靠这张表发现 DIV=8 在 flatR=200 时窗口过小、补偿失效。
⚠️ 生成变体时**先全部落盘再动态 import**（漏了生成步骤会得到 `ERR_MODULE_NOT_FOUND` 而不是「参数不存在」）。

## 「不该动的笔画有没有被动」必须量轮廓位移，不能看字节差（2026-09-18 宽度拉平三次修复）

给平滑/拉平类算法加「按局部形态修正」的项时，最容易出的错不是力度不对，而是**在不该动的地方产生了结构性位移**。
判据不能只跑「旧版 vs 新版字节差」——字节差会被"绝大多数像素恰好没变"稀释掉：

- 实测等宽长弧（宽 20，中轴 60·sin(πy/620)）：旧版对它**完全不动**，新版把轮廓推了 **左 5px / 右 −6px**，
  而字节差只有 2115/200000 ≈ **1.1%**（最大差 48）。看字节差会得出"基本没动"的错误结论。
- 正确口径：**量墨迹外沿（alpha≥32）的最左/最右像素**，逐行打 `ΔL / ΔR`，并给出 max。
  合成一批「宽度恒定、只让路径变化」的用例（等宽直线 / 等宽斜线 / 对称弯折 / 等宽长弧 / 弧上单侧凸起），
  **理想结果就是轮廓一动不动**。这份台架（`diag_trend_cases.mjs`）比 A/B 字节差更早、更准地抓到伪影。

### 修正项必须量纲自洽，别用经验门控
第一版把「中轴位移」按 `g = min(1, |Δ|/1.0px)` 线性衰减 —— **量纲不对**：
δh = 0.79 时应把 δc 压到 0.79 量级，实际只把 12 压到 9.44，5px 位移只降到 5px（几乎没救）。
第二版改用**从定义直接推出的恒等式**：`Δc = (ΔL+ΔR)/2`、`Δh = (ΔR−ΔL)/2` ⇒ 任何真实变形都有 **`|δc| ≤ |δh|`**
⇒ 硬封顶 `sc = min(1, |Δ|/|δc|)`。同一用例立刻降到 左 −1px / 右 0px，且**自动**让"纯平移/纯路径弯曲"（Δ≈0）归零。
**经验规则：任何"按另一个量缩放"的修正，先问这个缩放因子有没有量级依据；能从定义推出恒等式就别选阈值。**

### 索引转置类 bug 的症状与探测
沿轴做「逐通道拟合/去趋势」时，通道步长极易写反（扁平下标 `k = gy·gw + gx` ⇒ 沿 y 的通道步长是 `gw`，不是 1）。
写反后通道变成"按行主序斜穿网格"的一串格子，它横跨目标、被拟合的量剧烈跳变 ⇒ 拟合出假斜率、凭空造出修正量。
**症状特征：不是"效果偏弱"，而是所有「应该逐字节一致」的场景一起大面积偏离**（本轮：对称凸起/凹陷/均匀/锥度
全部偏离旧版 8502~16093 字节，幂等二遍差 664→8811）。

⇒ **先跑"应该零差异"的用例组**，它们是这类 bug 的最灵敏探针；一旦这组不是 0，别调参，直接怀疑索引/坐标系。

### 定位伪影：dump 场，不要猜机制
发现"某处不该动却动了"时，**先写探针把中间场打出来**（`probe_arc_apex.mjs`：在 ⑥.5 之后、⑦ 之前 dump
`δh / δc / sw` + 在施加处 dump 逐像素 `d`），一次就给出 `δh=0.79 而 δc=12（被 CLAMP 顶到饱和）`，
直接指向修法（封顶为 |δ|）。凭机制猜测调参会绕远路（本轮已在门控阈值上白试了一轮）。



## 写回型像素处理器的边界两条铁律 + 三路对照台架（2026-09-19 高频增强「白边」）

**症状**：执行后沿**选区边缘**出一圈 1px 白边（浅色内容顶到 255）；全选时同因而沿**图层自身 alpha 轮廓**也出一圈。
用户会把症状描述成「靠近选区边缘的像素直接缺失了」——**字面是缺失，实指采样到 0**，别去找 alpha 被清零的代码。

**两条铁律**（凡「整层读入 → 处理 → 整层写回」的处理器都适用）：
1. 区域判定只用**选区掩码 > 0**（= 写回范围 `selectionDocIndices`），不要用 alpha>0；
2. 采样到**数据缺失**像素（图层外/全透明 ⇒ RGBA 全 0）必须用**中心像素值顶替（边缘延拓）**，
   不能把 0 当真实像素送进卷积/方差（3×3 高通核邻居全 0 ⇒ `hp = 8c` ⇒ `c + 8c·k·0.5` 当场饱和）。

**先查两处**：① `AdjustmentPanel` 调用点传的是 `fullPixelData` 还是 `selectionPixelData`
（后者对普通图层只复制选区内像素、区外恒 0）；② 处理器内部是否有「区域/统计量」分支。

**三路对照台架写法**（样板 `analysis/line_vis/repro_hf_edge.mjs`）：
A = 旧处理器 + 旧输入（复现现象）/ B = 旧处理器 + 新输入 / C = 新处理器 + 新输入。
**B 是关键一路**：B 与 A 同样坏 ⇒ 成因不止输入源（本轮 T2 就是靠它证明光换数据源不够、必须加边缘延拓）。
指标 = 按写回混合公式算出的**最终 RGB** 与原图之差，分 rim / band2 / core 三区，
外加 **A vs C 逐像素 RGB 完全相同比例**（core 必须 100%）。
**必须同时看 rim 与 core**：自适应阈值类算法里伪影会劫持 `maxIntensity` ⇒ rim 出白边的同时 core 被
阈值抬高废掉（实测 core Δ 恒 0），只盯边缘会漏掉半个 bug。
