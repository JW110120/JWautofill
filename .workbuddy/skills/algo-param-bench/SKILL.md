# 图像算法参数对拍（真实素材 + 定量结论）

**适用**：为图像处理算法选公式、定默认参数、验证某个「模式」到底做了什么。
**不适用**：纯 UI/样式改动，或没有真实素材可测的纯理论讨论。
**配套**：本项目算法现状与铁律见 `.workbuddy/memory/refs/pixel-algorithms.md`。

## 一、铁律（踩过的坑）

1. **落盘**：本仓 Edit 工具**经常「报成功但没落盘」**（多点、多行修改尤其明显）。改动多时直接 `Write` 整文件重写，或用 Node 脚本按行 `splice`（写回前逐行断言 + 写回后 `includes()` 复核）。本仓**行尾不统一**（`.tsx` LF、部分 `.ts` CRLF）⇒ 跨行字符串匹配在 CRLF 文件里必然失配。
2. **解码 PNG**：Python 侧用 PIL（`C:\Users\Administrator\.workbuddy\binaries\python\versions\3.13.12\python.exe`，已装 Pillow）；Node 侧复制文末解码器，**不要 `npm i pngjs`**（本仓 `node_modules` 是 UXP 用的，别污染）。
3. **素材路径**：用户粘贴的截图在 `C:\Users\Administrator\.workbuddy\clipboard-images\clipboard-<ISO>-<hash>.png`，用 Glob 取最新的；不要凭文件名猜。
4. ⚠️ **扫描网格上限必须等于实测数据最大值，不能外扩**。`max − end` 型指标（「是否单调」「反转量」）在定义域两端不一致时会算出假值 —— 曾把真实的 0.00 报成 37.62，且看起来完全合理。**所有单调性/极值指标，先断言网格两端 == 数据两端。**
5. **度量必须分档**。只报全图平均会把「背景几乎不动、特征被重压」这类效果完全抹平 ⇒ 先按偏离量分档（背景带/过渡带/特征带），每档单独报级数与百分比。
6. **先解析推、再数值验，两者必须一致**。不一致就是脚本 bug，不要相信数值。
7. **对拍脚本本身是本地临时草稿**：放本机临时目录（`outputs/`、`analysis/` 均已 gitignore）即可，**但不要把它们的路径写进长期记忆/spec**（本地会被清、不跨机同步）。交付时可用 present_files 给用户，让他能自己重跑。
8. **度量口径要按源码原样复刻**：容差、通道数（单通道 vs 四通道平方和）、`|0` 截断这类细节会改结论。
9. ⚠️ **JS 参数遮蔽会静默算错**：像素脚本里 `r,g,b` 是常用参数名，若同一函数签名里还有 `a,b` 当阈值/端点，`b` 会覆盖蓝通道 —— 结果只是「数值温和地不对」，不报错、不崩。**阈值一律叫 `a0,b0,lam`。**
10. **候选「方向」先由硬约束裁决，再讨论形态**：用户的质量条件（如「压缩后大小关系不能变」= 映射严格单调）常常直接砍掉一半方向 —— 本项目「保护小偏离像素」的方向在斜率上必然逆序，根本不用看它好不好看。**先问清「有没有质量约束」，比事后调参便宜得多。**
11. **否定一条实现路线时，要算出它对「目标之外」的影响**，别只讲道理（本项目否决一条路线时，除可解析证明的 alpha 通胀外，还实测出「选区外灰值 100 被抬亮 42–69 级」，比道理更有说服力）。

## 二、算法级对拍：绕开 PS，直接跑 TS 源

看截图只能看结果，定位不到「哪个像素被改成了什么」。算法类问题（斑驳/条纹/对齐不彻底/花屏）走这条闭环：

1. 解码截图 → 裸 RGBA（PIL 或手写解码器）。
2. **用 `typescript.transpileModule` 把 `src/adjustments/*.ts` 现场编译后 `require` 真函数**（保证与插件同源，不要手抄一份算法），跑完输出裸 RGBA + 指标 + 关键 console 日志。
3. 回合成垫纯白 PNG 肉眼看 + 打印局部区块的 `源值 / 结果值` 对照表（最能看出「相邻像素被拉到了不同层级」）。
4. 出多面板 before/after 对比图（PIL + `C:\Windows\Fonts\msyh.ttc` 可画中文标签）。

⚠️ **先用用户给的截图复现**：复现图与用户截图逐点一致后才开始改，否则所有结论都是猜的。

### 三个够用的度量（远好于「看起来还行」）
- **一阶差分粗糙度** = `mean(|a(x,y) − a(x±1,y)|)`（alpha>0 像素，横/纵分开）。斑驳与条纹的直接代理量。
- **3×3 中位数离群点占比** = `|a − median(3×3)| ≥ 20` 的比例。专抓棋盘格式斑驳。
- **直方图不同值数** + **输出均值 vs 选区众数**：一眼判断「对齐是否彻底、落到了哪一层」。

### 逐像素参照类算法的通病
逐像素**独立**估计参照 → 邻域内相邻像素选中不同层级 ⇒ 斑驳；沿笔触连成线 ⇒ 条纹；大量像素判为「不改」⇒ 对齐不彻底。
**修法不是再调阈值，而是给参照场加一次「窗口共识」**（窗口内出现次数达标的参照取极值），并对「没拿到参照」的像素按落差补判。补判门槛取「参照量程/2」这类**有语义的锚点**，不要选扫描出来的数值最优 —— 那是在过拟合单张素材。

## 三、标准流程

1. 找素材 → 解码 → 打印尺寸/均值/σ 与偏离分布直方图（先确认素材范围，比如是否含面板 UI）。
2. 定分档阈值（看直方图的谷底；天然可分才用单指标判据）。
3. 参数扫描：一维网格扫每个候选参数，对每个取值报**分档改动幅度 + 百分比 + 区分比**。
4. 传输曲线：`原始偏离 → 处理后的偏离`，标出「背景带」与「特征带」。这比任何指标都好读。
5. 单调性/伪影检查：扫定义域找极值点、报反转量，同时给出解析临界值互相印证。
6. 落盘脚本 + 输出 markdown 表格，给出「推荐值 + 为什么，以及不要选其他值的原因」。
7. **大数组不要用 spread 求极值**：`Math.max(...arr)` 在 20 万元素时抛 `RangeError`，改用循环累计。

**「选择比」= 特征带压缩率 / 背景带压缩率**，是判断「只压特征、不动背景」是否达成的核心指标（不要用「剩余偏离之比」，方向相反容易读反）。

## 四、不变量测试（改/还原算法前先架好，比参数扫描更早做）

把算法正确性拆成几条**可断言的不变量**，用合成图 + 真函数跑一遍就有结论：

| 不变量 | 断言写法 | 防的是什么 |
| --- | --- | --- |
| **幂等** | 同一输入连跑两次，第二次改动像素数 == 0 | 连点越改越实/越粗；也是「阈值/参照水平漂移」的探测器 |
| **集合不变** | 输出按同一阈值二值化，mask 与输入逐像素一致 | 形状被吃掉 / 被外扩 |
| **单侧单调** | 分类后逐像素比大小：内侧只削不抬、外侧只补不削 | 半透明内容被「描边」推实（湿边） |
| **上界** | 输出最大值 ≤ 本体水平（形状自身的实心不透明度） | 轮廓比本体更实 |

- **用例矩阵**：硬边不透明 / 硬边半透明 / 软边半透明 / 长台阶直边（触发分化分支）—— 4 个就够。
- **穿过轮廓的一行 alpha 剖面**（原图 vs 结果并排打出来）比任何指标都好读，一定打。
- ⚠️ **幂等断言是性价比最高的探测器**：残留哪怕只有几十像素、每次差 1 级，肉眼绝看不出，但它准确指向「某个中间量在两次运行之间变了」。**别把小残留当噪声放过 —— 那是设计缺陷的指纹。**
- 也要接受一个物理事实：**处理后的 1px@满不透明度 与 天生的 2px@半不透明度 像素值完全相同**，任何纯局部判据都分不开 ⇒ 验收标准应是「峰值不降、线心误差随点击单调收敛」，而不是「二次改动必须为 0」。

### trace 定位法（patch 一份副本，不要改源文件）
读源码 → `String.replace` 注入日志 → transpile → 跑两次。`replace` 的锚点必须唯一（用紧邻的注释行），只打印关心的像素（用 `globalThis.__TRACE` 集合过滤，别刷屏）。
**凡「从图像里现算的参照量」都要问一句：它依赖的那些像素，会被自己改动吗？** 会 → 逐次漂移、幂等破功。

## 五、兼容性回归三件套（用户要求「修 A，不能影响 B」）

别用「跑一堆合成场景看数值有没有变」来回答 —— 那只能证伪、不能证明。正确顺序：

### ① 变化集代数刻画（最强的一步）
把新旧判据写成集合关系。例：门槛从 `H1 < T` 改成 `ref < T`，而 `ref ≥ H1` **恒成立** ⇒ 新豁免集 ⊆ 旧豁免集 ⇒ **唯一变化集 = { H1 < T 且 ref ≥ T }**（不必再猜别的分支有没有被碰到）。
**推论：任何「参照量替换」都要先问新参照与旧参照的大小关系（≥ / ≤ / 不可比）。** 若不可比，就必须逐场景取证。

### ② 定向探针：把变化集打出来
在门槛行之前插一条记录（`[col, row, ref, H1, T]`），跑完只筛变化集里的格子。一次就能解释「为什么某处多了 1px」，比凭空猜机制快得多。

### ③ 差异像素分类（比「差异数」更有说服力的验收口径）
跑 OLD vs NEW 后**按类别统计**差异像素：

| 类别 | 判据 |
| --- | --- |
| 亚阈值碎片被清 | `0 < a0 ≤ THR` 且 OLD 保留、NEW 清零 ⇒ 本次要修的目标 |
| **墨像素(≥THR) 变化** | **必须为 0 才能说「没动本体」** |
| RGB 同时变化 | 查有没有误改颜色 |

⇒ 「差异 1232px = 亚阈值碎片被清 1232 / 墨像素变化 0」比「差异像素很少」强得多。

### ④ 变体源单常量扫描（标定 MIN/DIV 这类常数）
像素处理器**自包含、零 import** ⇒ 把「只改一个常量的副本」写到任意目录即可 `await import(...)`，一个脚本跑完参数网格，用**同一台架的同一场景**取舍。判定表必须同时列**目标指标**与**代价指标**，否则会只优化一边。⚠️ 生成变体时**先全部落盘再动态 import**（漏了生成步骤会得到 `ERR_MODULE_NOT_FOUND` 而不是「参数不存在」）。

### ⑤「不该动的笔画有没有被动」必须量轮廓位移
不能看字节差 —— 会被「绝大多数像素恰好没变」稀释（实测等宽长弧被推了左 5px/右 −6px，字节差却只有 1.1%）。正确口径：**量墨迹外沿（`alpha≥32`）的最左/最右像素**，逐行打 `ΔL / ΔR` 并给 max；合成一批「宽度恒定、只让路径变化」的用例，**理想结果就是轮廓一动不动**。
**修正项必须量纲自洽**：能从定义推出恒等式就别选经验阈值（例：由 `Δc=(ΔL+ΔR)/2`、`Δh=(ΔR−ΔL)/2` 推出任何真实变形都有 `|δc| ≤ |δh|` ⇒ 直接硬封顶 `|δc| ≤ |Δ|`）。
**索引转置类 bug 的症状**：不是「效果偏弱」，而是**所有「应逐字节一致」的场景一起大面积偏离** ⇒ 先跑「应零差异」的用例组当探针。

## 六、移植旧算法回来：用「逐字节保真比对」代替肉眼截图

用户说「旧版算法在该场景有可取之处，恢复它，但作用通道要扩展」时：

1. `git show <sha>:<path>` 把旧版整份拿出来当**参照实现**（若文件正是在该提交里被删的，用 `<sha>^:<path>`；先 `git log --oneline --follow -- <path>` 看历史）。
2. 同一脚本里 `transpileModule` **两个文件各转一份**再 `require`，一次跑出两版输出 ⇒ 断言 `diff === 0` ⇒ 「移植是忠实的」这句话才成立。**扩展的通道（新能力）单独断言语义**，别混在一起。
3. **扩展通道时先找出旧版里「与通道语义绑定」的常量**：旧版只处理 alpha 时写进各夹取的 `minAlpha` 之类的下限，换成 RGB 后必须回落成 0（否则深色内容找不到参照）；旧版的「层保护/邻域护栏」若依赖 alpha 的物理语义（另一条线、叠画带），**不要照搬到颜色通道**（颜色没有「层」，通道落差本身就是待修对象）。这类取舍要写进注释与 refs，并在 console 打命中计数，**不要静默改阈值**。
4. **「不激进」要用改动像素数证明**：同一素材分别跑新按钮与旧实现，报**改动像素数 + 档位数变化**，一句话回答「有多保守、有没有保留层次」。
5. ⚠️ **别漏了「没有目标缺陷时必须是 0 改动」这组用例**（如纯平直线 / 同水平交叉）—— 移植类改动最怕在正常内容上乱动，而这组是唯一的探针。

## 七、平滑 / 距离场类算法的对拍口径

- **基线怎么取**：不要用几轮前的 `*.bak`，直接 `git show HEAD:<path>` 导出到本地 `_old/`，台架同时 `import` 新旧两版做 A/B（Node 22 能直接 import `.ts`）。
- **两个必须同时报的度量，缺一会漏判**：
  1. **vs 旧版**（回归）：形状差（输出 mask 成员变化）/ 强差 `|Δα|≥128` / 弱差 / 占比。
  2. **vs 原图**（能力）：`改动像素数 + 平均Δα`，以及**跨轮廓的 alpha 剖面**与**边缘过渡带宽**。
     ⇒ 只报第 1 项会漏掉「改动更少、每条线都对，但平滑能力整体退化」。
- ⚠️ **局部的「到最近背景距离」(EDT) 不能当作该处线宽**：任何形状的边界像素到背景都只有 1px ⇒ 粗线边缘被误判成细线 ⇒ σ 被压到最低档 ⇒ 平滑能力掉到 1/4。正确判据要问「**附近有没有足够粗的结构**」（窗口内是否存在内切半径 ≥ k·σ 的线内像素），用积分图 O(1)/像素。
- ⚠️ **抗锯齿带宽随 σ 缩放时，最高档必须保持原值**；否则在某些参数下粗线边缘与旧版不一致。改完必须跑一遍 `radius × strength` 参数矩阵对拍。
- **分档 σ 的跳变会在边缘留下非单调剖面**（`255,251,254`）；只要保证「粗线整条落在同一档」就不会出现。

## 八、新增参数要打通「面板 → 转发 → 处理器」整条链

本项目 webpack 的 ts-loader 配了 **`transpileOnly: true`** ⇒ `--mode=production` **只转译、不做类型检查，0 error 完全不代表接对了线**。新增参数时漏声明接口字段或漏转发：**构建完全通过，但滑块拖动毫无效果**（值在转发层被静默丢弃）。唯一可靠的探测手段是**类型校验（不是构建）**：

```
npx tsc --noEmit          # 只指要查的文件亦可
```

- ⚠️ 判据**不看报错总数**（本仓约 700 条环境噪声：TS2705/TS2550/TS2583/TS2591/TS2307），只看**新增标识符是否出现在任何报错里**。
- ⚠️ 若临时写 tsconfig：`types: []` 是**必需**的（默认加载 `@types/node`，其 `ffi.d.ts` 含语法错 ⇒ **tsc 提前中止、一条 src 报错都不输出 = 假通过**）；`lib` 里必须带 `es2015.promise`（否则每个 `async` 报 TS2705）。
- **串参数链的检查清单**（少一处就静默失效）：接口字段 → 默认值对象 → 面板 state → 预设恢复 → 持久化 values → 持久化 deps → 复位 → 调用点传参 → 拖拽量程表 → switch case → handler ×2 → JSX 滑块行 → helpTexts 键。
- ⚠️ **逐行 splice 类补丁必须断言「上下文形状」，不能只断言锚点行存在**：多插/少插一个闭合标签时锚点照样存在（曾打破 JSX 平衡、webpack 报连锁语法错、看不出真因）。

## 九、度量与验收指标（补充）

- 「锯齿消没消」直接对应 **max|重心 − 真值线心|**（真值在合成图里已知）：硬阶梯 ≈0.25~0.50，好的 AA ≤0.05。只用「改动像素数」区分不出「变淡」和「消锯齿」。
- 抖动 Δ²（重心二阶差分）受整数舍入影响大，当粗筛可以、当验收不行。
- 端部效应单独看：把误差按行铺开找 max 落在哪几行。
- 复跑验收矩阵：`{近垂直, 近水平} × {线宽 1,2,3,4} × {本体 90,130,255} × {纯硬, 5% 毛刺, 50% 毛刺, 软笔刷}`，外加「压感渐变」与「连点 3~6 次看是否收敛」。改完算法**必须把旧验证台也一起跑**。

## 十、真实工况复现 + 恢复被删的旧实现

- 用户报「功能没有任何效果」时，先把他给的截图 PNG 解码、灰度反推 alpha 剖面：边缘是硬阶跃还是灰过渡、本体灰阶沿线漂移、截图是否被最近邻放大 ⇒ 常常直接指向「闸门太严」而非「算法没生效」。
- 恢复被某次提交删掉的功能：`git show <sha>:<path>` 取不到（文件正是在那个提交里被删的）⇒ 用 `git show <sha>^:<path>`（父提交的树）；先用 `git log --oneline --follow -- <path>` 看历史。

## 十一、环境与复核（本仓库）

## 附：PNG 解码器（8bit、非隔行；复制即用）

```js
const fs = require('fs'), zlib = require('zlib');
function loadPng(file) {
  const buf = fs.readFileSync(file);
  if (buf.readUInt32BE(0) !== 0x89504e47) throw new Error('not png');
  let off = 8, w = 0, h = 0, bd = 0, ct = 0, il = 0, plte = null;
  const idat = [];
  while (off < buf.length) {
    const len = buf.readUInt32BE(off), type = buf.toString('ascii', off + 4, off + 8);
    const d = buf.subarray(off + 8, off + 8 + len);
    if (type === 'IHDR') { w = d.readUInt32BE(0); h = d.readUInt32BE(4); bd = d[8]; ct = d[9]; il = d[12]; }
    else if (type === 'PLTE') plte = Buffer.from(d);
    else if (type === 'IDAT') idat.push(Buffer.from(d));
    else if (type === 'IEND') break;
    off += 12 + len;
  }
  if (bd !== 8 || il !== 0) throw new Error('只支持 8bit 非隔行');
  const chN = { 0: 1, 2: 3, 3: 1, 4: 2, 6: 4 }[ct];
  const raw = zlib.inflateSync(Buffer.concat(idat));
  const stride = w * chN, px = new Uint8Array(h * stride);
  let p = 0;
  for (let y = 0; y < h; y++) {
    const f = raw[p++], line = raw.subarray(p, p + stride); p += stride;
    const cur = px.subarray(y * stride, (y + 1) * stride);
    const prev = y > 0 ? px.subarray((y - 1) * stride, y * stride) : null;
    for (let i = 0; i < stride; i++) {
      const a = i >= chN ? cur[i - chN] : 0, b = prev ? prev[i] : 0, c = (prev && i >= chN) ? prev[i - chN] : 0;
      let v = line[i];
      if (f === 1) v += a; else if (f === 2) v += b; else if (f === 3) v += (a + b) >> 1;
      else if (f === 4) { const pa = Math.abs(b - c), pb = Math.abs(a - c), pc = Math.abs(a + b - 2 * c); v += (pa <= pb && pa <= pc) ? a : (pb <= pc ? b : c); }
      cur[i] = v & 255;
    }
  }
  const at = (x, y) => { const i = y * stride + x * chN;
    if (ct === 2 || ct === 6) return [px[i], px[i + 1], px[i + 2]];
    if (ct === 0 || ct === 4) return [px[i], px[i], px[i]];
    const q = px[i] * 3; return [plte[q], plte[q + 1], plte[q + 2]]; };
  return { w, h, at };
}
```

内缩 6px 避开截图外框；亮度用 `0.299R + 0.587G + 0.114B`。**判据用亮度、并用 RGB 欧氏 RMS ≈ √3×σ_L 验证「偏离全在明度轴上」后才成立。**
